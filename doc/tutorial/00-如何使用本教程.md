# 00 · 如何使用本教程

## 本章目标

读完之后你应该能回答：

- 我该「跟敲」还是「通读」？
- 一共要花多少时间？
- 出错了怎么快速定位？

---

## 先说清楚这个项目**不是**什么

它**不是**一个能复现 GPT-2 的项目。硬件差了约 1250 倍 FLOPs，做不到。

它**也不是**一个把 nanochat 拆开讲讲的注释版。nanochat 的优化器有 3 个变体、
5 个残差流 trick、ZeRO-2 手写通信，一次性全塞给你只会让你迷路。

它**是**一个把 nanochat 的每个设计**单独拆出来、单独验证**的教学项目。
每一个设计你都会亲手打开、关掉、看数字。

---

## 两条路线

### 路线 A：跟敲（推荐，约 17 小时）

每章的「手抄代码」块自己敲进 `src/` 对应文件。敲完跑「动手验证」，
数字对了才继续下一章。

好处：你会记住那些「不这么做就会 nan / 会泄漏未来 / 会静默算错」的坑。
本项目里的每一个坑都是真踩过的，代码注释里都标了「曾经的 bug」。

坏处：慢，而且中途会有很多次「数字不对」的挫败。

### 路线 B：通读（3-4 小时）

代码已经在 `src/` 里了（`git checkout solution` 之后）。
本教程当注释读，重点看每章的「概念」和「延伸」两节。

好处：快速建立全貌，知道每个零件叫什么、为什么存在。
坏处：坑还是会踩，只是知道坑名叫什么。

### 混合（我最推荐的）

**卷 1-4 跟敲**（数据、模型、trick、优化器 —— 这是理解 GPT 的核心），
**卷 5-8 通读**（训练循环、分布式、对齐 —— 这些更像工程而非原理）。

---

## 时间预算

| 卷 | 内容 | 跟敲 | 通读 |
|---|---|---|---|
| 0 | 准备 | 20 min | 10 min |
| 1 | 数据（5 章） | 2.5 h | 40 min |
| 2 | 模型（9 章） | 4 h | 1 h |
| 3 | trick（5 章） | 2 h | 30 min |
| 4 | 优化器（8 章） | 5 h | 1.5 h |
| 5-8 | 循环/分布/对齐 | 3 h | 1 h |
| **合计** | | **~17 h** | **~5 h** |

> **和 README 说的「8-11 小时」差在哪？** 两个数都在量同一个项目，但量的不是同一件事：
>
> | 口径 | 数字 | 包含什么 |
> |---|---|---|
> | **纯敲代码** | 8-11 h | 只把 ~2100 行敲进 `src/`，键盘时间 |
> | **跟敲（本章口径）** | ~17 h | 敲代码 + 每章「动手验证」跑通 + 卡住时读概念 |
> | **+ 消融实验** | 再加 4-8 h | 见下 |
>
> 按哪个估都行，取决于你卡住时会不会回去读「概念」小节。
> 保守起见：**按 17 h 规划**，做快了你会有意外。

加上做**消融实验**的时间还要再加 4-8 小时
（每次 smoke 档训练 2-3 分钟，跑 20 组对比约 1 小时，但思考要很久）。

## 四档规模怎么选

```bash
bash script/train_base.sh debug     # 秒级。写代码时用这个，改一行就重跑
bash script/train_base.sh smoke     # 2-3 分钟。每章的「动手验证」用这个
bash script/train_base.sh ablation  # d6，约 44 分钟。做消融实验用这个（信号更干净）
bash script/train_base.sh full      # d24，约 41 小时。消融后的最佳组合，只训一次
```

**关键**：消融实验必须用 `ablation` 档。`smoke` 档只有 896 步、14M token，
val bpb 的随机波动（约 ±0.02）会比你要测的效应（0.01-0.05）还大，
测出来的结论不可信。

> **`ablation` 和 `full` 的区别不是「大小」，是「用途」。**
> `ablation`（d6）的基线**刻意保持中性**：Muon `simple` + 5 个 trick 全关。
> 这一点很关键 —— 如果基线自己就开了 trick，你测出来的是「A 相对 A+B」，
> 单项贡献被稀释，消融表就失去意义了。
> `full`（d24）则相反：它开满 nanochat 生产配置，只训一次、不做对照。

## 出错了怎么定位

**第一步永远是跑测试**：

```bash
uv run pytest tests/ -v
```

194 个章节判据专门覆盖「看起来对其实错了」的 bug。你在跟敲过程中改坏东西，
测试会立刻告诉你哪里坏了。

> 刚开始跑时看到一堆 `failed` 是**对的** —— `main` 分支的 `src/` 是骨架，
> 那些 failed 就是你的待办清单。见 README 的「环境自检」。

几个重点：

| 测试名 | 锁住的坑 |
|---|---|
| `test_sdpa_layout_is_bhtd_not_bthd` | PyTorch SDPA 严格按 `(B,H,L,E)` 解读，`T==1` 时形状会**悄悄变** |
| `test_kv_cache_writes_all_batches` | `scatter_` 配 stride-0 索引会漏写 batch 的非 0 行 |
| `test_causality_no_future_leak` | attention 的 causal mask 漏了（最严重的 bug） |
| `test_rope_relative_position` | RoPE 的相对位置性质 |
| `test_muon_plus_rescues_low_rank` | Newton-Schulz 推不动近零奇异值 |
| `test_forward_loss_starts_uniform` | 初始 loss 应该 ≈ `ln(vocab_size)`，nan 就说明初始化坏了 |

**第二步**：如果 loss 变成 `nan`，99% 是这三类原因：

1. 某个张量没被正确初始化（检查是不是在 meta device 上创建了却没重算）
2. 整批 `targets` 都是 `-1`（`F.cross_entropy` 算 0/0）
3. 某个除法/范数分母为 0

**第三步**：`debug` 档 + 在关键位置打印张量的 `dtype` / `shape` / `abs().max()`。
十六进制内存地址式的报错信息基本都和 dtype 或 shape 有关。

## 一个建议：不要跳过消融实验

如果你只读概念不跑消融，最后你会得到一堆「听起来很有道理」的知识，
但说不出 RoPE 到底值多少 bpb、Muon 比 AdamW 好多少、滑窗在 SDPA 上慢多少倍。

消融实验是这个教程唯一能给你的东西。全部做完你会得到一张表，
长这样（数字需要你自己跑出来）：

| 组件 | 打开 | 关掉 | bpb 差异 | 结论 |
|---|---|---|---|---|
| RoPE | ? | ? | ? | ? |
| QK Norm | ? | ? | ? | ? |
| ReLU² vs GELU | ? | ? | ? | ? |
| 权重绑定 | ? | ? | ? | ? |
| logit softcap | ? | ? | ? | ? |
| Muon simple vs advanced | ? | ? | ? | ? |
| best-fit 打包 vs 朴素 | ? | ? | ? | ? |
| ... | | | | |

这张表是**你**的，不是 nanochat README 上的。这才是这个项目存在的意义。

**下面是用 `smoke` 档实测的真实结果**（你的 `ablation` 档数字会不同，
但量级关系应该一致）：

| 变体 | val_bpb | Δ | 解读 |
|---|---|---|---|
| 基线（RoPE + QK-Norm + ReLU²） | 1.7136 | — | |
| **去掉 RoPE** | 1.8013 | **+0.0877** | 最大的单项影响。序列 512 已经开始依赖位置信息 |
| **GELU 替代 ReLU²** | 1.7240 | **+0.0104** | relu² 确实略好，印证 nanochat 的说法 |
| 去掉 QK Norm | 1.7098 | −0.0038 | **噪声**（\|Δ\|<0.02，按纪律要重跑确认） |

**怎么复现**：

> ⚠ 这张表里的数字来自 **smoke 档**（d4 / 896 步 / 2-3 分钟），不是 full 档。
> 它们足以看出 RoPE、ReLU² 这种**大效应**（Δ 0.01 ~ 0.09），
> 但 QK-Norm 那一行（Δ −0.0038）落在噪声范围内，**不能下结论**。
> 要得出可信结论必须用 `ablation` 档（d6 / 3096 步 / 约 44 分钟）：
> smoke 档的 bpb 噪声（±0.02）大于大部分单项效应本身。

```bash
# smoke 档（快，适合先跑通流程）
uv run python -m training.train_base --mode smoke --no-resume --model-tag d4base
uv run python -m training.train_base --mode smoke --no-resume --model-tag d4norope --no-rope
uv run python -m training.train_base --mode smoke --no-resume --model-tag d4gelu --activation gelu
bash scratch/ablation.sh d4base

# ablation 档（可信结论）
uv run python -m training.train_base --mode ablation --no-resume --model-tag d6_base
uv run python -m training.train_base --mode ablation --no-resume --model-tag d6_norope --no-rope
bash scratch/ablation.sh d6_base

# 顺便验一下 weight decay（full 档「最佳超参」里唯一没实测依据的一个）
uv run python -m training.train_base --mode ablation --no-resume --muon-weight-decay 0.05 --model-tag d6_wd005
uv run python -m training.train_base --mode ablation --no-resume --muon-weight-decay 0.1  --model-tag d6_wd01
bash scratch/ablation.sh d6_base
```

> **关于 weight decay 的 λ=0.1**：那是**按量级推测**的值，不是抄来的 ——
> nanochat 把 `weight_decay` 放在 train 脚本的 CLI 默认值里，不进 `optim.py`。
> 而且缩放因子随档位变化 **9.5 倍**（`full` 0.213 / `ablation` 2.039），
> 所以 λ **不能跨档位照搬**。详见第 01 章「关于 weight decay 的一处诚实标注」。

**三个必须注意的坑**（我踩过）：

1. **不加 `--no-resume` 会得到全等的 bpb。**
   auto-resume 会把上次同名 tag 的存档捡起来，0 步就跑完了。
   表现是所有变体的 bpb 一模一样，看起来像「所有架构都毫无影响」。

2. **`debug` 档（20 步）测不出架构差异。**
   实测五组变体的 bpb 全部是 3.2564 —— 模型还在初始化附近，
   架构还没来得及起作用。**消融必须用 `ablation` 档**
   （`smoke` 勉强能看趋势，`ablation` 才能下结论）。

3. **`|Δ| < 0.02` 时重跑一次。**
   那个量级是初始化随机性的波动范围，不是真实效应。
