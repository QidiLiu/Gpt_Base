## 概念：一次训练的全景

先把最粗的骨架画出来。**从一行原始文本到一个被更新的参数**，中间经过这些环节：

```
   ClimbMix parquet shard（磁盘，92MB 压缩包，每行是一篇文档）
        │
        │  pyarrow 逐 row_group 读取（每次约 1024 篇、3MB）
        ▼
   原始文本（一堆长短不一的字符串）
        │
        │  tiktoken BPE 编码，每篇前面加 <|bos|>
        ▼
   token id 列表（一堆长短不一的 list[int]）
        │
        │  ★ best-fit 装箱：塞成定长行
        ▼
   (B, T+1) 的整数张量   ← 至此「文本」变成了「矩阵」
        │
        │  切出 inputs = row[:-1], targets = row[1:]
        ▼
   inputs (B,T)   targets (B,T)
        │
        │  embedding 查表 → (B,T,D)
        │  RoPE / QK-Norm / 注意力 / MLP / logit softcap
        ▼
   logits (B,T,V)
        │
        │  softcap → 切掉 padding → fp32 → cross_entropy
        ▼
   一个标量 loss
        │
        │  反向传播
        ▼
   每个参数的 .grad
        │
        │  Muon（矩阵参数，正交化后更新）
        │  AdamW（嵌入/标量，逐元素归一化步长）
        ▼
   更新后的参数
        │
        │  torch.save
        ▼
   runs/base_checkpoints/dN/model_XXXXXX.pt
```

把上面每个框对应到代码：

| 框 | 代码位置 |
|---|---|
| 读 parquet | `src/data/dataset.py: list_parquet_files` + `src/data/dataloader.py: iter_documents` |
| BPE 编码 | `src/data/tokenizer.py: BPETokenizer.encode` |
| **best-fit 装箱** | `src/data/dataloader.py: make_dataloader` ← 卷1 核心 |
| 切 inputs/targets | `src/data/dataloader.py: make_dataloader`（`cpu_inputs` / `cpu_targets`） |
| 模型前向 | `src/model/gpt.py: GPT.forward` + `src/model/layers.py` |
| loss | `src/model/gpt.py: GPT.forward` 最后 10 行 |
| 优化器 | `src/optim/muon.py: MuonAdamW.step` + `orthogonalize.py` |
| 存档 | `src/common/checkpoint.py: save_checkpoint` |
| 训练循环 | `src/training/train_base.py: main` |

## 概念：为什么是这个顺序

有几个设计上的因果链，值得先想清楚，否则后面每章都会觉得「为什么这么绕」。

**为什么先打包再切 targets，而不是先切再打包？**
因为要构造 `inputs[i]` 和 `targets[i]` 这一对，必须同时有第 `i` 和第 `i+1` 个 token。
所以每行需要 `T+1` 个 token，最后一个 token 只当 target 不当 input。
这个「多出来的一个 token」是整套数据管线里最容易被忽略的细节。

**为什么打包时不 padding，而 SFT 时 padding？**
预训练的数据是海量自然文本，padding token 的占比如果很高，模型就会学到
「一大段 pad 是什么」这种推理时永远用不到的模式。宁可裁掉 35% 的 token。
SFT 的数据量小（几十万条），不 padding 的话显存会爆炸，所以必须补齐，
用 `<|bos|>` 补，并且把它的 loss mask 掉。

**为什么 tokenizer 要单独训，而不是训练时顺便学？**
分词器是离散优化（每一步 merge 都是全局选择），没有梯度。
必须先用一批文本把它训好冻结，再开始训模型。

**为什么优化器分两组（Muon + AdamW）？**
判据是「参数在矩阵乘里扮演什么角色」。
2D 矩阵参与大规模 GEMM，梯度谱严重不均衡 → 适合正交化（Muon）。
嵌入是查表，梯度稀疏 → 正交化会毁掉它 → 用 AdamW。
标量只有一个元素 → 正交化无从谈起 → 用 AdamW。

## 概念：本项目的硬件约束

这一节很重要，因为它决定了后面每一个「为什么这么简化」的选择。

**实测的硬件**：

| 项 | 值 |
|---|---|
| GPU | 1× RTX 4060 Ti, SM 8.9 (Ada), **16 GB** |
| 内存 | 15 GB |
| bf16 | 支持（Ampere 之后都有） |
| Flash Attention 3 | **不可用**（FA3 主要为 Hopper 编译） |
| FP8 | **不可用**（fp8 tensor core 是 Blackwell 才有） |
| 多卡 DDP | **不可用**（只有 1 张卡） |
| torch.compile | **不可用**（缺 C 编译器，见下） |

**由此推出的四个设计决策**：

1. **不用 FA3，全部走 PyTorch SDPA。**
   代价：SDPA 只认 `(B,H,L,E)` 布局，所以我们在 `sdpa_bt()` 里做了转置。
   而且 SDPA **不支持滑动窗口**，开了滑窗就必须自己造 mask，性能悬崖见第 20 章。

2. **不用 fp8。** 第 12 章 nanochat 的 speedrun 用 fp8 快了 4%，
   我们没有这个选项，纯粹因为硬件。

3. **分布式代码只写不跑。** `src/optim/muon.py` 里有完整的 ZeRO-2 分支
   （`reduce_scatter_tensor` / `all_gather_into_tensor` / 分片优化器状态），
   但 `world_size` 恒为 1，永远走退化路径。留着它是因为「为什么 nanochat
   不用 DDP」这个问题只有读到那段代码才有答案。

4. **torch.compile 会静默降级。** 缺 C 编译器时 inductor 会失败。
   `src/optim/muon.py: compile_or_eager` 会在第一次调用时用真实张量试跑一次，
   失败就永久切回 eager，并在日志里告诉你。想启用它：
   `sudo apt install gcc`。这不影响正确性，只影响速度。

**训练预算的实测量级**（用 nanochat 的 FLOPs 公式算的）：

| 档位 | FLOPs/token | 总 FLOPs | 实测耗时 | MFU |
|---|---|---|---|---|
| `smoke` (d4) | 14.2 M | 2.1e14 | 1m46s | 3.0% |
| `full` (d6) | 130 M | 2.6e16 | 预计 20-25 min | ~3% |

**MFU 只有 3% 很正常**，两个原因：
- 模型太小（d6 只有 1700 万参数），GPU 算不满，瓶颈在 kernel launch 开销
- torch.compile 没开，优化器的 Python 循环开销占比很高

**nanochat 在 8×H100 上 MFU 能到 40%+。** 差距主要来自规模和编译。

want = F.scaled_dot_product_attention(       # 正确：转成 (B,H,T,D)
    q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2), is_causal=True).transpose(1, 2)
got = F.scaled_dot_product_attention(q, k, v, is_causal=True)   # 错误：直接喂 (B,T,H,D)

print(f"输入 (B,T,H,D) = {tuple(q.shape)}，我们要 {H} 个头 x 长度 {T}")
print(f"形状相同       = {want.shape == got.shape}")

</details>

跑：

```bash
mkdir -p scratch && uv run python scratch/hardware.py
```

**最后一段的输出是本教程最重要的一次警告**：

```
输入 (B,T,H,D) = (2, 3, 6, 32)，我们要 6 个头 x 长度 3
形状相同       = True
数值相同       = False
最大绝对误差   = 4.7833
```

本项目全程用 `(B,T,H,D)` 布局（这是 nanochat 和 Flash Attention 3 的约定），
但 PyTorch 的 `scaled_dot_product_attention` 严格按 `(B,H,L,E)` 解读输入。
直接喂 `(2,3,6,32)`，它会理解成「3 个头、每个头长度 6」—— 算的是另一个东西。

**而且它不报错、输出形状也刚好一样。** 因为 q/k/v 三个张量内部是自洽的，
只是整套被重新解释了。这种 bug 会跑通、会出 loss 曲线、loss 还会下降，
但训出来的模型是错的。

只有当 q 的「长度」维恰好和 k 的「头数」维撞上时才会暴露成 RuntimeError；
更常见的情况就是这种静默算错。

第 11 章会详细讲。修法在 `src/model/layers.py: sdpa_bt()` ——
进 SDPA 前把 T 和 H 对调，出来后再对调回来。

### 验证 1：看一次完整的 smoke 训练

```bash
bash script/train_base.sh smoke
```

盯住这几个数字，它们分别对应不同的机制：

| 日志行 | 对应什么 | 本章第几节讲过 |
|---|---|---|
| `词表 8192（padding 后 8192）` | 词表对齐到 64 的倍数 | 「为什么先打包再切 targets」 |
| `scaling 参数量  1,835,008` | 用于 scaling law 的参数量口径 | 卷5 |
| `全局 batch  16,384 = 4 × 8×512` | 梯度累积的分解 | 卷5 |
| `GPU 峰值算力（fp32累加）= 82.6 TFLOPS` | GeForce 的 fp32 累加减半 | 本章硬件表 |
| `step 0 loss 9.0109` | 初始 loss ≈ `ln(8192)=9.011` | 第 07 章 |
| `bpb: 总 nats=... / 总字节=...` | bpb 的两个累加量 | 第 06 章 |

**第一个 loss 必须是 9.0109 左右**（= `ln(8192)`）。这说明模型初始时对所有 token
几乎等概率，即「什么都没学到」。如果第一个 loss 偏离这个值很大，
说明初始化被改坏了 —— 跑 `pytest -k uniform` 检查。

### 验证 2：确认数据管线的不变量

新建 `scratch/check_data.py`：

```python
from data.tokenizer import get_tokenizer
from data.dataloader import make_dataloader

tok = get_tokenizer()
bos = tok.get_bos_token_id()
dl = make_dataloader(tok, batch_size=4, seq_len=512, split="train", device="cpu")
x, y, st = next(dl)

print("inputs ", tuple(x.shape), x.dtype)
print("targets", tuple(y.shape))
print("state  ", st)
print()

# 不变量 1：targets 就是 inputs 右移一位
assert (y[:, :-1] == x[:, 1:]).all(), "targets 必须是 inputs 的右移"
print("[OK] targets == inputs 右移一位")

# 不变量 2：每行以 BOS 开头
assert (x[:, 0] == bos).all(), "每行必须以 BOS 开头"
print("[OK] 每行以 <|bos|> 开头")

# 不变量 3：没有 padding —— 所有 token id 都在 [0, vocab) 内
V = tok.get_vocab_size()
assert ((x >= 0) & (x < V)).all() and ((y >= 0) & (y < V)).all()
print(f"[OK] 无 padding，全部落在 [0, {V})")

# 观察：文档边界 = BOS 的位置
n_bos = (x[0] == bos).sum().item()
print(f"\n第 0 行里有 {n_bos} 个 BOS，即约 {n_bos} 篇文档")
print("前 20 个 token：")
print(" ", tok.visualize(x[0, :20].tolist(), with_token_id=True))
```

跑：

```bash
uv run python scratch/check_data.py
```

**这个实验值得仔细看输出**。你会看到 ClimbMix 的文档很长（中位数 2400 字符
≈ 740 token），而 seq_len=512。所以**一行里通常只有 1 篇完整文档 + 下一篇被裁掉的开头**。
BOS 的数量远小于「512/平均文档长度」，因为大部分文档根本放不进去。

这直接引出第 05 章的核心问题：**这个裁剪浪费了 35% 的 token，值得吗？**

## 常见坑

**坑 1：uv 装的 torch 找不到 CUDA。**
检查是不是用了 PyPI 的默认 torch 而不是 cu132 版本：
```bash
uv run python -c "import torch; print(torch.__version__, torch.version.cuda)"
```
应该输出类似 `2.14.0+cu132 13.2`。如果 cuda 是 None，说明索引没生效，
删掉 `uv.lock` 和 `.venv` 重跑 `uv sync`。

**坑 2：`uv sync` 报 `Failed to find C compiler`。**
这不是错误，是 torch.compile 探测失败后的**提示**。代码会自动回落到 eager。
想启用编译：`sudo apt install gcc`。

**坑 3：下载数据卡住不动。**
本机 `huggingface.co` 不可达，必须走 `hf-mirror.com`。
检查 `echo $HF_ENDPOINT` 应该有值。`script/_common.sh` 里已经默认设了。

**坑 4：16GB 显存不够。**
降 `--device-batch-size`：`bash script/train_base.sh full --device-batch-size 8`。
但要注意 `total_batch_size` 必须能被 `device_batch_size × sequence_len` 整除，
否则 `resolve_scaling` 会直接 assert（这是故意的，比静默算错好）。

**坑 5：loss 变成 nan。**
看 `src/model/gpt.py` 里的警告日志。最常见是整批 targets 都是 -1。
详见第 00 章的「出错了怎么定位」。

## 延伸

**nanochat 完整版怎么做的**

| 维度 | nanochat | 本项目 | 为什么简化 |
|---|---|---|---|
| 硬件 | 8×H100 80GB | 1×4060Ti 16GB | 现实 |
| 注意力 | Flash Attention 3 | PyTorch SDPA | Ada 上没有 FA3 |
| 精度 | bf16 + **fp8** | bf16 | fp8 要 Blackwell |
| 分布式 | ZeRO-2（8 卡） | 写但不跑 | 只有 1 张卡 |
| 优化器 | Muon advanced（Polar Express + MuonEq + Muon+ + NorMuon + 谨慎 WD） | 两种都实现，默认 simple | 教学分层 |
| 深度 | d12-d32 | d2-d6 | 显存与时间 |
| 词表 | 32768 | 8192 / 16384 | 小模型的 embedding 不能太大（见第 02 章） |
| 目标 | 超过 GPT-2 的 CORE 分 | **让每个组件可测量** | 完全不同的目标 |

**本项目每个简化都是硬件或教学目的导致的，不是「这样更好」。**
等你的显卡更强（或者你去租 8×H100），把 `src/optim/muon.py` 的
`flavor="advanced"` 打开、把 `--fp8` 加上、把 d 调到 24，
你就是在跑 nanochat 的 speedrun 了。
