## 概念：一次训练的全景

先把最粗的骨架画出来。**从一行原始文本到一个被更新的参数**，中间经过这些环节：

```
   ClimbMix parquet shard（磁盘，92MB 压缩包，每行是一篇文档）
        │
        │  pyarrow 逐 row_group 读取（每次约 1024 篇、3MB）
        ▼
   原始文本（一堆长短不一的字符串）
        │
        │  tiktoken BPE 编码，每篇前面加 <|bos|>
        ▼
   token id 列表（一堆长短不一的 list[int]）
        │
        │  ★ best-fit 装箱：塞成定长行
        ▼
   (B, T+1) 的整数张量   ← 至此「文本」变成了「矩阵」
        │
        │  切出 inputs = row[:-1], targets = row[1:]
        ▼
   inputs (B,T)   targets (B,T)
        │
        │  embedding 查表 → (B,T,D)
        │  RoPE / QK-Norm / 注意力 / MLP / logit softcap
        ▼
   logits (B,T,V)
        │
        │  softcap → 切掉 padding → fp32 → cross_entropy
        ▼
   一个标量 loss
        │
        │  反向传播
        ▼
   每个参数的 .grad
        │
        │  Muon（矩阵参数，正交化后更新）
        │  AdamW（嵌入/标量，逐元素归一化步长）
        ▼
   更新后的参数
        │
        │  torch.save
        ▼
   runs/base_checkpoints/dN/model_XXXXXX.pt
```

把上面每个框对应到代码：

| 框 | 代码位置 |
|---|---|
| 读 parquet | `src/data/dataset.py: list_parquet_files` + `src/data/dataloader.py: iter_documents` |
| BPE 编码 | `src/data/tokenizer.py: BPETokenizer.encode` |
| **best-fit 装箱** | `src/data/dataloader.py: make_dataloader` ← 卷1 核心 |

| 存档 | `src/common/checkpoint.py: save_checkpoint` |
| 训练循环 | `src/training/train_base.py: main` |

## 概念：为什么是这个顺序

有几个设计上的因果链，值得先想清楚，否则后面每章都会觉得「为什么这么绕」。

**为什么先打包再切 targets，而不是先切再打包？**
因为要构造 `inputs[i]` 和 `targets[i]` 这一对，必须同时有第 `i` 和第 `i+1` 个 token。
所以每行需要 `T+1` 个 token，最后一个 token 只当 target 不当 input。
这个「多出来的一个 token」是整套数据管线里最容易被忽略的细节。

**为什么打包时不 padding，而 SFT 时 padding？**
预训练的数据是海量自然文本，padding token 的占比如果很高，模型就会学到
「一大段 pad 是什么」这种推理时永远用不到的模式。宁可裁掉 35% 的 token。
SFT 的数据量小（几十万条），不 padding 的话显存会爆炸，所以必须补齐，
用 `<|bos|>` 补，并且把它的 loss mask 掉。

**为什么 tokenizer 要单独训，而不是训练时顺便学？**
分词器是离散优化（每一步 merge 都是全局选择），没有梯度。
必须先用一批文本把它训好冻结，再开始训模型。

**为什么优化器分两组（Muon + AdamW）？**
判据是「参数在矩阵乘里扮演什么角色」。
2D 矩阵参与大规模 GEMM，梯度谱严重不均衡 → 适合正交化（Muon）。
嵌入是查表，梯度稀疏 → 正交化会毁掉它 → 用 AdamW。
标量只有一个元素 → 正交化无从谈起 → 用 AdamW。

## 概念：本项目的硬件约束

这一节很重要，因为它决定了后面每一个「为什么这么简化」的选择。

**实测的硬件**：

| 项 | 值 |
|---|---|
| GPU | 1× RTX 4060 Ti, SM 8.9 (Ada), **16 GB** |
| 内存 | 15 GB |
| bf16 | 支持（Ampere 之后都有） |
| Flash Attention 3 | **不可用**（FA3 主要为 Hopper 编译） |
| FP8 | **不可用**（fp8 tensor core 是 Blackwell 才有） |
| 多卡 DDP | **不可用**（只有 1 张卡） |
| torch.compile | 可用（需 C 编译器，见下） |

**由此推出的四个设计决策**：

1. **不用 FA3，全部走 PyTorch SDPA。**
   代价：SDPA 只认 `(B,H,L,E)` 布局，所以我们在 `sdpa_bt()` 里做了转置。
   滑窗比较麻烦：SDPA 的 flash 后端**不接受 attn_mask**（硬钉会抛
   `No available kernel`），所以滑窗改走 PyTorch 内建的 `flex_attention`，
   它编译出的是 FA2 风格的 kernel 且原生支持块级滑窗 mask（实测
   0.50ms → 0.18ms）。两条路径都保留（`ModelConfig.attn_impl` 开关），
   因为第 20 章要教的「性能悬崖」需要一个慢的参照物。

2. **不用 fp8。** 第 12 章 nanochat 的 speedrun 用 fp8 快了 4%，
   我们没有这个选项，纯粹因为硬件。

3. **分布式代码只写不跑。** `src/optim/muon.py` 里有完整的 ZeRO-2 分支
   （`reduce_scatter_tensor` / `all_gather_into_tensor` / 分片优化器状态），
   但 `world_size` 恒为 1，永远走退化路径。留着它是因为「为什么 nanochat
   不用 DDP」这个问题只有读到那段代码才有答案。

4. **torch.compile 的降级兜底。** inductor 需要一个 C 编译器（`gcc`）。
   `src/optim/muon.py: compile_or_eager` 会在第一次调用时用真实张量试跑一次，
   编译失败就永久切回 eager，并在日志里告诉你一行。
   本机实测有 gcc 15.2，**编译正常工作** —— 这一点很重要，因为：
   - 少了编译，`muon_step` 会慢约 1.2 倍（full 档 55 小时 vs 45 小时）
   - 更隐蔽的是：编译失败**不报错**。有一个真实 bug 就是
     `hp["wd"] != 0` 这个 data-dependent branching 让 `fullgraph=True`
     拒绝编译，于是 Muon advanced 静默回落 eager，日志里只有一行
     「回落到 eager」，极易漏看。详见第 28 章。
   没装编译器时：`sudo apt install gcc`。这不影响正确性，只影响速度。

**训练预算的实测量级**（FLOPs 用 nanochat 的公式算，耗时是实测）：

| 档位 | FLOPs/token | 总 FLOPs | 实测耗时 | MFU |
|---|---|---|---|---|
| `smoke` (d4) | 14.2 M | 2.1e14 | 1m46s | 3.0% |
| `ablation` (d6) | 130 M | 2.6e16 | 实测约 44 min | 13.4% |
| `full` (d24) | 1.32 G | 2.9e18 | 实测约 41 h | **23.6%** |

（`ablation` / `full` 的耗时区间对应「trick 与 Muon flavor 开不开」，
见 `config.py` 的 PRESETS 注释里的 2×2 实测表。）

**MFU 从 3% 到 23.6%，差在模型规模，不在编译。** 实测 `full` 档每步的时间分布：

| 阶段 | 占比 |
|---|---|
| forward | 32.8% |
| backward | 66.6% |
| optimizer.step() | **0.7%** |

三个推论：

- **优化器的 Python 开销可以忽略**（0.7%）。这条曾经写反过 ——
  早期文档说「优化器的 Python 循环开销占比很高」，那是没有实测的猜测。
  优化器逻辑（Muon + 正交化 + 谨慎 WD）确实在 Python 里，但它的
  工作量与参数量成正比（一次遍历），而 fwd/bwd 要过 346M 参数的矩阵。
- **smoke 档 MFU 低（3%）是正常的**：d4 只有 1.8M 参数，矩阵乘太小，
  GPU 算不满，瓶颈在 kernel launch 开销而非算力。这也是为什么
  消融必须用 `ablation` 档而不是 `smoke`。
- **23.6% 是这张卡的真实上限**，不是配置没调好。实测把
  `device_batch_size` 从 4 加到 8，MFU 纹丝不动（23.7% → 23.6%）
  —— GPU 早就吃饱了。详见 `config.py` 里 PRESETS 的 dbs 实测阶梯。

**nanochat 在 8×H100 上 MFU 能到 40%+。** 差距来自规模（H100 的
bf16 tensor core 吞吐约是 4060 Ti 的 12 倍，且有 fp8）和 FA3。

**最后一段的输出是本教程最重要的一次警告**：

```
输入 (B,T,H,D) = (2, 3, 6, 32)，我们要 6 个头 x 长度 3
形状相同       = True
数值相同       = False
最大绝对误差   = 4.7833
```

本项目全程用 `(B,T,H,D)` 布局（这是 nanochat 和 Flash Attention 3 的约定），
但 PyTorch 的 `scaled_dot_product_attention` 严格按 `(B,H,L,E)` 解读输入。
直接喂 `(2,3,6,32)`，它会理解成「3 个头、每个头长度 6」—— 算的是另一个东西。

**而且它不报错、输出形状也刚好一样。** 因为 q/k/v 三个张量内部是自洽的，
只是整套被重新解释了。这种 bug 会跑通、会出 loss 曲线、loss 还会下降，
但训出来的模型是错的。

只有当 q 的「长度」维恰好和 k 的「头数」维撞上时才会暴露成 RuntimeError；
更常见的情况就是这种静默算错。

第 11 章会详细讲。修法在 `src/model/layers.py: sdpa_bt()` ——
进 SDPA 前把 T 和 H 对调，出来后再对调回来。

### 验证 2：确认数据管线的不变量

🔒 需要：卷 1 第 02-05 章

```bash
uv run python scratch/check_data.py
```

**这个实验值得仔细看输出**。你会看到 ClimbMix 的文档长度差异很大
（本项目实测：2048 篇样本里 min=4、**中位数 628** token、p75=829、max=25055），
而 seq_len=512。所以**一行里往往只有 1 篇文档，甚至放不下一篇完整的**。

顺带说明一下 nanochat 的 docstring 里写的「约 35% token 被裁掉」：
那是他们在 T=2048 和全量数据下的数字。我们这个 shard 的文档更短
（中位数 628 而非他们说的 740），所以实测裁剪率低得多
（`uv run python scratch/packing_demo.py` 会给出准确数字，T=512 时约 0.5%）。

这直接引出第 05 章的核心问题：**这个裁剪浪费了 token，值得吗？**

## ★ 消融实验

本章不做消融（还没到能改的地方）。但先把实验框架搭好 —— 第 04、05 章会开始用。

`train_base.sh` 支持透传任意命令行参数，所以做消融只要：

```bash
# 基线（--no-resume 必须加，否则 auto-resume 会把上次的存档捡起来，0 步跑完）
bash script/train_base.sh ablation --no-resume
cp runs/base_checkpoints/d6/history.csv scratch/ablation_baseline.csv

# 消融：关掉 QK Norm
bash script/train_base.sh ablation --no-qk-norm --model-tag d6_noqknorm
cp runs/base_checkpoints/d6_noqknorm/history.csv scratch/ablation_noqknorm.csv
```

**关键纪律**：
- 消融必须用 `ablation` 档。`smoke` 档的 val bpb 噪声（±0.02）大于效应本身（0.01-0.05）
- 每次只改**一个**变量
- 记录到同一张表里（模板见 `doc/tutorial/README.md` 的「消融总表」）

## 常见坑

**坑 1：uv 装的 torch 找不到 CUDA。**
检查是不是用了 PyPI 的默认 torch 而不是 cu132 版本：
```bash
uv run python -c "import torch; print(torch.__version__, torch.version.cuda)"
```
应该输出类似 `2.14.0+cu132 13.2`。如果 cuda 是 None，说明索引没生效，
删掉 `uv.lock` 和 `.venv` 重跑 `uv sync`。

**坑 2：`uv sync` 报 `Failed to find C compiler`。**
这不是错误，是 torch.compile 探测失败后的**提示**。代码会自动回落到 eager。
想启用编译：`sudo apt install gcc`。

**坑 3：下载数据卡住不动。**
本机 `huggingface.co` 不可达，必须走 `hf-mirror.com`。
检查 `echo $HF_ENDPOINT` 应该有值。`script/_common.sh` 里已经默认设了。

**坑 4：16GB 显存不够。**
降 `--device-batch-size`：`bash script/train_base.sh full --device-batch-size 2`。
但要注意 `total_batch_size` 必须能被 `device_batch_size × sequence_len` 整除，
否则 `resolve_scaling` 会直接 assert（这是故意的，比静默算错好）。

**坑 5：loss 变成 nan。**
看 `src/model/gpt.py` 里的警告日志。最常见是整批 targets 都是 -1。
详见第 00 章的「出错了怎么定位」。

## 延伸

**nanochat 完整版怎么做的**

| 维度 | nanochat | 本项目 | 为什么简化 |
|---|---|---|---|
| 硬件 | 8×H100 80GB | 1×4060Ti 16GB | 现实 |
| 注意力 | Flash Attention 3 | **FA2**（SDPA flash + flex_attention） | Ada 上没有 FA3 |
| 精度 | bf16 + **fp8** | bf16 | fp8 要 Blackwell |
| 分布式 | ZeRO-2（8 卡） | 写但不跑 | 只有 1 张卡 |
| 优化器 | Muon advanced（Polar Express + MuonEq + Muon+ + NorMuon + 谨慎 WD） | 两种都实现，消融档 simple / full 档 advanced | 教学分层 |
| 深度 | d12-d32 | d2-d24 | 显存与时间 |
| 词表 | 32768 | 8192 / 16384 | 小模型的 embedding 不能太大（见第 02 章） |
| 目标 | 超过 GPT-2 的 CORE 分 | **让每个组件可测量** | 完全不同的目标 |

**关于 weight decay 的一处诚实标注**：

谨慎 WD 的**算法**两边完全一致（`(g * p) >= 0` 的 mask，无条件计算）。
但 λ 的**数值**我们没能从 nanochat 抄到 —— 它放在 train 脚本的 CLI 默认值里，
不进 `optim.py`，而那个文件我们拉取时超时了。

所以 `full` 档用的 `λ_ref = 0.1` 是**按量级推测**的：比照 `AdamWConfig`
里 embedding=0.001 / unembedding=0.01，矩阵参数通常比 embedding 大一个量级。
再经 `resolve_scaling` 的 T_epoch 缩放（full 档因子 0.213），峰值是 0.0213。

⚠ **缩放因子强烈依赖档位**，实测差 9.5 倍：

| 档位 | B | D | 缩放因子 | λ=0.05 的峰值 |
|---|---|---|---|---|
| `full` | 2^20 | 2.19B | 0.213 | 0.0107 |
| `ablation` | 65536 | 203M | 2.039 | 0.1020 |

所以 λ **不能跨档位照搬**。要验证这个值，用 `ablation` 档跑 44 分钟对拍
（`--muon-weight-decay 0.05`），别拿 `full` 档的 41 小时去试超参。

**本项目每个简化都是硬件或教学目的导致的，不是「这样更好」。**
`full` 档（d24）已经开满 Muon advanced + 5 个 trick，只差 `--fp8`
（要 Blackwell）和多卡 ZeRO-2。等你的显卡更强（或者你去租 8×H100），
把这两样加上，你就是在跑 nanochat 的 speedrun 了。
