## 概念：三种粒度的切法都不行

把 `"The cat sat on the mat."` 变成整数序列，有三种显然的做法：

**字符级**：每个字符一个 id
```
T=0 h=1 e=2 ' '=3 c=4 a=5 t=6 ...   14 个 token
```
- ✅ 词表极小（~100），嵌入层几乎不占参数
- ❌ 序列极长：同样一段文本，token 数是单词级的 5 倍，
  注意力是 O(T²)，所以计算量是 25 倍。而且模型要「学会」拼单词，
  本该一层解决的事要很多层才学会

**单词级**：每个单词一个 id
```
The=0 cat=1 sat=2 on=3 the=4 mat=5 .=6   7 个 token
```
- ✅ 序列短
- ❌ **词表爆炸**。英语词汇量约 5 万词，加上各种变体、专有名词、数字，
  词表轻易上百万。而每个 id 都要一个嵌入向量。
  词表 100 万 × 维度 1024 = **10 亿参数**，比模型主体还大
- ❌ 没见过的东西就完全没法表示（拼写错误、新词、其他语言）

**子词级（subword）**：在字符和单词之间取折中
```
The=0 cat=1 sat=2 on=3 the=4 mat=5 .=6  ← 都是常见词，整个词一个 token
但 "unbelievable" 会被切成 "un" + "bel" + "iev" + "able"
```
- ✅ 词表可控（8K-128K）
- ✅ 任何字符串都能表示
- ✅ 高频片段整体成 token，压缩率高

**这就是 BPE（Byte Pair Encoding）做的事。**

## 概念：BPE 的核心是「用高频换低频」

BPE 的算法极其简单：

```
1. 把所有文本拆成「字节」序列（256 个基础符号）
2. 重复 N 次：
     找出语料里出现次数最多的相邻符号对 (A, B)
     把所有 (A,B) 合并成新符号 AB
3. 得到 N 个 merge 规则
```

直观理解：**「un」和「believable」总是一起出现，那就把它们焊成一个 token。**

压缩率来自哪里？来看实际数字（本项目 tokenizer 在 8192 词表下的真实输出）：

| 单词 | token 数 | 字符数 | 说明 |
|---|---|---|---|
| `the` | 1 | 3 | 高频，整体成 token |
| ` because` | 1 | 8 | 更高频 |
| ` unbelievable` | 3-4 | 12 | 低频，被切开 |
| ` dro` + `pped` | 2 | 7 | 中频，部分合并 |

**关键观察**：被合并成单 token 的，恰恰是那些**模型需要重点建模的组合**。
「the」「because」这些高频功能词占了大半 token 数但几乎不含信息；
真正需要模型「理解」的低频词被切开了，需要模型自己学怎么拼。

这个取舍是有利的：**模型把容量花在低频词上，而不是浪费在背高频词表上。**

## 概念：词表大小的三角权衡

`V`（词表大小）同时影响三个东西，而且方向不同：

| 影响 | 公式 | `V` 增大 |
|---|---|---|
| 嵌入层参数量 | `2 × V × D`（wte + lm_head） | ↑↑↑ |
| 序列长度 | `tokens ≈ chars / (V 越大压缩越高)` | ↓ |
| 注意力计算量 | `O(T²)` | ↓↓ |

所以 `V` 有个最优点。本项目实测（`scratch/vocab_math.py` 的输出，
`aspect_ratio=64`）：

**看第 4 列**：小模型里嵌入层是参数的大头。同一个 V=32768：

| 模型 | wte+lm_head 参数 | 嵌入占总参数 | 判断 |
|---|---|---|---|
| d4 (D=256) | 16.8 M | **84%** | 荒谬，几乎全是查表 |
| d6 (D=384) | 25.2 M | **70%** | 明显失衡 |
| d12 (D=768) | 50.3 M | 37% | 勉强 |
| d24 (D=1536) | 100.7 M | 12.9% | 健康 |

**模型能力应该花在矩阵上，不是花在查表上。** d4/d6 的绝大部分参数
在做「查一个向量」这种几乎没有计算量的操作，矩阵部分被挤得可怜。

所以本项目：
- `smoke` 档 d4 用 **V=8192**（嵌入仍占 57%，但 smoke 档只是用来验证流程的）
- `full` 档 d6 用 **V=16384**（54%，是本项目能达到的最好平衡）

而 nanochat 的 d24（7.8 亿参数）用 V=32768 只有 12.9% 占比，
非常健康 —— 它完全负担得起更大的词表。

> **一条经验规则**：嵌入层参数量应该 < 总参数的 20%。
> 不满足就说明模型相对于词表太小了，该加大模型或者减小词表。
> 跑 `scratch/vocab_math.py` 可以看到完整的交叉表。

## 概念：本项目的 SPLIT_PATTERN

代码位置：`src/data/tokenizer.py: SPLIT_PATTERN`

```python
SPLIT_PATTERN = (
    r"""'(?i:[sdmt]|ll|ve|re)|[^\r\n\p{L}\p{N}]?+\p{L}+|\p{N}{1,2}"""
    r"""| ?[^\s\p{L}\p{N}]++[\r\n]*|\s*[\r\n]|\s+(?!\S)|\s+"""
)
```

BPE 训练的第一步是「预切分」：先用这个正则把文本切成**块**，
BPE 的合并只能在块内进行，不能跨越块的边界。目的是避免合并出
「半个词 + 半个词」这种无意义的 token。

逐段读：

| 片段 | 匹配什么 | 为什么 |
|---|---|---|
| `'(?i:[sdmt]\|ll\|ve\|re)` | `'s` `'ll` `'ve` 等缩写 | 英文缩写极常见，整体成 token 划算 |
| `[^\r\n\p{L}\p{N}]?+\p{L}+` | 可选的「非字母前缀」+ 一串字母 | 把 `"hello` 里的引号和词粘在一起；`+`（占有量词）表示「尽可能少地重复」，保证非贪婪 |
| `\p{N}{1,2}` | **1 到 2 位**数字 | 见下 |
| ` ?[^\s\p{L}\p{N}]++[\r\n]*` | 可选空格 + 非字母非数字非空白 + 换行 | 标点符号 |
| `\s*[\r\n]` | 换行及其前导空白 | 单独切出来，让模型能学到「换行」的换行 |
| `\s+(?!\S)` | 行尾空白（后面不是非空白） | 行尾换行也归到这里 |
| `\s+` | 其余空白 | 兜底 |

**唯一一个与 GPT-4 不同的地方是 `\p{N}{1,2}`**（GPT-4 用 `{1,3}`）。
nanochat 作者的注释解释得很清楚：

> 我改成 2 是因为不想在数字上「浪费」太多 token，对小词表来说不划算。
> 我验证过 2 是 32K 词表的甜点：1 差一点，3 更差。

数字是很反直觉的一类 token：
- 数字的**种类**几乎是无限的（任意长的整数）
- 但数字的**结构**高度重复（`2026` = `20` + `26`）

所以让数字按 2 位一组切，词表只需要几百个就能覆盖任意数字，
剩下的大量常见数字（`0`-`9999`）会被 BPE 合并成单 token。

```python
    "<|user_end|>",
    "<|assistant_start|>",  # assistant 消息开始
    "<|assistant_end|>",
    "<|python_start|>",  # assistant 调用 python 工具
    "<|python_end|>",
```

### 第 2 块：训练 + 桥接

接在 `SPLIT_PATTERN` 下面：

```python
class BPETokenizer:
    """
    薄薄一层包装：训练用 rustbpe，编码用 tiktoken。

    为什么要两个库？
      rustbpe 训练快（Rust 实现），但没有高效的推理实现；
      tiktoken 推理极快（Rust + SIMD），但**不能训练**。
      训练一次、推理无数次，所以训练用 rustbpe、推理用 tiktoken，
      中间用「mergeable_ranks」这个中间表示搭桥。
    """

    def __init__(self, enc, bos_token: str = "<|bos|>"):
        self.enc = enc
        self.bos_token_id = self.encode_special(bos_token)

    @classmethod
    def train(cls, text_iterator, vocab_size: int):
        """
        从文本流训练 BPE。

        注意 vocab_size 这里**不含**特殊 token：
        特殊 token 在搭桥那一步追加到词表末尾，训练时看不到它们。
        """
        vocab_size_no_special = vocab_size - len(SPECIAL_TOKENS)
        assert vocab_size_no_special >= 256, (
            f"扣掉 {len(SPECIAL_TOKENS)} 个特殊 token 后至少要 256，"
            f"得到 {vocab_size_no_special}")
        log0(f"训练 BPE：目标词表 {vocab_size_no_special}"
             f"（+{len(SPECIAL_TOKENS)} 特殊 token = {vocab_size}）")
        t = rustbpe.Tokenizer()
        t.train_from_iterator(text_iterator, vocab_size_no_special,
                              pattern=SPLIT_PATTERN)

        # ── 桥接：rustbpe 的输出 -> tiktoken 的输入 ──
        pattern = t.get_pattern()                    # 正则，tiktoken 也要用
        mergeable_ranks = {bytes(k): v
                           for k, v in t.get_mergeable_ranks()}
        offset = len(mergeable_ranks)                # 普通 token 占了 [0, offset)
        special_tokens = {name: offset + i          # 特殊 token 接在后面
                          for i, name in enumerate(SPECIAL_TOKENS)}
        log0(f"BPE 训练完成，{offset} 个普通 token"
             f" + {len(SPECIAL_TOKENS)} 个特殊 token")
        enc = tiktoken.Encoding(
            name="gpt_base_bpe",
            pat_str=pattern,
            mergeable_ranks=mergeable_ranks,   # bytes -> 合并优先级 rank
            special_tokens=special_tokens,     # 名称 -> token id
        )
        return cls(enc)
```

### 第 3 块：编码接口

```python
    @lru_cache(maxsize=64)
    def encode_special(self, text: str) -> int:
        """把特殊 token 字符串（如 "<|bos|>"）转成 id。"""
        return self.enc.encode_single_token(text)

    def encode(self, text, prepend=None, append=None, num_threads=8):
        """
        text 可以是 str 或 list[str]（后者走批量编码，快很多）。

        prepend/append 可以是 token id 字符串，也可以是特殊 token 名。
        dataloader 用 prepend="<|bos|>" 给每篇文档加 BOS。
        """
        if prepend is not None and not isinstance(prepend, int):
            prepend = self.encode_special(prepend)
        if append is not None and not isinstance(append, int):
            append = self.encode_special(append)

        if isinstance(text, str):
            ids = [self.enc.encode_ordinary(text)]
        elif isinstance(text, list):
            ids = self.enc.encode_ordinary_batch(text, num_threads=num_threads)
        else:
            raise ValueError(f"不能编码的类型: {type(text)}")

        for row in ids:
            if prepend is not None:
                row.insert(0, prepend)
            if append is not None:
                row.append(append)
        return ids[0] if isinstance(text, str) else ids

    def __call__(self, *a, **kw):
        return self.encode(*a, **kw)

    def decode(self, ids) -> str:
        return self.enc.decode(ids)

    def decode_bytes(self, token_id: int) -> bytes:
        """
        拿到单个 token 对应的原始字节。
        bpb 指标要用它算「每个 token 覆盖几个字节」（第 06 章）。
        """
        return self.enc.decode_single_token_bytes(token_id)
```

```python
def iter_parquet_text(split="train", limit_shards=None):
    """
    惰性遍历 parquet 里的原始文本。

    为什么用生成器？
      4 个 shard 约 10 亿字符，不可能全读进内存。
      BPE 训练器只需要「一个接一个的字符串」，生成器正好满足。

    if limit_shards:
        paths = paths[:limit_shards]
    for path in paths:
        pf = pq.ParquetFile(path)
        for rg_idx in range(pf.num_row_groups):
            rg = pf.read_row_group(rg_idx)
            yield from rg.column("text").to_pylist()
```

### 验证 2：亲手看 BPE 合并的中间过程

新建 `scratch/toy_bpe.py`。**这个实验值得你手写一遍**，因为它让你
彻底搞懂 BPE 在做什么（而不是当成黑盒 API）：

```python
"""
手写一个玩具版 BPE（纯 Python，约 30 行），看合并过程。
这是本章的「手抄代码」的最小可理解版本。
"""
from collections import Counter

def toy_bpe(text: str, num_merges: int = 20) -> list[tuple[str, str]]:
    """
    最朴素的 BPE 实现（为了看清原理，不追求效率）。

    1) 从「字符」开始：每个词是一个字符 list
    2) 反复合并全局最高频的相邻对
    3) 记录每一步合并了什么

    返回：合并历史 [(被合并的符号A, 被合并的符号B), ...]
    """
    # 步骤 1：切成「词」（按空白分），每个词再拆成字符
    words = [list(w) for w in text.split()]
    # 词频表：同一个词只算一次，但带重复次数
    freq = Counter(words)

    history = []
    for _ in range(num_merges):
        # 步骤 2：统计所有相邻对的总频率
        pairs = Counter()
        for word, cnt in freq.items():
            for i in range(len(word) - 1):
                pairs[(word[i], word[i + 1])] += cnt
        if not pairs:
            break
        # 步骤 3：取最高频的对
        best, best_n = pairs.most_common(1)[0]
        if best_n < 2:          # 只出现一次就不值得合并
            break
        history.append((best[0], best[1], best_n))
        # 步骤 4：把所有 (A,B) 替换成新符号 AB
        new_freq = Counter()
        for word, cnt in freq.items():
            merged, i = [], 0
            while i < len(word):
                if i < len(word) - 1 and (word[i], word[i + 1]) == best:
                    merged.append(word[i] + word[i + 1])
                    i += 2
                else:
                    merged.append(word[i])
                    i += 1
            new_freq[tuple(merged)] += cnt
        freq = new_freq
    return history


# ── 实验 1：观察合并的优先顺序 ──
text = """
the quick brown fox jumps over the lazy dog
the fox is quick and the dog is lazy
a quick fox jumps over a lazy dog
"""
print("=== 合并历史（按发生顺序）===")
for i, (a, b, n) in enumerate(toy_bpe(text, 15)):
    print(f"  第 {i+1:2d} 步: 合并 {a!r} + {b!r}   (语料中出现 {n} 次)")

# ── 实验 2：换成「不那么重复」的文本，合并会变慢 ──
print("\n=== 换个文本，合并质量如何变化 ===")
random_text = "zq wv xp kl mn bv tr gh yz cd" * 3
hist = toy_bpe(random_text, 15)
print(f"  只合并了 {len(hist)} 次就停了（因为剩下的对都只出现 1 次）")
for a, b, n in hist[:5]:
    print(f"  合并 {a!r} + {b!r}  (n={n})")
```

跑：

```bash
uv run python scratch/toy_bpe.py
```

**观察重点**：

1. 合并顺序是**严格按频率从高到低**的。频率最高的先合并。
   这意味着「合并表」本质上就是一张按信息量排序的优先级表。

2. 有些合并看起来「很奇怪」（比如 `t`+`h` 而不是 `th`+`e`），
   因为频率高的一定先合。等 `th` 成形后它会参与下一轮竞争。
   **贪心 BPE 没有全局最优性**，但实测效果足够好。

3. 第二个实验里合并很快停住了 —— 因为剩下的相邻对都只出现一次。
   `if best_n < 2: break` 这一句就是「不值得为只出现一次的东西增加词表」。
   这也是为什么**训练 BPE 需要大量语料**：语料太少，学不到有意义的合并。

```python
from common.config import make_run_config, build_model_config, scaling_params

print("词表大小对参数量的影响（aspect_ratio=64）")
print(f"{'depth':>5} {'D':>5} {'V':>6} {'wte+head':>11} {'总参数':>11} {'嵌入占比':>8} {'<20%?':>6}")
print("-" * 60)
for depth in (4, 6, 12, 24):
    for V in (8192, 16384, 32768):
        cfg = build_model_config(depth, 64, 64, sequence_len=1024, vocab_size=V)
        embed = 2 * V * cfg.n_embd          # wte + lm_head（不绑权重时是两份）
        total = embed + 6 * depth * cfg.n_embd ** 2 * 2 / 2 * 2  # 粗略：矩阵部分
        total = embed + scaling_params(cfg) - cfg.n_embd * V  # scaling_params 含 lm_head
        ratio = embed / total
        flag = "OK" if ratio < 0.2 else "偏大"
        print(f"{depth:5d} {cfg.n_embd:5d} {V:6d} {embed:11,} {total:11,} "
              f"{ratio*100:7.1f}% {flag:>6}")
    print()
```

跑：`uv run python scratch/vocab_math.py`

**这张表就是本章的结论**。同一个 V=32768：
- 在 d4 上占 79% 的参数（荒谬）
- 在 d24 上只占 8%（完全合理）

**所以「用多大的词表」不是一个独立决策，它取决于你的模型有多大。**

## ★ 消融实验

本章的消融是「词表大小」，但它不是开关式的，而是要重训 tokenizer + 模型，成本高。
本项目已经给了你答案（`full` 档选 16384 而不是 32768），这里记录结论：

| 配置 | 嵌入占比 | 结论 |
|---|---|---|
| nanochat d24 + V=32768 | 12.9% | 健康，词表越大越好（压缩率更高） |
| 本项目 full 档 d6 + V=16384 | 54.2% | 已经是本项目能达到的最好平衡 |
| 本项目 full 档 d6 + V=32768 | 70.3% | 明显失衡，参数都花在查表上 |

**想自己验证？** 训一个 V=32768 的 tokenizer，然后在 `full` 档下训练：

```bash
rm -rf ~/.cache/gpt_base/tokenizer
uv run python -m training.train_tokenizer --vocab-size 32768 --shards 2
# 然后需要修改 config.py 里 full 档的 vocab_size=32768 再训练
```

预期：**序列更短（省注意力计算）但参数更多**。在 d6 这种小模型上，
净效果通常是**略差**（参数花在了查表上）。这就是 nanochat 敢用 32768
而我们不敢的原因。

## 常见坑

**坑 1：把特殊 token 拿去参与 BPE 训练。**
结果：语料里没有 `<|bos|>` 这种字符串，训练时不会有任何影响，
但 `encode_special` 会失败。特殊 token 必须在训练**之后**追加。
本项目的代码顺序是：rustbpe 训练 → 算 offset → 追加特殊 token。

**坑 2：`vocab_size` 不是 64 的倍数。**
模型里会把词表 padding 到 64 的倍数（`ModelConfig.pad_vocab_size_to`），
因为 DDP 梯度切分和 GEMM tile 都喜欢 64 的倍数。
8192 / 16384 / 32768 天然满足。

**坑 3：把 `token_bytes.pt` 算在训练之前。**
这个文件要记录「最终词表里每个 token 对应多少字节」，
必须在 tokenizer 定下来之后算，而且要用**同一个** tokenizer 对象。
本项目的 `train_tokenizer.py` 里 `compute_token_bytes(tok)` 在 `tok.save()` 之后调用。

**坑 4：数字 token 吃掉词表。**
如果 `\p{N}{1,3}`，词表里会有大量 `000` `001` `123` 这种纯数字 token。
在 8192 词表下这会挤掉真正有用的词。
可以自己试：把 `SPLIT_PATTERN` 里的 `{1,2}` 改成 `{1,3}`，
重训 tokenizer，看 `bytes/token` 变化和分词预览。

## 延伸

**nanochat 完整版怎么做的**

- 词表 32768（`2**15`）
- `SPLIT_PATTERN` 和我们完全一样，包括 `\p{N}{1,2}` 这个改动
- tokenizer 训练用 `python -m nanochat.dataset -n 8` 下载的
  8 个 shard（约 2B 字符）
- 训练完后立刻算 `token_bytes.pt` 并写盘（我们也是）

**唯一的小差别**：nanochat 的 tokenizer 训练是流水线的一环
（`speedrun.sh` 里 tok_train 紧跟着 tok_eval）；我们是独立脚本，
因为我们希望你能单独重训它来做对比。

**本项目多做的**：
- `report_compression()` 会打印分词预览，方便直观判断 tokenize 得好不好
- `tokenizer.visualize()` 能把对话渲染的 token 染色输出，
  第 04 章会用它检查 loss mask
