# 20 · 滑动窗口注意力

卷 3 的最后一章。这个 trick **不改任何数学** —— 它只改「每层看多远」。

而且本章要给你一个本项目实测的、反直觉的结论：

> **在 `full` 档（T=1024）上，滑窗一点速度都省不下来。**
> 实测 1.01×，也就是噪声。

这不是「滑窗没用」，而是「滑窗的收益有前提条件」。
本章要把那个条件量出来。

## 概念：注意力是唯一与 T 线性相关的部分

先算一笔账。`full` 档（24 层 / 768 维 / T=1024）的 FLOPs 分布：

| 部分 | FLOPs/token | 占比 |
|---|---|---|
| 矩阵乘（`6 × matmul_params`） | 1,170,210,816 | **83.8%** |
| 注意力（`QK^T` + `AV`，随 T 线性） | 226,492,416 | **16.2%** |

**矩阵乘占 84%，而且它和序列长度无关。** 无论 T 是 128 还是 8192，
每个 token 要过的矩阵乘都一样多。

只有那 16.2% 的注意力部分和 T 成正比。所以：

> **滑窗的理论天花板就是「把注意力那部分砍掉」。**
> 在 T=1024、`full` 档上，天花板是 16.2%。

而且这个 16.2% 里还要再打折 —— 滑窗层的窗口只有全上下文的 25%。

现在算 `SSSL` 模式：

| 模式 | 注意力 FLOPs | 占总 FLOPs |
|---|---|---|
| `L`（全上下文） | 226,492,416 | 16.2% |
| `SSSL`（18 层滑窗 + 6 层全上下文） | 99,090,432 | 7.8% |

**理论上省了 8.4 个百分点的 FLOPs（总 FLOPs 的 9.1%）。**

如果时间严格等于 FLOPs，这应该是 1.10× 的加速。

**实测是 1.01×。** 差的那 9% 去哪了？这是本章要回答的问题。

## 概念：`window_pattern` 怎么展开

```python
def window_sizes(self) -> list[tuple[int, int]]:
    """
    把 window_pattern 字符串展开成「每一层的窗口大小」。

    "L"  = 全上下文      -> (sequence_len, 0)
    "S"  = 四分之一上下文 -> (ceil(sequence_len/4 对齐到 128), 0)

    最后一层强制 L：最靠近输出的层需要看全局。
    """
    pattern = self.window_pattern.upper()
    assert all(c in "SL" for c in pattern), f"非法 window_pattern: {self.window_pattern}"
    long_w = self.sequence_len
    short_w = -(-long_w // 4 // 128) * 128  # 向上取整到 128 的倍数
    table = {"L": (long_w, 0), "S": (short_w, 0)}
    sizes = [table[pattern[i % len(pattern)]] for i in range(self.n_layer)]
    sizes[-1] = (long_w, 0)
    return sizes
```

四个设计点：

**① 字符串平铺，不是「前 N 层滑窗」**

```python
sizes = [table[pattern[i % len(pattern)]] for i in range(self.n_layer)]
```

`pattern[i % len(pattern)]` 是**取模平铺**。所以
`window_pattern="SS"` 在 6 层上是 `S S S S S S`（6 层全滑窗），
在 5 层上是 `S S S S S`（5 层全滑窗），
在 6 层上而 pattern 是 `"SSL"` 才是 `S S L S S L`。

**这意味着你不能靠「模式字符串的长度」控制滑窗层数** ——
层数是 `n_layer` 决定的，字符串只决定**比例**。

**② 短窗是 `sequence_len / 4`**

不是 nanochat 那个「1/4 但对齐到 FA3 的 tile size」。
本项目 `sequence_len=1024`，所以：

```
short_w = ceil(1024/4/128)*128 = ceil(256/128)*128 = 256
```

**正好 256，占全上下文的 25.0%。**

**③ 向上取整到 128 —— 这是性能原因**

```python
short_w = -(-long_w // 4 // 128) * 128
```

两个 `-` 和一个 `//` 叠起来是向上取整的惯用法：
`-(-a // b) == ceil(a / b)`。

**为什么必须是 128？** 因为 `flex_attention` 把序列切成
`128 × 128` 的块，`block_mask` 是**块级**的摘要。
如果窗口边界不落在块的整数倍上，就得做「部分块」处理 ——
要么退化到更慢的路径，要么 mask 失效。

这就是第 11 章说「flex_attention 把 mask 编译成块级 block_mask
（只存 128×128 的块摘要）」的直接后果。

> ⚠ 如果 `sequence_len` 很小（比如 256），那
> `ceil(256/4/128)*128 = 64` —— **小于块尺寸**。
> 这时一个块里装不下整个窗口，flex 的效率会下降。
> 本项目最小档 `debug` 的 `sequence_len=32`，
> `short_w = ceil(8/128)*128 = 128` —— **比 sequence_len 还大**，
> 等于「全上下文」。这也是为什么小档位上滑窗天然测不出差别。

**④ 最后一层强制 L**

```python
sizes[-1] = (long_w, 0)
```

和第 18 章的 `has_value_embed` 同一个思路：**最靠近输出的
那一层必须看全局**。它在写代码时**无条件覆盖**你写的 pattern ——
`window_pattern="S"`（想全滑窗）也拦不住最后一层。

### 三种 pattern 的展开（`full` 档 24 层）

```
  L     -> [(1024,0) × 24]                      全上下文层 24 / 滑窗层 0
  SSL   -> [(256,0), (256,0), (1024,0)] × 8      全上下文层  8 / 滑窗层 16
  SSSL  -> [(256,0), (256,0), (256,0), (1024,0)] ×6  全上下文层 6 / 滑窗层 18
```

注意 `SSL` 和 `SSSL` 差别很小（16 vs 18 个滑窗层），
但 `L` 和它们差别巨大（0 vs 16/18）。

**所以 `window_pattern` 实际上是个「全上下文 vs 混合」的二元选择** ——
`SSL` 和 `SSSL` 之间的差别是二阶的。

## 概念：滑窗的实现（两条路径）

第 11 章详细讲过，这里只回顾决策点：

```python
def attend(q, k, v, window, attn_impl="flex"):
    left = window[0]
    T = q.size(1)
    if left is None or left <= 0 or left >= T:
        # 全上下文：永远走 SDPA 的 is_causal=True（这条路径 FA2 可选）
        return sdpa_bt(q, k, v, causal=True, gqa=(q.size(2) != k.size(2)))
    # 滑窗：两条路径
    if attn_impl == "sdpa":
        return attend_sliding_sdpa(q, k, v, left)
    return attend_sliding_flex(q, k, v, left)
```

| 路径 | 实现 | 实测（4×12×1024×64, 滑窗 256） |
|---|---|---|
| 全上下文 | `SDPA(is_causal=True)` | 0.207 ms |
| 滑窗 + `flex` | `block_mask` 编译成 FA2 风格 kernel | 0.128 ms |
| 滑窗 + 显式 mask | `SDPA(mem_efficient)` + `(T,T)` bool mask | 0.516 ms |

**`full` 档默认 `window_pattern="L"`** —— 实测四档全部如此：

| 档位 | `sequence_len` | `short_w` | 默认 pattern | 滑窗层数 |
|---|---|---|---|---|
| `debug` | 128 | 128 | `L` | 0 |
| `smoke` | 512 | 128 | `L` | 0 |
| `ablation` | 1024 | 256 | `L` | 0 |
| `full` | 1024 | 256 | `L` | 0 |

**所以本项目默认根本不走滑窗路径。** 本章的滑窗内容全部是
「如果你要开它，会发生什么」。

> ⚠ 顺带修掉一处过时注释：`config.py` 里 `window_pattern` 那行
> 原本写着「（滑窗需要 FA3）」。**本项目没有 FA3** ——
> 滑窗走的是 `flex_attention` 的 `block_mask` 或 SDPA 的显式 mask
> （第 11 章）。那句话是从 nanochat 抄来时没改的。已修正。
> 这和第 13 章的 `activation` 漏 `gelu_tanh` 是同一类问题：
> **照抄上游注释而没核对本项目的实际实现。**

### 注意 `debug` 档的短窗（128）= `sequence_len`（128）

`short_w = ceil(128/4/128)*128 = 128`，**等于全上下文**。
所以即使 `debug` 档设 `window_pattern="S"`，也不会真的滑窗 ——
而且 `attend` 里的 `left >= T` 分支会直接把它路由到全上下文路径。

**这是「小档位天然测不出滑窗差异」的第二个原因**
（第一个是层数太少）。

## 概念：★ 实测 —— 滑窗的收益从哪里开始出现

这是本章的核心实验。**先看 kernel 层面**（排除其他因素）：

```python
import sys, time, torch
sys.path.insert(0, "src")
from model.layers import attend_sliding_flex

print(f"{'T':>6} {'全上下文 ms':>12} {'滑窗 flex ms':>13} {'加速':>8}")
print("-" * 46)
for T in (256, 512, 1024, 2048, 4096, 8192):
    q = torch.randn(4, T, 12, 64, device="cuda", dtype=torch.bfloat16)
    k = torch.randn_like(q); v = torch.randn_like(q)

    def bench(fn, n=20):
        for _ in range(5):
            fn()
        torch.cuda.synchronize()
        t0 = time.time()
        for _ in range(n):
            fn()
        torch.cuda.synchronize()
        return (time.time() - t0) / n * 1000

    full = bench(lambda: torch.nn.functional.scaled_dot_product_attention(
        q.transpose(1, 2), k.transpose(1, 2), v.transpose(1, 2), is_causal=True))
    sw = bench(lambda: attend_sliding_flex(q, k, v, 256))
    print(f"{T:>6} {full:>12.3f} {sw:>13.3f} {full / sw:>7.2f}x")
```

**实测**：

```
     T   全上下文 ms   滑窗 flex ms     加速
----------------------------------------------
   256         0.030         0.134     0.22x
   512         0.068         0.135     0.51x
  1024         0.221         0.128     1.73x
  2048         0.740         0.278     2.66x
  4096         2.714         0.507     5.36x
  8192         9.800         0.942    10.40x
```

**这张表的信息量很大，有三个转折点：**

**转折点 1：T ≤ 512 时滑窗更慢（0.22x ~ 0.51x）**

因为滑窗的绝对耗时**几乎是常数**（0.134 / 0.135 / 0.128 ms）
—— 无论 T 是 256 还是 1024。而全上下文的耗时随 T 快速上升。

**常数 0.13ms 就是 `flex_attention` 的固定开销**：
`create_block_mask` + 编译调度 + kernel 启动
（第 11 章说的「block_mask 的 lru_cache 帮了大忙，
但第一次仍要建块摘要」）。

在 T=256 时，全上下文只要 0.030ms —— **比那个固定开销还少 4 倍**。

**转折点 2：T=1024 是盈亏平衡点（1.73x）**

`full` 档的 `sequence_len` **正好在这里**。这是本项目选
`T=1024` 的一个意外后果 —— 恰好在 kernel 层面刚开始赚。

**转折点 3：T≥2048 后收益爆发（2.66x → 10.40x）**

因为滑窗耗时也随 T 增长了（窗口是绝对宽度 256，
但被查询的位置数随 T 增加），而全上下文是 T²。
**T=8192 时 10.4 倍加速**。

### 那为什么端到端测出来只有 1.01×？

```python
# full 档，batch=8，24 层，端到端 fwd+bwd
print(f"{'pattern':<8} {'滑窗层':>6} {'每步 ms':>10} {'GPU 峰值 GiB':>13}")
```

**实测**：

```
pattern     滑窗层      每步 ms    GPU 峰值 GiB
------------------------------------------
L             0      750.4         13.66   (1.00x)
SSSL         18      741.7         13.66   (1.01x)
```

**三层原因叠加**：

**① 注意力只占 16.2% 的 FLOPs。**
就算注意力免费了，端到端也只能快 1/0.838 = 1.19×。
这是**结构性上限**。

**② 实际只省了其中的一部分。**
`SSSL` 把注意力 FLOPs 降到 43.7%（227M → 99M），
即总 FLOPs 的 9.1%。

**③ flex 的固定开销吃掉了 9.1%。**
每个滑窗层都要跑一次 `attend_sliding_flex`（0.128ms），
而全上下文只要 0.207ms —— **单层确实省了 0.079ms**，
但 24 层 × 8 batch × (fwd+bwd 三次) 的调用次数极多，
每次的固定开销累加起来就把收益吃光了。

> **注意「GPU 峰值 13.66 GiB 两者完全相同」。**
> 滑窗**不省显存** —— 因为峰值由优化器状态（AdamW/Muon 的
> momentum 缓冲）和激活值决定，不是由 `(T,T)` 注意力矩阵
> 决定。后者在本项目的规模下根本不是峰值。
> 第 11 章说「显式 mask 要物化 (T,T) bool mask，T=1024 时每层每步 1MB」
> —— 24 层 × 8 batch × 3 次 = 576 MB，这才是显式 mask 路径的额外开销，
> 而 `flex` 路径**不物化**，所以两者峰值相同。

## 手抄代码

### 第 1 块：`window_sizes`

```python
def window_sizes(self) -> list[tuple[int, int]]:
    pattern = self.window_pattern.upper()
    assert all(c in "SL" for c in pattern), f"非法 window_pattern: {self.window_pattern}"
    long_w = self.sequence_len
    short_w = -(-long_w // 4 // 128) * 128  # 向上取整到 128 的倍数
    table = {"L": (long_w, 0), "S": (short_w, 0)}
    sizes = [table[pattern[i % len(pattern)]] for i in range(self.n_layer)]
    sizes[-1] = (long_w, 0)
    return sizes
```

**三处容易写错**：

1. **`sizes[-1] = (long_w, 0)` 不能漏。** 漏了的话
   `window_pattern="S"` 会让最后一层也滑窗 —— 而第 18 章说过
   最后一层是最要紧的（它决定输出）。
2. **`-(-a // b)` 是向上取整。** 写成 `a // 4 // 128 * 128` 是
   **向下取整** —— `1024//4//128*128 = 256` 碰巧一样，
   但 `sequence_len=1000` 时：`ceil(250/128)*128 = 384` vs
   `250//128*128 = 128`。差了 3 倍。
3. **返回的是 `tuple` 而不是 `int`。** 因为接口要表达
   `(left, right)`，虽然右窗口永远是 0（因果）。

### 第 2 块：`attend` 的路由

```python
def attend(q, k, v, window, attn_impl="flex"):
    left = window[0]
    T = q.size(1)
    if left is None or left <= 0 or left >= T:
        return sdpa_bt(q, k, v, causal=True, gqa=(q.size(2) != k.size(2)))
    ...
```

**⚠ `left >= T` 这个分支是本项目特有的一个优化。**

nanochat 用 `-1` 表示全上下文。本项目直接用 `sequence_len`，
所以当 `left >= T` 时（`T` 小于配置的长度，比如推理时的短序列）
自动退化成全上下文。

这个分支很重要：**它意味着小 T 的推理根本不走滑窗路径**，
避免了上面那个「T≤512 反而更慢」的陷阱。实测那三行
（0.22x / 0.51x）之所以是「浪费」，就是因为测试脚本直接调了
`attend_sliding_flex` 而没走 `attend` 的路由。

### 第 3 块：两条滑窗路径并存

见第 11 章。本章只强调**它们为什么都要保留**：

`attend_sliding_sdpa` 是**对照组**。第 11 章那章量出的
「flex vs mem-efficient 差 4.42×」需要一条慢路径做参照。
把慢路径删掉，第 11 章就失去教学对象了。

**教程项目保留「明知更慢的路径」的理由不是性能，是可测量性。**


**预期（这个消融的结论和直觉相反）**：

- **`full_SSSL` 的 bpb 会明显更差。** 因为 18/24 层只能看
  最近 256 个 token，而 `full` 档的序列长度是 1024 ——
  **四分之三的上下文被模型物理上看不到了。**
- 而速度只快 1%（实测）。

**所以在 `T=1024` 上，滑窗是「纯亏」：质量掉，速度不涨。**

### 那滑窗什么时候划算？

把它当一个**交换率**来算。用实测数据：

| 序列长度 | 注意力 kernel 加速 | 端到端预期加速 | 质量损失 |
|---|---|---|---|
| 1024（`full` 档） | 1.73× | **1.01×** | 严重（窗口 256 = 全局的 25%） |
| 4096 | 5.36× | ~1.2× | 取决于任务 |
| 32768+ | ~20×+ | ~1.5× | 长程检索任务上更明显 |

**盈亏平衡的经验规则**：

```
滑窗划算，当且仅当  T ≳ 4 × (矩阵 FLOPs 占比的倒数) × 短窗长度
本项目: T ≳ 4 × 5.2 × 256 ≈ 5300
```

对长上下文任务（长程检索、文档理解），质量损失可以接受，
那时滑窗的 1.2~1.5× 是实打实的。**本项目的 `full` 档不属于那一类。**

### 更值得做的消融：调 `sequence_len` 而不是调 pattern

如果目标是「用滑窗省算力」，先问「能不能不做那个省算力的需求」。

```bash
# T=2048，比 T=1024 多一倍 token，但注意力 FLOPs 是 4 倍
bash script/train_base.sh full --no-resume --model-tag full_T2048 --seq-len 2048
```

⚠ 但这会让 batch 装不下（显存），得同时降
`device_batch_size` + 升 `grad_accum` —— 那就抵消了。

**这就是第 02 章那个「嵌入占比」分析的现实版本：
所有「省算力」的选项都在和其他预算抢空间。**

## 常见坑

### 坑 1：以为滑窗总是更快

**实测 `full` 档 1.01×。** 而且 `T ≤ 512` 时 kernel 层面
**慢 2~4 倍**。滑窗有 0.13ms 的固定开销。

**只在 `T` 足够大时才用滑窗。** 本项目 `attend` 里的
`left >= T` 分支就是自动避开这个陷阱。

### 坑 2：忘了「最后一层强制 L」

见上面。`window_pattern="S"` **不会**让最后一层滑窗。

这不是 bug，是设计（第 18 章解释过原因）。但如果你的消融
假设「`S` = 全滑窗」，你会得到一个假结论。

### 坑 3：向上取整写成向下取整

见上面。`sequence_len=1000` 时差 3 倍。

### 坑 4：以为滑窗省显存

**实测两者峰值完全相同（13.66 GiB）。**

显存峰值由优化器状态和激活值决定。`flex` 路径不物化 `(T,T)`，
所以滑窗和全上下文的激活值一样多。

**只有用显式 mask 的 SDPA 路径**才会多占
（`T=1024` 时每层每步 1MB，24 层 × 8 batch × 3 次 ≈ 576 MB）。

### 坑 5：以为滑窗不改变 bpb

**滑窗显著改变 bpb。** 它让 18/24 层的模型物理上看不到
75% 的上下文。这不是实现细节，是**架构改变**。

第 11 章说过滑窗路径和全上下文路径**数值等价** ——
那是指「两条滑窗 kernel 互相等价」，不是「滑窗 ≡ 全上下文」。

## 延伸

**Gemma-2 的 5:1 交替**

Gemma-2 用 5 个 local（窗口 4096）+ 1 个 global（窗口 8192）。
本项目的 `window_pattern` 能表达类似模式（`"SSSSS"` 平铺），
但**只能表达「全上下文」和「1/4 上下文」两种窗口** ——
不能指定任意窗口宽度。

要支持更多宽度，得改 `window_sizes` 的 `table`：

```python
table = {"L": (long_w, 0), "M": (long_w // 2, 0), "S": (short_w, 0)}
```

**为什么 nanochat 也只给两档**：因为滑窗的收益高度依赖
「短窗 vs 长窗」的比值，而只有「1/4」这个比值被实测过。
加一档 `M` 是零成本但也零依据的。

**Mistral 的 SWA 和滑动窗口的滑窗不是一回事**

两者常被混淆：
- **本项目 / Gemma-2**：不同**层**有不同的窗口（layer-wise）
- **Mistral**：所有层同一个窗口，但**跨层传递状态** ——
  每个块的输出喂给下一个块的输入**再过一个窗口**，
  有效感受野因此远超窗口本身

Mistral 那个更强也更复杂，本项目没实现。

**滑窗 + KV cache 的组合问题**

滑窗有个工程优势：**KV cache 可以只存窗口内的 token**。
本项目没做 —— `kv_bytes_per_token()` 算的是全量：

```python
def kv_bytes_per_token(self) -> int:
    return (self.config.n_layer * 2 * self.config.n_kv_head
            * self.config.head_dim * COMPUTE_DTYPE.itemsize)
```

nanochat 有 `kv_read_bytes(context_len)` 能算出「实际读取量」
（滑窗层只读最近 window 个）。如果本项目要加那个方法，
**这里的公式要改成按层区分**：

```
总读取 = Σ_layer 2 · n_kv_head · head_dim · 2 · min(context_len, window[layer])
```

**这是「滑窗在推理侧的真实收益」** —— 而本项目是训练项目，
所以那部分收益（约 2× 的 decode 带宽）拿不到。

## 卷 3 完成

5 个 trick 全部讲完。回看一下它们在残差流上的位置：

```
x = rms_norm(wte(idx))
     │
     ├─ ★ smear（第 19 章）        x[i] += λ·gate·x[i-1]
     │
     ├─ x0 = x   ← 快照
     │
     ├─ 第 0 层
     │    resid[0]·x + x0[0]·x0        ← resid / x0（第 17 章）
     │    Block 0（ve? 否）             ← 第 18 / 14 章
     ├─ 第 1 层
     │    resid[1]·x + x0[1]·x0
     │    Block 1（ve? 是 → 门控混进 v）  ← 第 18 章
     │    ★ x_backout = x（若 n_layer//2 == 1）
     ├─ ...
     ├─ 第 23 层
     │    resid[23]·x + x0[23]·x0
     │    Block 23（ve? 是）
     │
     ├─ ★ backout：x -= 0.2·x_backout    ← 第 19 章（唯一做减法）
     │
     └─ rms_norm → lm_head → softcap     ← 第 15 章
```

**四个加，一个减，一套缩放。** 这就是 nanochat 的全部 trick ——
加起来占 `full` 档 43.64% 的参数（几乎全是 value embeds）
和 0.00002% 的参数（其余四个加起来 74 个）。
