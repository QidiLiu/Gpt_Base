## 概念：两条分界线

`setup_optimizer` 里两类分组用了**完全不同的判据**：

```python
# Muon 组：按**形状**（因为要 stack）
for shape in sorted({p.shape for p in matrix_params}):
    param_groups.append(dict(
        kind="muon", params=[p for p in matrix_params if p.shape == shape],
        lr=mc.lr * batch_lr_scale, momentum=mc.momentum, ns_steps=mc.ns_steps, ...))

# AdamW 组：按**角色**（wte / ve / lm_head / scalar）
```

**为什么 Muon 按形状**：第 22 章讲过 —— 同一组的参数要
`torch.stack` 成 `(K, m, n)` 才能一次算 K 个矩阵，
**形状必须相同**。而矩阵参数有 5 种形状
（`(768,768)` / `(768,3072)` / `(3072,768)` / `(12,12)` / `(1,24)`），
所以分成 5 组。

**为什么 AdamW 按角色**：第 21 章讲过 —— `wte` 和 `lm_head`
的 lr 差 37.5 倍，**它们的形状反而一样**（都是 `(V,D)` 或 `(D,V)`）。
按形状分组会把它们混在一起。

**这是一个很好的对照**：

| 优化器 | 分组判据 | 因为 |
|---|---|---|
| Muon | **形状** | 要 stack，必须同形 |
| AdamW | **角色** | 每个角色的 lr/wd 不同 |

## 概念：★ 本项目的分界线划错了一处

```python
matrix_params, adam_groups = [], {}
for name, p in model.named_parameters():
    if not p.requires_grad:
        continue
    if p.ndim == 2 and "wte" not in name and "value_embeds" not in name \
            and name != "lm_head.weight":
        matrix_params.append(p)
    elif name.startswith("transformer.wte"):
        adam_groups.setdefault("wte", []).append(p)
    elif name.startswith("value_embeds"):
        adam_groups.setdefault("ve", []).append(p)
    elif name == "lm_head.weight":
        adam_groups.setdefault("lm_head", []).append(p)
    else:
        adam_groups.setdefault("scalar", []).append(p)

accounted = len(matrix_params) + sum(len(v) for v in adam_groups.values())
assert accounted == sum(1 for _ in model.parameters()), (
    f"参数分组不完整：分到 {accounted} 个，模型有 "
    f"{sum(1 for _ in model.parameters())} 个")
```

**规则是「`ndim == 2` 且不是嵌入」**。而 `ndim == 2` 会捞进
两个不该在 Muon 的东西：

实测（`ablation` 档全开 trick，Muon 组 40 个张量 / 5 种形状）：

```
Muon 组里形状不是「矩阵」的东西：
  smear_gate.weight                            (1, 24)
  transformer.h.1.attn.ve_gate.weight          (6, 12)
```

### `(1, 24)` 是什么

第 19 章讲过：`smear_gate = Linear(24, 1)`。
它的权重是 `(out_features, in_features) = (1, 24)`。

**这是一个 rank-1 矩阵**（`min(1, 24) = 1`，只有一个奇异值）。
「正交化」它没有任何意义 —— 唯一效果是把那个向量缩放到单位长度。

### nanochat 怎么做的

```python
matrix_params = list(self.transformer.h.parameters())
```

**按名字取** —— `smear_gate` 挂在 `self` 上，不在 `transformer.h` 里，
所以自动留在 AdamW 那边（`smear_params` 组）。

**教训**：`ndim == 2` 是一个**便利但不可靠**的代理。
真正的问题是「这个参数参与大规模矩阵乘吗」，
按名字取比按形状取更准。

### 一个容易被忽略的连锁反应

`setup_optimizer` 的分组规则决定了
**Muon 组里有几个张量，进而决定了 `param_breakdown` 和日志**。

`(1,24)` 的 `smear_gate` 在 Muon 组里意味着：

- 它的梯度会被 `orthogonalize_advanced` 处理
- 而 `smear_lambda` 初始为 0 → 梯度精确为 0 →
  正交化输出 0 → 参数不动（实测无 NaN）
- **后果**：只要 `λ` 一直是 0，`smear_gate` 的 24 个参数就永远不动

而 nanochat 的版本里它在 AdamW 组，AdamW 处理零梯度也没问题。

**两者都不动，但路径不同。** 这个偏差的实际影响很小
（24 个参数），但它是「分界线划错」的证据。

## 概念：muP 的宽度缩放

```python
dmodel_lr_scale = (d / optim_cfg.dmodel_lr_ref) ** -0.5
```

`dmodel_lr_ref = 768`。四档实测：

| 档位 | `n_embd` | `(D/768)^-0.5` | `wte` 有效 lr |
|---|---|---|---|
| `debug` | 32 | **4.8990** | 1.470 |
| `smoke` | 128 | 2.4495 | 0.735 |
| `ablation` | 384 | 1.4142 | 0.424 |
| `full` | 768 | **1.0000** | 0.300 |

**为什么是 `-0.5`**：

宽度变大时，每个参数的「分摊职责」变小 —— 参数多了，
每个只需要负责一小块。所以 LR 要**调小**，
否则有效步长会随宽度放大。

`√` 的来源（muP，*Tensor Programs V*，Yang & Hu 2022）：
在 `D` 维空间里，最优的单参数步长应该 ∝ `1/√D`。
**这是「超参可迁移」的核心** —— 用一个 768 维模型调出来的
`lr=0.3`，在任意宽度下都能直接用。

> ⚠ 严格说 muP 给的是 `(D/D_ref)^-1/α`，`α` 取决于
> 「per-parameter 还是 per-output」。`α=0.5` 对应某些约定，
> `α=1` 对应另一些。nanochat 用的是 `-0.5`，
> **本项目照抄**。这个选择的细节我没有核对 muP 论文原文，
> 标为**未验证**。

### 注意 `full` 档是 1.0

`D = 768 = dmodel_lr_ref`，所以缩放因子恰好是 1。
**所有超参的「调参基准」就是 `full` 档。**

其他三档的超参是**从 full 档缩放来的**，不是独立调的。
这是 muP 的实用价值 —— **调一次，所有宽度通用**。

### `debug` 档的 lr 是 1.47

`4.899 × 0.3 = 1.47`。**参数一步就被推 1.47**，
如果 `wte` 的元素量级是 `~1`，这一步就能把它翻倍。

`debug` 档只跑几步做冒烟测试，所以无所谓。
但如果有人拿 `debug` 档跑稍微长一点的训练，
**这个 lr 会让它发散**。

## 概念：Muon 的形状补偿（与论文不一致）

`MuonAdamW.step` 的 Muon 分支里：

```python
# 形状修正：高矩阵（m>n）乘 √(m/n)。
# 原因：正交化后每个元素量级是 1/√n，高矩阵列数少，
# 不补偿的话每步实际位移偏小，等效于更小的学习率。
m, n = params[0].shape[-2], params[0].shape[-1]
self._hp.set(
    lr=group["lr"] * max(1.0, m / n) ** 0.5,
    ...)
```

而 Muon+ 论文（2602.21545）引用的原始公式（Bernstein 2025 建议）是：

```
W ← W - η · √(m/n) · O
```

**区别在 `max(1.0, ...)`**：

| 矩阵形状 | `m/n` | 论文 `√(m/n)` | 本项目 `√(max(1,m/n))` |
|---|---|---|---|
| `(768, 768)` 方阵 | 1.000 | 1.0000 | 1.0000 |
| **`(768, 3072)` 宽** | 0.250 | **0.5000** | **1.0000** |
| `(3072, 768)` 高 | 4.000 | 2.0000 | 2.0000 |
| `(1, 24)` | 0.042 | 0.2041 | 1.0000 |
| `(12, 12)` | 1.000 | 1.0000 | 1.0000 |

**`full` 档的 5 个 Muon 分组**：

```
       形状    个数    论文 sqrt(m/n)       项目    例
    (1, 24)     1          0.2041   1.0000  smear_gate.weight
    (12, 12)    12          1.0000   1.0000  transformer.h.1.attn.ve_gate.weight
   (768, 768)   96          1.0000   1.0000  transformer.h.0.attn.c_q.weight
   (768, 3072)  24          0.5000   1.0000  transformer.h.0.mlp.c_proj.weight
  (3072, 768)   24          2.0000   2.0000  transformer.h.0.mlp.c_fc.weight
```

**唯一不一致的是宽矩阵 `(768, 3072)`** ——
本项目给 1.0（不修正），论文给 0.5。

**24 个 MLP 降维投影的 lr 因此是论文值的 2 倍。**

`max(1.0, ...)` 的效果是：**只放大高矩阵，从不缩小宽矩阵。**
这是一个**不对称的修正**。

> 我倾向认为 `max(1.0, ...)` 是**有意的**：修正的目的是
> 「补偿高矩阵因为列数少而步长偏小」，
> 而宽矩阵（`m<n`，如 `c_fc` 的反向）步长偏大**不是问题**
> （高维空间的每元素步长本来就该小）。
> 但这与论文的 `√(m/n)` 不一致，且**本项目未验证哪种更好**。
> 标为**已知偏差，未定论**。

## 手抄代码

分组的核心：

```python
matrix_params, adam_groups = [], {}
for name, p in model.named_parameters():
    if not p.requires_grad:
        continue
    if p.ndim == 2 and "wte" not in name and "value_embeds" not in name \
            and name != "lm_head.weight":
        matrix_params.append(p)
    elif name.startswith("transformer.wte"):
        adam_groups.setdefault("wte", []).append(p)
    elif name.startswith("value_embeds"):
        adam_groups.setdefault("ve", []).append(p)
    elif name == "lm_head.weight":
        adam_groups.setdefault("lm_head", []).append(p)
    else:
        adam_groups.setdefault("scalar", []).append(p)

accounted = len(matrix_params) + sum(len(v) for v in adam_groups.values())
assert accounted == sum(1 for _ in model.parameters()), (
    f"参数分组不完整：分到 {accounted} 个，模型有 "
    f"{sum(1 for _ in model.parameters())} 个")
```

**四条判据的顺序不能换**：

```python
"wte" not in name and "value_embeds" not in name and name != "lm_head.weight"
```

这三个排除条件的顺序无关（是 `and`），但**它们必须在最前面**。
如果 `elif name.startswith("transformer.wte")` 排在前面，
`wte` 就会被重复收集。

### ⚠ `assert accounted == ...` 是最重要的一行

**这是「新增参数被漏掉」的唯一防线。**

新增一个参数（比如某个新 trick）而忘了加进分组规则，
它会落到 `else` 分支的 `scalar` 组 ——
**assert 不会报警**，因为它确实被分组了（只是分错组）。

所以这条 assert 只能抓「**完全没被分组**」的情况，
抓不到「**分错组**」。

**第 22 章说的 `smear_gate` 落进 Muon 就是「分错组」——
assert 完全无感。**

> 顺带说：`value_embeds` 现在有两种形态（`ModuleDict` 和
> 裸 `nn.Embedding`，第 18 章的 `--shared-value-embeds`）。
> 两种形态的参数名都以 `value_embeds` 开头
> （`value_embeds.5.weight` 和 `value_embeds.weight`），
> 所以 `name.startswith("value_embeds")` 两条路径都对。
> **这是那个开关没写错分组的原因** —— 但值得确认。

### 消融 1：`dmodel_lr_scale` 的指数

```python
# 改 optim_cfg.dmodel_lr_ref 的用法，或者直接改成 (d/768)**-1.0
```

**预期**：`D=32`（`debug`）时 `-0.5` 给 4.90，`-1.0` 给 24。
小模型上 24 倍的 lr 几乎肯定发散。

**但在 `full` 档上两者都是 1.0**（`D = D_ref`）——
所以这个消融**只能在 `ablation` 档做**
（`D=384`，`-0.5` 给 1.414，`-1.0` 给 2.0，差 1.4 倍）。

⚠ 差 1.4 倍的效应可能很小。要看清需要更宽的对比，
而更宽的模型本项目跑不动。

> ★ 参照：实测 σ_Δ = 0.000190、阈值 0.001（见消融总表），
> 所以「测不出」的理由不再是噪声，而是**你只能跑一个宽度**。

### 消融 2：标量组的超参（第 17 章的雷）

```python
# 把 scalar 拆成 3 组，lr 各不相同
# resid_lambdas: lr=0.005, betas=(0.8,0.95), wd=0.05
# x0_lambdas:    lr=0.5,   betas=(0.96,0.95), wd=0.0
# smear/backout: lr=0.2,   betas=(0.8,0.95), wd=0.0
```

**预期**：`resid_lambdas` 的 lr 从 0.5 降到 0.005（100 倍）
会显著改变训练。

**这是第 17 章那个「100 倍 lr」的具体代价。**
而 nanochat 选 0.005 的理由是「resid 直接乘整条总线，
尺度失控风险最高」。

⚠ 本项目**未跑过**这个消融。而 `full` 档一次 41 小时。

## 常见坑

### 坑 1：`ndim == 2` ≠ 「是矩阵」

见上面。`(1, 24)` 是反例。

### 坑 2：assert 抓不到「分错组」

见上面。它只抓「完全没分组」。

### 坑 3：以为 `full` 档的缩放因子不是 1

`D = 768 = dmodel_lr_ref`，**恰好是 1.0**。
如果你改了 `n_embd`，它就不再是 1 了 ——
`full` 档如果改成 `aspect_ratio=32`（第 02 章的讨论），
`D = 24 × 32 = 768`... 恰好还是 768。

> 有意思：`full` 档的 `aspect_ratio` 从 64 改成 32 的原因
> （第 00 批的档位重构）就是为了让 `D = 768`——
> 所以 `dmodel_lr_scale = 1.0` 是**设计出来的**，不是巧合。

### 坑 4：忘记形状补偿只对 Muon 生效

```python
self._hp.set(lr=group["lr"] * max(1.0, m / n) ** 0.5, ...)
```

这一行在 `MuonAdamW.step()` 的 `kind == "muon"` 分支里。
AdamW 分支没有形状补偿 —— **因为 AdamW 是逐元素归一化的**，
形状不影响每个元素的步长（第 21 章验证 1 实测：梯度差 10⁶ 倍
更新量一样）。

**Muon 需要补偿是因为正交化后的元素量级依赖形状**：
`Ortho` 的输出元素量级约 `1/√min(m,n)`。

### 坑 5：以为 lr 的「调参基准」是 `ablation` 档

是 `full` 档（`D = 768 = dmodel_lr_ref`，缩放 = 1.0）。

`ablation` 档的超参是**缩放来的**，不是独立调的。
所以「ablation 档上某个超参效果好」不能直接推到 full。

## 延伸

**muP（maximal update parameterization）**

Yang & Hu 2022 的 *Tensor Programs V*。核心是给出一套
「超参可跨宽度迁移」的约定：

| 量 | muP 的约定 |
|---|---|
| LR | ∝ `D^-1/α`（本项目取 `α=2`，即 `D^-0.5`） |
| 初始化 | `std ∝ D^-1/2`（第 23 章的 `s = √3·D^-0.5` 就是它） |
| 输出层 | 有特殊约定 |

muP 让「在 128 维调的超参直接用在 4096 维」成为可能。
**这正是本项目四个档位共用一套超参的依据。**

**Nemotron / YaRN 等「超参迁移」的变体**

实践中有时候发现 muP 的某个约定在特定架构上需要调整
（比如 MoE 的专家数、RoPE 的 base）。**但整体框架是通用的。**

**为什么 Muon 的 lr 不随 `D` 缩放

一个细节：`dmodel_lr_scale` **只用在 AdamW 组**：

```python
lr=ac.embedding_lr * batch_lr_scale * dmodel_lr_scale,
```

Muon 组的 lr 是 `mc.lr * batch_lr_scale` —— **没有 `dmodel_lr_scale`**。

**为什么？** 因为 Muon 的更新量已经被正交化**归一化**了 ——
第 22 章实测：梯度差 10⁶ 倍，正交化后的输出完全一样。

所以 Muon 的更新量天然与「梯度的绝对尺度」无关，
而 AdamW 那边 `embedding_lr = 0.3` 是绝对尺度 ——
宽度变大时绝对尺度需要调整，所以要缩放。

**这是一个内在一致的设计**：`lr` 的缩放规则和
「更新量是否已被归一化」匹配。

**ZeRO / FSDP 的分组顺序**

分布式下有一个额外的约束：**同一个 group 的参数必须在
同一个 rank 上**（或者按 `world_size` 等分）。

`shape` 分组天然满足（同形 → 可以等分）。
`角色` 分组（AdamW）**不满足** ——
`wte` 是单个大张量，`world_size=8` 时会被切 8 份。

`MuonAdamW.step` 的 AdamW 分支处理了这个：

```python
if p.numel() < 1024:
    # 小参数（标量类）：all_reduce 梯度，状态保持复制
    dist.all_reduce(p.grad, op=dist.ReduceOp.AVG)
    ...
else:
    # 大参数：reduce_scatter -> 各 rank 只更新自己那一片
    assert p.shape[0] % world == 0, ...
```

**`p.shape[0] % world == 0` 这个断言** 就是分组的额外约束。
本项目单卡所以不触发。卷 6 会细讲。
