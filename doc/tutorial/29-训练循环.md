## 读这段代码时注意什么 #1：续训要恢复四样东西

**最容易写漏的一段**（第 296-316 行）：

```python
if os.path.isdir(ckpt_dir) and not args.no_resume:
    last = find_latest(ckpt_dir)
    if last is not None:
        model.load_state_dict(load_checkpoint(ckpt_dir, last, device, "model"))
        # ★ 光恢复权重是不够的。meta 里另外三样也必须读回来，
        #   否则「续训」名不副实：
        #     dataloader_state  数据流位置。
        #     best_val_bpb      历史最好指标。
        #     history           训练曲线。
        meta = load_checkpoint(ckpt_dir, last, "cpu", "meta")
        resume_dl_state = meta.get("dataloader_state")
        _bpb = meta.get("best_val_bpb")
        best_bpb = float("inf") if _bpb is None else float(_bpb)
        history = meta.get("history", [])
        start_step = last + 1
```

**四个必须恢复的东西**，少一个都出问题：

| 恢复什么 | 不恢复的后果 |
|---|---|
| **模型权重** | 从头训练 |
| `dataloader_state` | **把前 `start_step` 步的数据重喂一遍** |
| `best_val_bpb` | 「历史最好」只统计续训之后，**还会把错误值写回新存档** |
| `history` | 曲线图只剩续训之后那一段 |

**第二行是最严重的** —— 它意味着「续训」在偷偷重复训练。
而且 `dataloader.py` 里那个认真实现了 `pq_idx/rg_idx/epoch` 的
`resume_state` 参数（第 05 章）**就永远没有调用方**。

> **「一个功能被认真实现了但没有调用方」是最难发现的死代码。**
> 看代码时要专门找这种：参数存在、逻辑正确、测试覆盖 ——
> 但生产路径从没传过。

**第四行那个 `inf` ↔ `None` 的转换**也很值得注意：

```python
_bpb = meta.get("best_val_bpb")
best_bpb = float("inf") if _bpb is None else float(_bpb)
```

因为 JSON **不能表示 `inf`**。`checkpoint._json_safe` 会把它写成 `null`。
所以从 JSON 读回来是 `None`，必须还原成 `inf`。

⚠ 如果忘了还原：续训后 `best_bpb = None`，
然后 `min(None, bpb)` 在第一次验证时抛 `TypeError`。
第 36 章讲 checkpoint 时会再碰一次这个。


## 读这段代码时注意什么 #2：梯度累积为什么要除

```python
# ---- 6.1 梯度累积 ----
loss_val = 0.0
for micro in range(sc["grad_accum_steps"]):
    loss = model(x, y)
    loss_val = loss.detach()
    (loss / sc["grad_accum_steps"]).backward()
    # 立刻预取下一批：这次 H2D 与 GPU 上的反向重叠，不浪费时间
    x, y, dl_state = next(train_loader)
```

**`(loss / grad_accum_steps).backward()` 的除法不能省。**

`backward()` 是**梯度累加**：每次调用把 `∂loss/∂θ` 加到 `θ.grad` 上。
不除的话：

```
累积 grad = Σ_{i=1}^{G} ∂loss_i/∂θ    （G = grad_accum）
```

有效学习率会**放大 G 倍**。

**实测档位**：

| 档位 | `grad_accum` | `device_batch_size` | `seq_len` | 全局 batch |
|---|---|---|---|---|
| `ablation` | 4 | 16 | 1024 | 65,536 |
| `full` | **128** | **8** | 1024 | **1,048,576** |

`full` 档要累积 **128 次**才能凑够 2²⁰ token 的全局 batch ——
**除错的话 lr 会大 128 倍，第一步就 NaN。**

### `loss_val = 0.0` 然后被覆盖

```python
loss_val = 0.0
for micro in range(...):
    loss_val = loss.detach()      # ← 每次覆盖
```

初始化成 `0.0` **只是为了不让 linter 抱怨「可能未定义」**。
实际值是**最后一个 micro-step** 的 loss，不是平均值。

⚠ 这意味着日志里的 `loss` 是「最后一个小批的 loss」，
不是「这一步的平均 loss」。在 batch 大小差异不大时没差别，
但**不该把它当成精确的平均值**。

## 读这段代码时注意什么 #3：预取是怎么重叠的

```python
    loss.backward()
    model.zero_grad(set_to_none=True)      # ← 实际上在 optimizer.step() 之后

    for micro in range(...):
        ...
        (loss / G).backward()
        x, y, dl_state = next(train_loader)      # ★ 立刻预取下一批
```

**`next(train_loader)` 在 `backward()` 之后立刻调用。**

这一行做的是 **CPU 侧**（dataloader 的打包 + tokenize）+ **H2D 拷贝**。
而 GPU 上正在跑 `backward` 的 kernel。

**两者天然重叠** —— 这是「零开销预取」的来源：
CPU 那几毫秒被 GPU 的计算完全盖住了。

⚠ **但这只在 `grad_accum > 1` 时有意义。**
`grad_accum = 1` 时循环只跑一次，`next(loader)` 紧跟着
`backward()`，而那时 GPU 已经在等数据了 ——
**变成串行，H2D 完全暴露**。

`ablation` 档 `grad_accum=4`，所以还有 3 次机会重叠。
`full` 档 128 次，重叠得很充分。

> 这也解释了 `full` 档为什么选 `dbs=8` 而不是更大的值
> （第 00 批的档位重构）：更大的 dbs 意味着每 micro-step 更慢，
> GPU 吃数据的间隔更长。

**第 05 章的「先建 CPU row_buffer，再一次性搬到 GPU」**
就是这个设计的另一半 —— 单次 H2D 而不是几千次小拷贝。

## 读这段代码时注意什么 #4：超参更新在 `step()` 之前

```python
# ---- 6.2 更新超参 ----
lm = lr_mult(step)
for g in optimizer.param_groups:
    g["lr"] = g["initial_lr"] * lm
    if g["kind"] == "muon":
        g["momentum"] = mom_sched(step)
        g["weight_decay"] = wd_sched(step)
optimizer.step()
model.zero_grad(set_to_none=True)
```

**顺序：改超参 → step → 清梯度。**

三个细节：

**① `g["initial_lr"]`** 是循环外面存的（第 334-335 行）：

```python
for g in optimizer.param_groups:
    g["initial_lr"] = g["lr"]
```

**必须先存再反复乘。** 否则 `lr = initial_lr × lr_mult` 写成
`lr = lr × lr_mult` 会指数爆炸 —— 第 1 步就 inf。

**② 只给 muon 组设 `momentum` 和 `weight_decay`**

```python
if g["kind"] == "muon":
```

因为 AdamW 组没有这两个字段（第 27 章：`betas` 才是它的）。
**如果无条件设，会往 AdamW 的 group 里塞一个它不读的多余字段** ——
不报错，但会让人以为 AdamW 也在做 WD。

**③ `zero_grad(set_to_none=True)` 而不是 `zero_grad()`**

`set_to_none=True` 把 `.grad` 置为 `None` 而不是 0 张量。
省显存（`None` 不占内存），而且下一次 backward 会重新分配。

**代价**：第一次 backward 时 `p.grad` 是 `None`，
`torch._foreach` 那套优化路径要多一个判断分支。
在 `muon_step` 里显式 `continue` 掉了 `p.grad is None` 的情况。

## 读这段代码时注意什么 #5：日志的 EMA 偏差修正

```python
ema, smooth, total_time = 0.9, 0.0, 0.0
...
lf = loss_val.item()
smooth = ema * smooth + (1 - ema) * lf
debiased = smooth / (1 - ema ** (step + 1))
```

`smooth` 是一个 **EMA**，初始化为 0，所以**早期系统性偏低**。
偏差修正 `1/(1 - ema^t)` 把它还原。

⚠ **`step + 1` 而不是 `step`**：因为 `step` 从 0 开始，
第 0 步之后 `smooth` 只累积了 1 项，对应的修正是 `1/(1-0.9) = 10`。
用 `step` 会得到 `1/(1-1) = ∞`。

**实测 step 0 的 loss**（`full` 档 / `ablation` 档，各跑 2 步）：

```
full:      step 0 | loss 9.0117   lrm 0.025 | dt 61745ms
ablation:  step 0 | loss 9.0108   lrm 0.025 | dt  3190ms
```

**这两个数都等于 `ln(8192) = 9.0109`** —— 差 0.0001~0.0008，
就是 bf16 舍入的量级（第 07 章量过同样的现象）。

> **这是一个可以自查的量**：随机初始化 + 正确 softmax 的模型，
> 第一步 loss 必须 ≈ `ln(V)`。
> 明显**高于** `ln(V)` → 初始化有问题（比如 `lm_head` 太大）。
> 明显**低于** → logits 太集中，有数值问题。
>
> ⚠ **算 `ln(V)` 一定要用 `tokenizer.get_vocab_size()`，不是预设里的值。**
> 见下面「★ 预设的 16384 没有真正生效」。

## ★ 预设的 `vocab_size=16384` 没有真正生效 —— 本次实测发现

`ModelConfig` 的定义是自相矛盾的：

```python
vocab_size: int = 16384       # 由 tokenizer 决定
```

**默认值写死 16384，注释却说「由 tokenizer 决定」。**

而 `train_base.main` 无条件用真实词表覆盖：

```python
cfg = make_run_config(args.mode, depth=args.depth,
                      vocab_size=tokenizer.get_vocab_size())
```

**没有 `--vocab-size` 开关，也没有条件判断** —— 只要传了就是覆盖。

而本仓库的 tokenizer 是 **8192**（不是 16384）。实测启动日志：

```
词表           : 8192（padding 后 8192）
```

### 后果：所有按 16384 推导的数字都不是真实训练的那个

| 量 | 按预设 16384 算（**文档里写的**） | 按实际 8192 算（**真正训的**） |
|---|---|---|
| `ln(V)` 随机基线 | 9.7041 | **9.0109** |
| `lm_head`（d24） | 12,582,912 | **6,291,456** |
| 12 张 ve 表（d24） | 150,994,944 | **75,497,472** |
| `scaling_params`（d24） | 195,035,136 | **176,160,768** |

四档实测：

| 档 | 预设 `vocab_size` | 实际 `vocab_size` | `scaling_params` | `lm_head` |
|---|---|---|---|---|
| `debug` | 8192 | 8192 | 286,720 | 262,144 |
| `smoke` | 8192 | 8192 | 1,835,008 | 1,048,576 |
| `ablation` | **16384** | **8192** | 13,762,560 | 3,145,728 |
| `full` | **16384** | **8192** | 176,160,768 | 6,291,456 |

⚠ **受影响的历史章节**（它们把预设值当成了实际值）：
[第 02 章](02-为什么需要分词器.md)（V=16384 的压缩率论证）、
[第 07 章](07-先跑通一个最小GPT.md)（`ln = 9.7041`）、
[第 14 章](14-残差流与Pre-LN.md)、[第 15 章](15-权重绑定与logit-softcap.md)（`lm_head` 尺寸）、
[第 18 章](18-Value-Embeddings与门控.md)（ve 表参数量）、
[第 22 章](22-为什么矩阵参数适合Muon.md)。

**这些章节的方法论仍然成立**（它们讲的是「V 怎么选」「lm_head 为什么要 softcap」）。
**只是那些具体数字描述的是一个当前跑不出来的配置。**

### ★ 根因不在 `ModelConfig`，在 tokenizer 的缓存

⚠ **我第一眼判断错了** —— 看到 `# 由 tokenizer 决定` 就以为
预设的 16384 是「有意的死值」。**它不是。**

本项目的本意链条是：

```
script/_common.sh:      debug|smoke → VOCAB=8192
                        ablation|full → VOCAB=16384
script/train_base.sh:   python -m training.train_tokenizer --vocab-size "$VOCAB"
```

**所以 16384 才是本意。** 问题出在 `train_tokenizer`：

```python
ckpt = os.path.join(tokdir, "tokenizer.pkl")
if os.path.exists(ckpt):
    log0(f"tokenizer 已存在，跳过训练：{ckpt}")
else:
    tok = BPETokenizer.train(..., args.vocab_size)
```

**它只判断文件存在，不检查词表大小是否等于 `args.vocab_size`。**

于是链条变成：

1. 第一次跑的是 `smoke`（或 `debug`）→ 缓存里建了一个 **8192** 的 tokenizer
2. 后来跑 `ablation` / `full`，传 `--vocab-size 16384`
3. 文件已存在 → **静默复用那个 8192 的**
4. `train_base` 读 `tokenizer.get_vocab_size()` = **8192** → 真的按 8192 训练

实测（当前仓库状态）：

```
$ uv run python -m training.train_tokenizer --vocab-size 16384 --shards 2
tokenizer 已存在，跳过训练：/home/ben/.cache/gpt_base/tokenizer/tokenizer.pkl
── 压缩率报告 ──────────────────────────────
chars / token  : 3.240
压缩率         : 3.240 bytes/token
词表大小       : 8,192          ← 要求的是 16384
```

⚠ **`词表大小 : 8,192` 就在日志里，但它上面那行写的是「跳过训练」** ——
读起来像「一切正常，无需处理」。**没有任何一行说
「这和你要的 16384 不符」。**

### 为什么它能活这么久

1. **判据没覆盖**：`test_presets.py` 检查的是 `script/*.sh` 里的 `VOCAB=`
   与 tokenizer 是否一致 —— 那条判据**在 `smoke` 下是绿的**
   （`smoke` 本来就要 8192）。而它**不检查 `train_tokenizer` 的复用逻辑**。
2. **预设自洽性判据也抓不到**：`test_full_preset_batch_size_is_self_consistent`
   之类只算「给定 V 时配置自洽吗」，**不检查 V 本身对不对**。
3. **它不是崩溃，是降级**：模型照训、loss 照降，只是**在另一个词表上**。

> **这是本项目「静默失效」的第四例**，也是最贵的一例 ——
> 前三例（第 24 章 `ns_steps>5`、第 25 章 `use_muon_plus`、
> 第 28 章 compile 回落）都只影响**效果**，
> 这一例影响的是**模型形状**，而且**改了之后所有文档数字都要重算**。
>
> **共通点：全部都是「复用了不该复用的旧状态」。**
> 前三例复用的是代码里的常量，这一例复用的是磁盘上的缓存。

### 修法（本次只记录不改行为）

```python
if os.path.exists(ckpt):
    existing = BPETokenizer.load().get_vocab_size()

```

⚠ **这会改变 `ablation` / `full` 档的训练结果**（真的按 16384 训练，
嵌入表显存翻倍），**属于需要用户拍板的事**，本会话不擅自改。

## 读这段代码时注意什么 #5b：★ `平均 MFU` 的分子分母口径不一致

**这是本章第二个实测发现的真 bug。**

```python
total_flops = flops_per_token * sc["total_batch_size"] * num_iterations   # ← 全部步
...
log0(f"  总 FLOPs              : {total_flops:.4e}")
log0(f"  平均 MFU              : {100*total_flops/total_time/peak_flops:.2f}%")
```

而 `total_time` 只累加 `step > 10` 的步（第 393-394 行）：

```python
dt = time.time() - t0
if step > 10:
    total_time += dt
```

**分子数了 `num_iterations` 步，分母只数了「跳过前 10 步之后」的步。**

### 实测：13 步的 `full` 档

```
step     0/13 (  0.0%) | loss  9.0117 | ... | mfu  26.4% | dt  61.75s
step     1/13 (  7.7%) | loss  8.9705 | ... | mfu  27.7% | dt  58.85s
...
step    13/13 (100.0%) | loss  6.9483 | ... | mfu  27.7% | dt  58.86s
...
总耗时（不含前 10 步）: 2m56s
平均 MFU              : 119.96%        ← 荒谬
```

逐步 MFU 全程是 **26.4% → 27.7%**，汇总却报 **119.96%**。

**精确算术**：

```
分子 = f × B × num_iterations = f × B × 2088
分母 = total_time            = 176.57 s（只有 step 11,12,13 三步）
比值 = 2088 / 3 = 696
```

⚠ **而逐步 MFU 是 27.68%。** 用同口径重算：

```
正确 = 100 × f × B × 3 / 176.57 / peak = 28.50%
```

（与逐步的 27.68% 差 3%，是我这里 `f` 用了预设的 16384 词表算的 ——
换成真实的 8192 词表后**两者完全吻合，差 0.00%**。见上一节。）

### ★ 为什么这个 bug 能活这么久

**因为它的误差正比于 `num_iterations / (num_iterations - 11)`：**

| 运行的 `num_iterations` | 比值 | 误差 |
|---|---|---|
| 13（我这次） | 2088/3 = **696** | 高估 69,500% |
| 100 | 100/89 = 1.124 | 高估 12.4% |
| 1,000 | 1000/989 = 1.011 | 高估 1.1% |
| **2,088（`full` 档全程）** | 2088/2077 = **1.0053** | **高估 0.53%** |

**在真实训练长度下只偏 0.53% —— 肉眼不可见。**

而 `debug` / `smoke` 这类「跑几步看看管线通不通」的场景下，
误差是**几百倍**。

> **这是本项目「单步测量不可信」的第三个变种**：
> 一个量的误差取决于你测多久，所以**短测试恰好是最容易骗过你的场景**。
> 参见第 00 批的显存/吞吐、第 01 章的时间分布。

### 为什么修它不影响任何训练结果

`平均 MFU` 是**收尾时打印的一个数字**，不参与任何计算、
不写进 checkpoint、不影响梯度。

所以修它是安全的。**但本会话按惯例只记录不改行为** ——
它会改动文档里引用的数字（`23.6%` 那个），属于需要用户拍板的事。

**一行修法**（把分子的步数口径对齐）：

```python
total_flops = flops_per_token * sc["total_batch_size"] * timed_steps
```

其中 `timed_steps` 应该和 `total_time` 一起累加。

⚠ 更彻底的做法是**把 `total_time` 改成累加全部步**，
这样两个数天然同口径，`step > 10` 的门槛就不需要了
（但那会让编译时间计入平均，得不偿失）。
**所以对齐分子是更小的改动。**

### 为什么排除前 10 步是对的

那 10 步包含 `torch.compile` 的编译时间（第 28 章实测首次 3 步 2.43s）、
CUDA context 初始化、cuDNN benchmark —— **混进平均会让 tok/s 完全失真**。

实测（`full` 档）：

| step | dt | 说明 |
|---|---|---|
| 0 | **61.75 s** | 含编译 + CUDA 初始化 |
| 1 | 58.85 s | |
| 2 ~ 13 | 58.81 ~ 58.86 s | 稳态，抖动 < 0.1% |

`ablation` 档的对比更明显：step 0 是 **3190 ms**，step 1 掉到 **522 ms**（6.1 倍）。

本项目已经因为「单步测量不可信」栽过两次

这里的 `step > 10` 是同一原则的代码体现。

⚠ **而这条门槛正是上面那个 bug 的成因** ——

## 读这段代码时注意什么 #6：MFU 是怎么算的

```python
flops_per_token = model.estimate_flops_per_token()
peak_flops = get_peak_flops(torch.cuda.get_device_name(0)) if device_type == "cuda" else float("inf")
...
tok_per_sec = int(sc["total_batch_size"] / dt)
flops_per_sec = flops_per_token * sc["total_batch_size"] / dt
mfu = 100 * flops_per_sec / peak_flops if peak_flops != float("inf") else 0.0
```

**MFU = 实际 FLOPs / GPU 峰值 FLOPs。**

两个注意点：

**① 分子用的是「估计的」FLOPs**

`estimate_flops_per_token()` 是**配置公式**算的
（`common/config.py` 里 `6 × matmul_params + attention`），
不是实测。

**它不含**：
- 嵌入查表（第 18 章：没有矩阵乘 FLOPs）
- norm、激活函数的逐元素运算
- 优化器自己的计算

所以「实际 FLOPs」其实是「**有用的** FLOPs」，
不是「GPU 真正执行的 FLOPs」。

**② 分母是 fp32 累加算力**

```python
get_peak_flops(torch.cuda.get_device_name(0))
```

而实际训练用的是 **bf16 tensor core**。
所以分母是「如果用 fp32 能跑多快」，
分子是「按 bf16 的公式估算的有用计算量」。

**两边的口径不一致 —— 所以本项目的 MFU 是个相对指标，不是绝对效率。**

## 读这段代码时注意什么 #7：`model.train()` / `model.eval()` 的三处

训练循环里有三组「进入 eval 再回来」：

```python
# 6.4 验证
bpb = evaluate_bpb(...)
...
model.train()

# 6.5 采样
model.eval()
out = list(model.generate(ids, ...))
model.train()
```

**本项目所有 `Block` / `MLP` / `Attention` 都没有
dropout 或 batchnorm**（第 07 章：nanochat 的设计里没有），
所以 `train()` / `eval()` **实际上不做任何事**。

但**必须写**，因为：
1. 将来加 dropout 时不会漏
2. `generate()` 带 `@torch.inference_mode()`（第 32 章），
   调用前后必须恢复梯度上下文

⚠ **`model.train()` 在 `evaluate_bpb` 之后、`generate` 之前
也调了一次**（第 427 行）。而 `evaluate_bpb` 内部已经
`model.eval()` 了。所以是两次成对的调用。

## 常见坑

### 坑 1：续训只恢复权重

见上面。**这是本章最重要的一条** —— 它的后果是
「悄悄重复训练」，而且**从任何日志里都看不出来**。

### 坑 2：梯度累积忘记除

见上面。`full` 档放大 128 倍。

### 坑 3：`zero_grad()` 而不是 `zero_grad(set_to_none=True)`

不报错，但显存高一点、backward 慢一点。

### 坑 4：把 `loss_val` 当成一步的平均

见上面。它是**最后一个 micro-step** 的值。

### 坑 5：把 MFU 当成绝对效率

见上面。分子「估计」、分母「fp32」，口径不一致。

### 坑 6：★ 照抄预设里的 `vocab_size` 算 `ln(V)`

**预设写 16384，实际训练是 8192**（tokenizer 缓存被 `smoke` 那次污染了，
根因见上面「★ 根因不在 `ModelConfig`，在 tokenizer 的缓存」）。

算随机基线、算 `lm_head` 尺寸、算 ve 表参数量 —— 全部要用
`tokenizer.get_vocab_size()`，不是 `PRESETS[mode]['vocab_size']`。

⚠ 最容易踩的地方是**验算自己的判据**：
如果用 16384 算 `flops_per_token`，重算出来的 MFU
会与日志差 3%，然后你会以为自己发现了什么 ——
**其实只是词表用错了。**（我这次就踩了。）

**最快的自查**：启动日志里有一行 `词表 : 8192（padding 后 8192）`。

### 坑 7：★ 相信「平均 MFU」那一行

它的分子分母口径不一致，短跑时能高估几百倍。
**用逐步 MFU 那一列，或者自己按同口径重算。**

### 坑 8：以为 `train()` / `eval()` 现在有用

本项目没有 dropout/batchnorm，所以它们是 no-op。
**但不要因此删掉调用。**

### 坑 9：`save_every = -1` 的含义

```python
if last_step or (cfg.train.save_every > 0 and step % cfg.train.save_every == 0):
```

`save_every > 0` 那个判断的意思是「关掉定期存档，只在最后一步存」。
**所以 `-1` 不是「每 -1 步存一次」，是「不存」。**

⚠ 但 `last_step` 那一支仍然会存 ——
**永远会有一个最后一步的 checkpoint**（这正是自动续训能工作的原因）。

## 延伸

**`grad_accum` 的显存含义**

`device_batch_size × grad_accum = 总 batch`。
固定总 batch 时，**`grad_accum` 越大，单步显存越小**。

`full` 档的 `dbs=8, grad_accum=128` 就是显存逼出来的
（第 00 批实测：dbs=12 峰值 15.01 GiB，第 2 步
`CUDA driver error: device not ready`）。

**梯度累积的一个理论问题**

累积期间的所有 micro-step 用的是**同一组权重**。
所以这不是「真正的大 batch」，而是「小 batch + 梯度平均」。

两者的区别：
- 真大 batch：batch 内样本之间可以有不同的激活、不同的中间状态
- 梯度累积：每个 micro-batch 独立前向反向，但参数不变

实践中两者结果非常接近（第 5 行脚手架和 nanochat 都用累积），
但**理论上不等价**。

**`set_to_none=True` 的代价**

`p.grad = None` 之后，第一次 `backward()` 要重新分配梯度张量。
对 346M 参数的模型，这是一次 **1.29 GiB 的分配**。

所以 `grad_accum=128` 意味着每步只分配**一次**，
而不是 128 次 —— **这是累积的另一个隐性好处。**

**`sync()` 的作用**

```python
sync()          # 循环开头
t0 = time.time()
...
sync()          # 循环结尾
dt = time.time() - t0
```

`synchronize(device_type)` 在 CPU 上是 no-op，
在 CUDA 上是 `torch.cuda.synchronize()`。

**两个 `sync()` 是计时必需的**：CUDA 是异步的，
不同步的话 `dt` 只测到「提交 kernel 的时间」，而不是「执行的时间」。

**为什么循环开头也要 sync**

防止上一轮的 GPU 工作泄漏到这一轮的计时里。
