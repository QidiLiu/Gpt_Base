## 读这段代码时注意什么 #1：续训要恢复四样东西

**最容易写漏的一段**（第 296-316 行）：

```python
if os.path.isdir(ckpt_dir) and not args.no_resume:
    last = find_latest(ckpt_dir)
    if last is not None:
        model.load_state_dict(load_checkpoint(ckpt_dir, last, device, "model"))
        # ★ 光恢复权重是不够的。meta 里另外三样也必须读回来，
        #   否则「续训」名不副实：
        #     dataloader_state  数据流位置。
        #     best_val_bpb      历史最好指标。
        #     history           训练曲线。
        meta = load_checkpoint(ckpt_dir, last, "cpu", "meta")
        resume_dl_state = meta.get("dataloader_state")
        _bpb = meta.get("best_val_bpb")
        best_bpb = float("inf") if _bpb is None else float(_bpb)
        history = meta.get("history", [])
        start_step = last + 1
```

**四个必须恢复的东西**，少一个都出问题：

| 恢复什么 | 不恢复的后果 |
|---|---|
| **模型权重** | 从头训练 |
| `dataloader_state` | **把前 `start_step` 步的数据重喂一遍** |
| `best_val_bpb` | 「历史最好」只统计续训之后，**还会把错误值写回新存档** |
| `history` | 曲线图只剩续训之后那一段 |

**第二行是最严重的** —— 它意味着「续训」在偷偷重复训练。
而且 `dataloader.py` 里那个认真实现了 `pq_idx/rg_idx/epoch` 的
`resume_state` 参数（第 05 章）**就永远没有调用方**。

> **「一个功能被认真实现了但没有调用方」是最难发现的死代码。**
> 看代码时要专门找这种：参数存在、逻辑正确、测试覆盖 ——
> 但生产路径从没传过。

**第四行那个 `inf` ↔ `None` 的转换**也很值得注意：

```python
_bpb = meta.get("best_val_bpb")
best_bpb = float("inf") if _bpb is None else float(_bpb)
```

因为 JSON **不能表示 `inf`**。`checkpoint._json_safe` 会把它写成 `null`。
所以从 JSON 读回来是 `None`，必须还原成 `inf`。

⚠ 如果忘了还原：续训后 `best_bpb = None`，
然后 `min(None, bpb)` 在第一次验证时抛 `TypeError`。
第 36 章讲 checkpoint 时会再碰一次这个。

## 读这段代码时注意什么 #2：梯度累积为什么要除

```python
# ---- 6.1 梯度累积 ----
loss_val = 0.0
for micro in range(sc["grad_accum_steps"]):
    loss = model(x, y)
    loss_val = loss.detach()
    (loss / sc["grad_accum_steps"]).backward()
    # 立刻预取下一批：这次 H2D 与 GPU 上的反向重叠，不浪费时间
    x, y, dl_state = next(train_loader)
```

**`(loss / grad_accum_steps).backward()` 的除法不能省。**

`backward()` 是**梯度累加**：每次调用把 `∂loss/∂θ` 加到 `θ.grad` 上。
不除的话：

```
累积 grad = Σ_{i=1}^{G} ∂loss_i/∂θ    （G = grad_accum）
```

有效学习率会**放大 G 倍**。

**实测档位**：

| 档位 | `grad_accum` | `device_batch_size` | `seq_len` | 全局 batch |
|---|---|---|---|---|
| `ablation` | 4 | 16 | 1024 | 65,536 |
| `full` | **128** | **8** | 1024 | **1,048,576** |

`full` 档要累积 **128 次**才能凑够 2²⁰ token 的全局 batch ——
**除错的话 lr 会大 128 倍，第一步就 NaN。**

### `loss_val = 0.0` 然后被覆盖

```python
loss_val = 0.0
for micro in range(...):
    loss_val = loss.detach()      # ← 每次覆盖
```

初始化成 `0.0` **只是为了不让 linter 抱怨「可能未定义」**。
实际值是**最后一个 micro-step** 的 loss，不是平均值。

⚠ 这意味着日志里的 `loss` 是「最后一个小批的 loss」，
不是「这一步的平均 loss」。在 batch 大小差异不大时没差别，
但**不该把它当成精确的平均值**。

## 读这段代码时注意什么 #3：预取是怎么重叠的

```python
    loss.backward()
    model.zero_grad(set_to_none=True)      # ← 实际上在 optimizer.step() 之后

    for micro in range(...):
        ...
        (loss / G).backward()
        x, y, dl_state = next(train_loader)      # ★ 立刻预取下一批
```

**`next(train_loader)` 在 `backward()` 之后立刻调用。**

这一行做的是 **CPU 侧**（dataloader 的打包 + tokenize）+ **H2D 拷贝**。
而 GPU 上正在跑 `backward` 的 kernel。

**两者天然重叠** —— 这是「零开销预取」的来源：
CPU 那几毫秒被 GPU 的计算完全盖住了。

⚠ **但这只在 `grad_accum > 1` 时有意义。**
`grad_accum = 1` 时循环只跑一次，`next(loader)` 紧跟着
`backward()`，而那时 GPU 已经在等数据了 ——
**变成串行，H2D 完全暴露**。

`ablation` 档 `grad_accum=4`，所以还有 3 次机会重叠。
`full` 档 128 次，重叠得很充分。

> 这也解释了 `full` 档为什么选 `dbs=8` 而不是更大的值
> （第 00 批的档位重构）：更大的 dbs 意味着每 micro-step 更慢，
> GPU 吃数据的间隔更长。

**第 05 章的「先建 CPU row_buffer，再一次性搬到 GPU」**
就是这个设计的另一半 —— 单次 H2D 而不是几千次小拷贝。

## 读这段代码时注意什么 #4：超参更新在 `step()` 之前

```python
# ---- 6.2 更新超参 ----
lm = lr_mult(step)
for g in optimizer.param_groups:
    g["lr"] = g["initial_lr"] * lm
    if g["kind"] == "muon":
        g["momentum"] = mom_sched(step)
        g["weight_decay"] = wd_sched(step)
optimizer.step()
model.zero_grad(set_to_none=True)
```

**顺序：改超参 → step → 清梯度。**

三个细节：

**① `g["initial_lr"]`** 是循环外面存的（第 334-335 行）：

```python
for g in optimizer.param_groups:
    g["initial_lr"] = g["lr"]
```

**必须先存再反复乘。** 否则 `lr = initial_lr × lr_mult` 写成
`lr = lr × lr_mult` 会指数爆炸 —— 第 1 步就 inf。

**② 只给 muon 组设 `momentum` 和 `weight_decay`**

```python
if g["kind"] == "muon":
```

因为 AdamW 组没有这两个字段（第 27 章：`betas` 才是它的）。
**如果无条件设，会往 AdamW 的 group 里塞一个它不读的多余字段** ——
不报错，但会让人以为 AdamW 也在做 WD。

**③ `zero_grad(set_to_none=True)` 而不是 `zero_grad()`**

`set_to_none=True` 把 `.grad` 置为 `None` 而不是 0 张量。
省显存（`None` 不占内存），而且下一次 backward 会重新分配。

**代价**：第一次 backward 时 `p.grad` 是 `None`，
`torch._foreach` 那套优化路径要多一个判断分支。
在 `muon_step` 里显式 `continue` 掉了 `p.grad is None` 的情况。

## 读这段代码时注意什么 #5：日志的 EMA 偏差修正

```python
ema, smooth, total_time = 0.9, 0.0, 0.0
...
lf = loss_val.item()
smooth = ema * smooth + (1 - ema) * lf
debiased = smooth / (1 - ema ** (step + 1))
```

`smooth` 是一个 **EMA**，初始化为 0，所以**早期系统性偏低**。
偏差修正 `1/(1 - ema^t)` 把它还原。

⚠ **`step + 1` 而不是 `step`**：因为 `step` 从 0 开始，
第 0 步之后 `smooth` 只累积了 1 项，对应的修正是 `1/(1-0.9) = 10`。
用 `step` 会得到 `1/(1-1) = ∞`。

**实测 step 0 和 step 1 的值**（`full` 档，2 步）：

```
step     0/2 | loss  9.0108
step     1/2 | loss  9.0101
```

两个数都接近 `ln(16384) = 9.70`... 不对，
`full` 档 `vocab_size = 16384`，`ln(16384) = 9.704`。
而实测是 9.0108。

⚠ **这个差值值得注意**：随机初始化的模型第一步 loss
应该 ≈ `ln(V)` = 9.704。实测 9.0108 **明显低于**。

**原因**：`lm_head` 初始化 `std=0.001`（第 16 章），
而 `wte` 是 `std=0.8` 经 `rms_norm` 后 RMS=1。
所以 logits 的方差很小，softmax 接近均匀但不是完全均匀 ——
**loss 略低于 `ln(V)`**。

> 这是个可以自查的量：如果你的第一步 loss 明显**高于** `ln(V)`，
> 说明初始化有问题（比如 `lm_head` 太大）。
> 如果**低很多**，说明 logits 太集中，可能有数值问题。

### `total_time` 只累计 step > 10

```python
sync()
dt = time.time() - t0
if step > 10:
    total_time += dt
```

**前 10 步被排除在计时之外。** 因为那 10 步包含
`torch.compile` 的编译时间（第 28 章实测首次 3 步 2.43s）、
CUDA context 初始化、cuDNN benchmark ——
**混进平均会让 tok/s 完全失真**。

本项目已经因为「单步测量不可信」栽过两次
（第 00 批：显存和吞吐必须连跑 3-4 步取稳态）。
这里的 `step > 10` 是同一原则的代码体现。

## 读这段代码时注意什么 #6：MFU 是怎么算的

```python
flops_per_token = model.estimate_flops_per_token()
peak_flops = get_peak_flops(torch.cuda.get_device_name(0)) if device_type == "cuda" else float("inf")
...
tok_per_sec = int(sc["total_batch_size"] / dt)
flops_per_sec = flops_per_token * sc["total_batch_size"] / dt
mfu = 100 * flops_per_sec / peak_flops if peak_flops != float("inf") else 0.0
```

**MFU = 实际 FLOPs / GPU 峰值 FLOPs。**

两个注意点：

**① 分子用的是「估计的」FLOPs**

`estimate_flops_per_token()` 是**配置公式**算的
（`common/config.py` 里 `6 × matmul_params + attention`），
不是实测。

**它不含**：
- 嵌入查表（第 18 章：没有矩阵乘 FLOPs）
- norm、激活函数的逐元素运算
- 优化器自己的计算

所以「实际 FLOPs」其实是「**有用的** FLOPs」，
不是「GPU 真正执行的 FLOPs」。

**② 分母是 fp32 累加算力**

```python
get_peak_flops(torch.cuda.get_device_name(0))
```

而实际训练用的是 **bf16 tensor core**。
所以分母是「如果用 fp32 能跑多快」，
分子是「按 bf16 的公式估算的有用计算量」。

**两边的口径不一致 —— 所以本项目的 MFU 是个相对指标，不是绝对效率。**

第 01 章那个 23.6% 就是这么来的。而第 01 章的**时间分布**
（fwd 32.8% / bwd 66.6% / **opt 0.7%**）才是真实分解。

> 0.7% 的 opt 时间和第 28 章「编译省 18%」之间**看起来矛盾** ——
> 其实不矛盾：编译把 opt 从 862ms 降到 710ms，
> 但那 710ms 在整个 step 里仍然只占 0.7%。
> **优化器不是瓶颈，前向反向才是。**
> 第 28 章那个「9.9 小时」是相对值，不是绝对大头。

## 读这段代码时注意什么 #7：`model.train()` / `model.eval()` 的三处

训练循环里有三组「进入 eval 再回来」：

```python
# 6.4 验证
bpb = evaluate_bpb(...)
...
model.train()

# 6.5 采样
model.eval()
out = list(model.generate(ids, ...))
model.train()
```

**本项目所有 `Block` / `MLP` / `Attention` 都没有
dropout 或 batchnorm**（第 07 章：nanochat 的设计里没有），
所以 `train()` / `eval()` **实际上不做任何事**。

但**必须写**，因为：
1. 将来加 dropout 时不会漏
2. `generate()` 带 `@torch.inference_mode()`（第 32 章），
   调用前后必须恢复梯度上下文

⚠ **`model.train()` 在 `evaluate_bpb` 之后、`generate` 之前
也调了一次**（第 427 行）。而 `evaluate_bpb` 内部已经
`model.eval()` 了。所以是两次成对的调用。

## 常见坑

### 坑 1：续训只恢复权重

见上面。**这是本章最重要的一条** —— 它的后果是
「悄悄重复训练」，而且**从任何日志里都看不出来**。

### 坑 2：梯度累积忘记除

见上面。`full` 档放大 128 倍。

### 坑 3：`zero_grad()` 而不是 `zero_grad(set_to_none=True)`

不报错，但显存高一点、backward 慢一点。

### 坑 4：把 `loss_val` 当成一步的平均

见上面。它是**最后一个 micro-step** 的值。

### 坑 5：把 MFU 当成绝对效率

见上面。分子「估计」、分母「fp32」，口径不一致。

### 坑 6：以为 `train()` / `eval()` 现在有用

本项目没有 dropout/batchnorm，所以它们是 no-op。
**但不要因此删掉调用。**

### 坑 7：`save_every = -1` 的含义

```python
if last_step or (cfg.train.save_every > 0 and step % cfg.train.save_every == 0):
```

`save_every > 0` 那个判断的意思是「关掉定期存档，只在最后一步存」。
**所以 `-1` 不是「每 -1 步存一次」，是「不存」。**

⚠ 但 `last_step` 那一支仍然会存 ——
**永远会有一个最后一步的 checkpoint**（这正是自动续训能工作的原因）。

## 延伸

**`grad_accum` 的显存含义**

`device_batch_size × grad_accum = 总 batch`。
固定总 batch 时，**`grad_accum` 越大，单步显存越小**。

`full` 档的 `dbs=8, grad_accum=128` 就是显存逼出来的
（第 00 批实测：dbs=12 峰值 15.01 GiB，第 2 步
`CUDA driver error: device not ready`）。

**梯度累积的一个理论问题**

累积期间的所有 micro-step 用的是**同一组权重**。
所以这不是「真正的大 batch」，而是「小 batch + 梯度平均」。

两者的区别：
- 真大 batch：batch 内样本之间可以有不同的激活、不同的中间状态
- 梯度累积：每个 micro-batch 独立前向反向，但参数不变

实践中两者结果非常接近（第 5 行脚手架和 nanochat 都用累积），
但**理论上不等价**。

**`set_to_none=True` 的代价**

`p.grad = None` 之后，第一次 `backward()` 要重新分配梯度张量。
对 346M 参数的模型，这是一次 **1.29 GiB 的分配**。

所以 `grad_accum=128` 意味着每步只分配**一次**，
而不是 128 次 —— **这是累积的另一个隐性好处。**

**`sync()` 的作用**

```python
sync()          # 循环开头
t0 = time.time()
...
sync()          # 循环结尾
dt = time.time() - t0
```

`synchronize(device_type)` 在 CPU 上是 no-op，
在 CUDA 上是 `torch.cuda.synchronize()`。

**两个 `sync()` 是计时必需的**：CUDA 是异步的，
不同步的话 `dt` 只测到「提交 kernel 的时间」，而不是「执行的时间」。

**为什么循环开头也要 sync**

防止上一轮的 GPU 工作泄漏到这一轮的计时里。
