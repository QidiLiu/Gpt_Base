## 三个函数的形状总览

```python
warmup = train_cfg.warmup_steps                                  # 40
warmdown = round(train_cfg.warmup_steps * 0) + \
           round(train_cfg.warmdown_ratio * num_iterations)       # 0.65 × n
final_frac = train_cfg.final_lr_frac                              # 0.05
```

⚠ `round(train_cfg.warmup_steps * 0)` 这个写法很奇怪 ——
**它恒等于 0**，所以整个表达式就是 `round(ratio * n)`。

**这是代码考古的痕迹**：曾经有一个「warmup 也要参与 warmdown 计算」的
想法被移除了，但 `* 0` 没删干净。

**它无害**（`round(0) = 0`），但会让读者以为是某种边界处理。
**如果你要改这一行，直接删掉前半段。**

## 曲线一：lr_mult（三段式）

```python
def lr_mult(step: int) -> float:
    if step < warmup:
        # 线性从 0 爬到 1。用 (step+1)/warmup 保证第一步不为 0，
        # 否则第一步的更新量是 0，等于白跑
        return (step + 1) / warmup
    if step <= num_iterations - warmdown:
        return 1.0
    progress = (num_iterations - step) / max(warmdown, 1)
    return progress + (1 - progress) * final_frac
```

### 形状

```
1.0 ┤      ╭──────────────╮
    │     ╱                ╲
0.05┤────╯                  ╰────
    └────┬──────────────────────┬────
         warmup              warmdown
         (40 步)              (65% of iters)
```

### 三个细节

**① `(step + 1) / warmup` 而不是 `step / warmup`**

实测（`full` 档，`warmup=40`）：

| step | `lr_mult` |
|---|---|
| 0 | **0.0250** |
| 1 | 0.0500 |
| 39 | **1.0000** |

注释说明了原因：

> 用 `(step+1)/warmup` 保证第一步不为 0，否则第一步的更新量是 0，
> 等于白跑

**实测确认：`lr_mult` 严格为 0 的步数 = 0 步。**

⚠ 而且注意 step 39 就已经是 1.0 了（`40/40 = 1`）——
所以 **warmup 实际只有 39 步**，不是 40。

**② 平台的边界是 `<=`，不是 `<`**

```python
if step <= num_iterations - warmdown:
    return 1.0
```

`full` 档：`num_iterations=2088`, `warmdown=1357`，
所以平台是 `step ≤ 731`。实测 step 731 和 732 的 `lr_mult` 都是 1.0000。

**③ warmdown 是**线性**的，不是余弦**

```python
progress = (num_iterations - step) / max(warmdown, 1)
return progress + (1 - progress) * final_frac
```

`final_frac = 0.05`。代入：

```
lr_mult = progress + (1 - progress) × 0.05
        = 0.05 + 0.95 × progress
```

**线性**从 1.0 降到 0.05。

实测（`full` 档）：

| step | `progress` | `lr_mult` |
|---|---|---|
| 731 | 1.000 | 1.0000 |
| 1044 | 0.768 | 0.7809 |
| 1410 | 0.500 | 0.5246 |
| 2087 | 0.0007 | 0.0507 |
| 2088 | 0.0000 | **0.0500** |

`0.05 + 0.95 × 0.768 = 0.7796`，实测 0.7809 ——
差 0.0013 是因为 `progress` 用的是整数步的精确值。

### 满速比例

```
满速 lr=1.0: 693/2089 = 33%
```

代码注释说：

> 三段式有 35% 的时间满速跑（余弦只有 20%）

实测 33%（因为 warmup 只占 39 步，且平台边界是 `<=`）。

**这个 33% 是「为什么不用余弦」的答案**：
余弦在 80% 的时间里 LR 都在下降，
三段式有 1/3 的时间**跑在满速上**。

## 曲线二：muon_momentum（★★ 这里有个不对称）

```python
def muon_momentum(step: int) -> float:
    # 动量也在 warmup：早期动量缓冲里的噪声应该被压制
    if step < 400:
        frac = step / 400
        return (1 - frac) * 0.85 + frac * 0.97
    if step >= num_iterations - warmdown:
        # 训练末期降动量：让最后几步更接近纯 SGD，更「稳」
        progress = (step - (num_iterations - warmdown)) / max(warmdown, 1)
        return 0.97 * (1 - progress) + 0.90 * progress
    return 0.97
```

### ★ `400` 是硬编码的

```python
if step < 400:      # ← 字面量，不是 train_cfg.warmup_steps
    frac = step / 400
```

**`warmup_steps = 40`，但 momentum 的 warmup 是 400 步 —— 10 倍。**

这不是笔误（写法太刻意了），但**它是一个硬编码的魔数**：

| 调度量 | warmup 长度 | 来源 |
|---|---|---|
| lr | 40 步 | `TrainConfig.warmup_steps` |
| **momentum** | **400 步** | **硬编码 `400`** |
| wd | 无 warmup | 直接从峰值开始 |

**后果**：

`full` 档 `num_iterations = 2088`，所以 momentum 的 warmup
占了前 **19%** 的训练。而 `ablation` 档 3096 步，占 13%。

⚠ **在很短的训练上（比如 `debug` 档跑 50 步），
momentum 永远处于 warmup 中段**，不会达到 0.97。

实测（`full` 档）：

| step | `momentum` | 说明 |
|---|---|---|
| 0 | **0.8500** | 起点 |
| 1 | 0.8503 | |
| 39 | 0.8617 | lr 已经满速，momentum 才 0.86 |
| 41 | 0.8623 | |
| 731 | **0.9700** | 平台起点（warmup 早就结束了） |

**看 step 39 和 731 的对比**：lr 在 step 39 满速，
momentum 在 step 400 才到 0.97。

**这两条曲线的「满速时刻」差了 10 倍。**

> 为什么 momentum 需要更长的 warmup？
> 因为动量缓冲 `momentum_buf` 是**累积**的：它的噪声水平
> 取决于「累积了多少步」。
> lr 立即生效（下一步就用新的 lr），
> 而动量要积累几百步才稳定 ——
> 所以需要更长的压制期。
>
> 但 `400` 这个具体数字**没有推导**。它应该是调出来的，
> 而调它的那个实验在这个项目里没有。

### 训练末期降到 0.90

```python
if step >= num_iterations - warmdown:
    progress = (step - (num_iterations - warmdown)) / max(warmdown, 1)
    return 0.97 * (1 - progress) + 0.90 * progress
```

实测：

| step | `momentum` |
|---|---|
| 731 | 0.9700 |
| 1044 | 0.9539 |
| 1410 | 0.9350 |
| 2087 | 0.9001 |
| 2088 | **0.9000** |

**注释的理由**：

> 训练末期降动量：让最后几步更接近纯 SGD，更「稳」

`momentum = 0` 是纯 SGD。所以从 0.97 降到 0.90
是「朝纯 SGD 靠一点」。

⚠ **但 0.90 离 0 还很远** —— 最后一步的动量仍是 0.9，
「接近纯 SGD」这个说法偏强了。实测最后一步是 0.9000，
不是 0。

**这是一个名不副实的描述**（和第 25 章 `use_muon_plus` 那条类似）。

### ⚠ momentum warmdown 和 lr warmdown 用同一个长度

两者都用 `warmdown`（= 0.65n）。
但 lr 从 1.0 降到 0.05（**降到 5%**），
momentum 从 0.97 降到 0.90（**降到 93%**）。

**同一条时间窗，两条曲线的变化幅度差 20 倍。**

这可能是有意的（动量不该剧烈变化），也可能只是
「懒得再定义一个参数」。**本项目未验证。**

## 曲线三：weight_decay（余弦到 0）

```python
def weight_decay(step: int) -> float:
    """
    余弦衰减到 0。

    `weight_decay_final` 是**缩放后的峰值**（来自 resolve_scaling 的
    weight_decay_scaled），不是「终点值」。曲线形状：
        step 0        -> peak × 1.0
        step n/2      -> peak × 0.5
        step n        -> 0
    """
    cos = 0.5 * (1 + math.cos(math.pi * min(step, num_iterations) / num_iterations))
    return cos * weight_decay_final
```

### 形状

```
peak ┤╲
     │ ╲
     │  ╲___
     │      ╲____
   0 ┤           ╲___
     └────────────────┬────
     0                n
```

实测（`full` 档，peak = 0.02134）：

| step | `wd/peak` |
|---|---|
| 0 | **1.0000** |
| 39 | 0.9991 |
| 731 | 0.7275 |
| 1044 | **0.5000** |
| 1410 | 0.2384 |
| 2087 | 0.0000 |
| 2088 | 0.0000 |

**step 0 和 step 39 都是 ~1.0** —— 因为余弦在起点斜率为 0。
这和 lr 的线性 warmup 完全不同（**wd 从第一就是满强度**）。

⚠ **这意味着 wd 在最不稳定的训练早期就是全强度施加的。**
而 lr 正在从 2.5% 爬。这两者是**反向**的。

> 合理吗？可能合理 —— wd 是个正则化项，
> 早期参数还小（`c_proj` 全零），早期强 WD 的伤害小。
> 但**本项目没有测过 wd 曲线形状**
> （第 26 章：wd 只占梯度项的 3.1%，形状差异更小）。

### ★ 一个被删掉的死配置

docstring 里记着：

> 注：TrainConfig 里曾有个 `weight_decay_final_frac` 想表达
> 「末尾停在 peak 的某个比例」，但它**从未被任何代码读取**
> （grep 全仓只有定义行），已删除。
> 真要那个行为，把这里改成
> `weight_decay_final * (frac + (1 - frac) * cos)`
> —— 但那是一个**从未验证过的调度形状，别顺手加**。

**「从未被任何代码读取」是一个非常有价值的死代码记录。**

第 00 批删过一个类似的 `weight_decay_final_frac`（commit `df03d3e`）——
理由就是「从未被读取，接上会引入未验证的调度形状」。

**这个记录教的一件事**：

> **一个配置项存在 ≠ 它有效。**
> `grep` 全仓只有定义行 = 死配置。
> 判断一个配置是否有效，要看它**是否影响任何计算路径**，
> 而不是看它是否出现在 dataclass 里。

### 验证 3：三条曲线的「起点 → 各自的平台 → 终点」

⚠ 两个陷阱：
1. `lr_mult(0)` 不是它的峰值（峰值在平台），直接比首尾会误导
2. **「平台」必须取各自的饱和点** —— momentum 的平台在 step 400，
   不是 `warmup_steps=40`。用 40 会得到 0.8620（还在 warmup 中段）

```python
# 各自找饱和点
lr_sat = next(s for s in range(n + 1) if lr_m(s) == 1.0)
mom_sat = next(s for s in range(n + 1) if abs(mom(s) - 0.97) < 1e-9)

for tag, fn, sat, peak in [
        ("lr_mult", lr_m, lr_sat, 1.0),
        ("momentum", mom, mom_sat, 0.97),
        ("wd/peak", lambda s: wd(s) / sc["weight_decay_scaled"], 0, 1.0)]:
    s0, s1, sn = fn(0), fn(sat), fn(n)
    print(f"  {tag:9} 平台@{sat:<5} step0 {s0:.4f}  平台 {s1:.4f}  "
          f"终点 {sn:.4f}   warmdown 段变化 {(sn - s1) / peak:+.1%}")
```

实测：

```
  lr_mult   平台@39    step0 0.0250  平台 1.0000  终点 0.0500   warmdown 段变化 -95.0%
  momentum  平台@400   step0 0.8500  平台 0.9700  终点 0.9000   warmdown 段变化 -7.2%
  wd/peak   平台@0     step0 1.0000  平台 1.0000  终点 0.0000   warmdown 段变化 -100.0%
```

**lr 在 warmdown 段掉了 95%，momentum 只掉 7.2%。**

**而两者用的是同一个 `warmdown` 时间窗**（0.65 × 2088 = 1357 步）。
**注意平台的 step 差 10 倍（39 vs 400）。**

## 常见坑

### 坑 1：以为 momentum 的 warmup 也是 40 步

**是 400，硬编码。** 见上面实测。

### 坑 2：`round(train_cfg.warmup_steps * 0)` 让人困惑

恒等于 0 的死代码。**无害但误导。**

### 坑 3：以为 `weight_decay_final` 是终点值

**是峰值。** 曲线从它衰减到 0。

docstring 明确写了：「`weight_decay_final` 是**缩放后的峰值**
（来自 resolve_scaling 的 weight_decay_scaled），不是「终点值」」。

⚠ 这个命名（`..._final` 表示峰值）是**反直觉的**。
读代码时如果按名字理解，方向会完全搞反。

### 坑 4：以为 wd 也有 warmup

没有。**step 0 就是满强度**（`cos(0) = 1`）。

### 坑 5：把 `lr_mult` 当成实际 lr

`lr_mult` 是**乘数**。实际 lr 是：

```python
g["lr"] = g["initial_lr"] * lm
```

而 `initial_lr` 本身已经含了 `dmodel_lr_scale` 和
`batch_lr_scale`（第 27 章）。**所以 `lr_mult` 之外的因子有两层。**

### 坑 6：以为 `final_lr_frac = 0.05` 表示「lr 降到 5% 就停了」

**不是**。它在 `num_iterations` 那一**步**取值，
不是「提前停止」。训练照样跑满 2088 步。

## 延伸

**WSD（Warmup-Stable-Decay）**

本项目用的其实就是 WSD 调度：warmup → 稳定 → 衰减。
它在 2024 年被提出，理由和代码注释一致：

> 余弦在前 80% 的时间里 LR 一直在下降，
> 相当于大部分训练都没跑在最佳 LR 上；
> 三段式有 35% 的时间满速跑。

**关键论文**：*Stable and Efficient Shapley Value-Based
Batch Size Scheduling for Training Large Language Models*
（2024）。核心结论：大 batch 下余弦衰减浪费了太多步在低 lr 上。

**线性 vs 余弦衰减**

本项目的 warmdown 是**线性**的（`0.05 + 0.95 × progress`）。
WSD 论文用的是**余弦**。

两者实测差别不大（都是单调下降），但**本项目未测过**。
这又是一个「从上游照抄但没有验证」的形状。

**动量调度的理论**

`momentum` 从 0.85 → 0.97 的 warmup，理论上对应
「动量缓冲的有效时间常数从 5.7 步增加到 33 步」。

```
有效窗口 ≈ 1/(1 - momentum)
0.85 -> 6.7 步
0.97 -> 33 步
```

**训练末期降到 0.90**（窗口 10 步）意味着「让最后几步更接近 SGD」
—— 但 0.90 的窗口仍然是 10 步，而 batch 是 2²⁰ token。
所以「接近纯 SGD」这个说法在**这个 batch 尺度上并不成立**。

**只有 momentum → 0 才是真的纯 SGD。** 0.90 差得很远。

**为什么 lr 和 momentum 的 warmdown 长度要一样**

直觉上它们应该一样（都是「训练进入尾声」的信号）。
但**变化的幅度差 20 倍**（实测）：

| | 起点 | 终点 | 变化 |
|---|---|---|---|
| lr | 1.0 | 0.05 | -95% |
| momentum | 0.97 | 0.90 | -7% |

**可能的设计意图**：lr 该大起大落（前期探索、后期收敛），
动量该保持稳定（动量是「记忆」，剧变会破坏记忆）。

⚠ 但这只是我的推测，**代码注释里没有解释**。
