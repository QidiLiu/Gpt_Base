## 三步走

```python
def generate(self, tokens, num_samples=1, max_tokens=128,
             temperature=1.0, top_k=None, seed=42, use_tools=True):
    """
    流式生成。每次 yield (token_column, token_masks)：
        token_column  长度 num_samples 的列表，这一步各行吐出的 token
        token_masks   同长度，1=模型采样得到，0=被强制注入（工具输出）
    """
```

### 步骤 1：batch=1 prefill

```python
prefill_cache = KVCache(1, max_seq_len=max(len(tokens), 1), device=device, **kv_kwargs)
ids = torch.tensor([tokens], dtype=torch.long, device=device)
logits = self.model.forward(ids, kv_cache=prefill_cache)[:, -1, :]
logits = logits.expand(num_samples, -1).contiguous()
```

**只算一次 prompt。** `max_seq_len=max(len(tokens), 1)` ——
**缓存恰好装下 prompt**，不多分配一个位置。

（⚠ 那 `max(..., 1)` 是防 `len(tokens) == 0` 时 `max_seq_len=0`
导致 `torch.zeros(..., 0, ...)` 出问题。）

### 步骤 2：复制成 N 份

```python
need = len(tokens) + max_tokens
cache = KVCache(num_samples, max_seq_len=need, device=device, **kv_kwargs)
cache.prefill_from(prefill_cache)
del prefill_cache
```

**这是 RL rollout 的关键优化**（第 32 章）：
prompt 的前向只做一次，然后复制 N 份。

`need = len(tokens) + max_tokens` —— **恰好装下 prompt + 全部生成**。
不多分配。

⚠ `del prefill_cache` 很重要 —— 否则那份 cache 的显存要到函数结束才释放。

### 步骤 3：逐 token 解码

```python
rows = [_Row(tokens) for _ in range(num_samples)]
for _ in range(max_tokens):
    if all(r.done for r in rows):
        break
    next_ids = sample_next_token(logits, rng, temperature, top_k)
    sampled = next_ids[:, 0].tolist()

    column, masks = [], []
    for i, row in enumerate(rows):
        if row.forced:
            tid, mask = row.forced.pop(0), 0   # 强制注入的 token 不训练
        else:
            tid, mask = sampled[i], 1
        column.append(tid)
        masks.append(mask)
        row.tokens.append(tid)

        if tid in (asst_end, bos):
            row.done = True
        ...
```

**三个观察**：

**① `if all(r.done for r in rows): break`**

**只有所有行都结束了才停。** 所以 `generate` 返回的行**长度可能不同** ——
第 2 行结束了，第 5 行还在写，第 6 行的 `column` 里是第 2 行结束后
继续补的 token（`row.done` 的行仍然会被追加 token？）。

⚠ 看代码：**`row.done = True` 之后没有 `continue`**，
所以它仍然会走完 `row.tokens.append(tid)` ——
**结束的行的长度会和其他行一样长（都到 `max_tokens` 或全体结束）**。

这由 `test_generate_batch_masks_length_matches_results` 守着。

**② `logits.expand(num_samples, -1).contiguous()`**

prefill 只算了 batch=1，logits 是 `(1, V)`。expand 成 `(N, V)`。

⚠ **`.contiguous()` 不能省** —— `expand` 返回视图，
后面的 `sample_next_token` 要做 `topk`/`multinomial`，
对非连续张量会走慢路径或报错。

**③ 每一步都 yield `(column, masks)`**

流式接口。调用方拿到的 `column` 是**这一步**各行吐的 token，
不是累计的。

## 概念：`token_masks` 是两个用途合一

```python
token_masks   同长度，1=模型采样得到，0=被强制注入（工具输出）
```

**这个返回值同时服务两个场景**：

| 场景 | 用途 |
|---|---|
| **推理** | 知道哪些 token 是真的生成的 |
| **SFT 训练** | `mask=0` 的 token **不参与 loss** |

第 04 章讲过 SFT 的 loss mask（对话模板里哪些位置学）。
而工具调用注入的 token（比如 Python 解释器的输出）
**是环境给的，不是模型生成的** —— 训练时**不应该学它**
（模型没法预测一个函数调用的结果）。

**所以 `mask=0` = 「这个位置不监督」。**

⚠ 这是 RLHF 里的标准做法：**tool output 不进 loss**。
否则模型会学着「产生工具调用后应该看到什么」——
而那不是它能控制的。

### `_Row` 的状态机

```python
class _Row:
    """生成过程中每一行的状态。"""
    def __init__(self, tokens: list[int]):
        self.tokens = list(tokens)
        self.forced = []       # 待强制注入的 token（工具输出）
```

**`forced` 是一个队列** —— 工具调用被触发时，
把工具输出的 token 逐个 `pop(0)` 注入。

解码循环里：

```python
if row.forced:
    tid, mask = row.forced.pop(0), 0   # 强制注入的 token 不训练
else:
    tid, mask = sampled[i], 1
```

⚠ **注意 `mask` 在 `pop` 的同一行赋值** ——
「取出来」和「标记不训练」是同一个动作。
如果写成两行，很容易在中间插入别的逻辑而丢掉 mask。

## 概念：终止条件

```python
asst_end, bos = S("<|assistant_end|>"), self.tokenizer.get_bos_token_id()
...
if tid in (asst_end, bos):
    row.done = True
```

**两个终止 token**：

| token | 为什么是终止 |
|---|---|
| `<|assistant_end|>` | 对话模板里 assistant 段的结束（第 04 章） |
| **`<|bos|>`** | **模型输出了 BOS = 它认为该重新开始了** |

⚠ **BOS 也能终止这件事有点反直觉** ——
模型「生成 BOS」通常意味着它学到了「一轮结束」。
把它当终止信号是 nanochat 的做法。

**但如果模型乱吐 BOS，这会提前截断。**
所以 `test_generate_stops_at_assistant_end` 守的是 `<|assistant_end|>` 这条路径。

### 特殊 token 被禁用在 batch 里

```python
test_generate_batch_excludes_termination_tokens
```

**批量采样时，禁止某些 token 被采到。**
因为在 `num_samples > 1` 时，某一行的终止
不应该影响其他行 —— 所以那一步的 `sampled[i]` 即使是 `<|assistant_end|>`
也要处理（只让第 i 行 `done`）。

## 概念：★ 两个采样实现的等价性边界

`gpt.py` 和 `engine.py` 各有一个采样函数：

| 文件 | 函数 | 实现 |
|---|---|---|
| `gpt.py` | `sample_from_logits` | 在**完整 vocab** 上置 `-inf`，softmax，`multinomial` |
| `engine.py` | `sample_next_token` | 只在 **top-k 的 k 个值**上 softmax，`multinomial` 后 `gather` |

**两者的 docstring 都说「先 top-k 再除温度」。**

`engine.py` 的理由：

> 温度是对「logits 做缩放」，它不改变排序。先除温度再 top_k，
> 被裁掉的 -inf 位置依然是 -inf，结果一样 —— 但先 top_k 可以保证
> 「只有 k 个数参与后续计算」，在 vocab 很大时是实打实的性能差异。

`gpt.py` 的理由：

> 如果先除温度再裁剪，被裁掉的 token 仍然参与了温度缩放，
> 边界位置会有微小的数值差异。

⚠ **两个理由指向不同结论**（一个说一样，一个说有差异）。
**实测一下**。

### 实测：分布相同，seed 取样不同

```python
import sys, torch
sys.path.insert(0, "src")
import torch.nn.functional as F
from model.gpt import sample_from_logits
from inference.engine import sample_next_token

# (1) 固定 seed 下取样是否一致
torch.manual_seed(0)
V = 500
same = True
for trial in range(200):
    logits = torch.randn(1, V) * 3
    k = int(torch.randint(1, 60, (1,)).item())
    T = float(torch.rand(1).item() * 1.5 + 0.2)
    r = torch.Generator().manual_seed(trial)
    a = sample_from_logits(logits.clone(), r, temperature=T, top_k=k)
    r2 = torch.Generator().manual_seed(trial)
    b = sample_next_token(logits.clone(), r2, temperature=T, top_k=k)
    if not torch.equal(a, b):
        same = False
        break
print("200 组随机 (logits, k, T) 下逐 token 相同:", same)
```

实测：**`False`**（第 3 组就分叉了：
`k=15, T=1.205` → 一个给 174，另一个给 195）。

### 但分布是相同的

```python
# (2) 经验频率
V, k, T, N = 50, 15, 1.205, 200000
logits = torch.randn(1, V) * 3

def emp(fn):
    counts = torch.zeros(V)
    for i in range(N):
        r = torch.Generator().manual_seed(i)
        counts[fn(logits.clone(), r, temperature=T, top_k=k).item()] += 1
    return counts / N

a = emp(sample_from_logits)
b = emp(sample_next_token)
print(f"最大差异 {float((a - b).abs().max()):.5f}  "
      f"采样误差量级 {1 / N ** 0.5:.5f}")
```

实测：

```
最大差异 0.00093  采样误差量级 0.00224  -> 差异是误差的 0.42 倍
```

**差异比采样误差小 2.4 倍 —— 统计上无法区分。**

**结论**：

> **两个 sampler 的输出分布相同，但在同一个 seed 下取到的
> token 不同。**
>
> 原因：`torch.multinomial` 在 `V` 个元素上和在 `k` 个元素上
> 消耗随机数的方式不同（要处理累积概率的归一化）。
>
> **实践含义**：如果你换了 sampler 实现，**旧 seed 的实验就不能复现了**。
> 但统计结论仍然有效。
>
> ⚠ **这意味着「两个 docstring 的说法谁对」无法用 seed 比较来判定** ——
> 必须比分布。

## 读这段代码时注意什么：`get_pos()` 的同步成本

第 32 章提过，这里再算一次。

```python
def get_pos(self) -> int:
    return int(self.cache_seqlens[0].item())
```

`GPT.forward` 里每个 step 调一次（算 RoPE 的起始位置）：

```python
T0 = 0 if kv_cache is None else kv_cache.get_pos()
```

**decode 时每步一次 GPU→CPU 同步。**

而实测「单次 decode 前向 26.5 ms」里，**一次同步大概占 0.1-1 ms**
（要等前面所有 kernel 完成）。

**这是第 32 章那个「overhead bound」的组成部分之一。**

## 常见坑

### 坑 1：以为换 sampler 实现还能用旧 seed

**不能。** 见本章实测。

### 坑 2：以为两个 docstring 的说法矛盾

**它们指向不同问题**：
- `engine.py` 说「先 top_k 是性能」
- `gpt.py` 说「先 top_k 是数值」

**实测：分布完全相同。** 所以 `gpt.py` 那个「微小的数值差异」
的说法**没有实测支撑**（第 21 章就标注过这一点）。

### 坑 3：忘了 `logits.expand(...).contiguous()`

`expand` 是视图。后面 `topk`/`multinomial` 对非连续张量
会走慢路径。

### 坑 4：以为所有行会同时停止

`if all(r.done ...)` 才 break。所以**部分行会先结束**，
但它们**仍然会被追加 token**（`row.done = True` 之后没有 `continue`）。

所以**所有返回的行等长**（`test_generate_batch_multiple_samples_same_length`）。

### 坑 5：以为 `token_masks` 只是「哪些是生成的」

**它同时是 SFT 的 loss mask。** `mask=0` 的位置不监督。

### 坑 6：让模型输出任意 Python 而不设边界

`test_non_math_expression_does_not_hang` 守着这一点。
**表达式不合法时必须有兜底**，否则死循环。

## 延伸

**为什么 tool output 的 mask 是 0**

RLHF 的标准做法。三条理由：

1. **不可预测** —— 函数调用的结果由环境决定，模型无法从上文推出
2. **会泄漏信息** —— 如果模型能「背」出某个工具的输出，
   就没必要真的调用
3. **长度不可控** —— 输出长度差异大，会扰乱 batch

**streaming vs batch 的取舍**

`generate` 是流式的（每次 yield 一列），
所以调用方能拿到「逐步生成」的结果。

但**它要求所有行等长**（因为要返回同形状的 `column`/`masks`）。
真正的「每行独立长度」需要不等长的表示（列表）。

**为什么 prefill 只算一次**

`prefill_from` 的收益：
- `num_samples = N` 时 prompt 前向从 N 次变 1 次
- **但只有 prefill 这一次**。后续 decode 是 N 行的 batch 前向，
  那个没法省（每行的 KV 不同）

所以 `prefill_from` 的收益是**常数倍**，不是线性。

**`bos` 作为终止 token 的来历**

nanochat 的模型在训练时见过 `<|bos|>`，
它在生成里出现意味着「新一轮对话开始」。

本项目把 BOS 也当终止：
```python
if tid in (asst_end, bos):
```

⚠ **这在没有对话模板的纯文本生成里有点怪** ——
模型偶尔吐 BOS 就会截断。

**本项目 `full` 档只跑 base 预训练，没有对话模板**，
所以 BOS 的语义没有被训练过。这条路径的行为是
「继承自 nanochat（那里用于 chat）」。
