## 指标一：bpb —— 唯一可跨模型比的

```python
def evaluate_bpb(model, loader, token_bytes, max_batches: int) -> float:
```

第 06 章讲过原理，这里只讲**实现上的三个坑**。

### 坑 1：`token_bytes` 必须和 dataloader 一致

```python
token_bytes = get_token_bytes(device)
x, y, dl_state = next(train_loader)
```

`get_token_bytes` 返回一个**tensor**（不是 list），
用 `decode_single_token_bytes` 逐 token 得到字节数。

⚠ **为什么用 tensor 而不是 dict**：
bpb 的分母是「这些 token 覆盖了多少字节」。
如果用 Python list + 循环累加，在 8192 词表 × 几千个 token 上会很慢。

**tensor 化的关键**：`token_bytes` 可以直接在 GPU 上 gather，
然后 `.sum()` 一次完成。

### 坑 2：必须跳过 `-1`

dataloader 产出的 `targets` 里有 `-1`（不可 padding，所以理论上没有，
但 SFT 会有）。**`-1` 不能查 `token_bytes`** ——
那会越界或者拿到垃圾字节。

### 坑 3：分母必须是「实际参与 loss 的那些 token 的字节数」

不是「整个 val set 的字节数」。

**这个口径必须和第 06 章讲的一致**，否则跨模型的比较就是错的。

```bash
uv run pytest tests/test_metrics.py -k bpb -v
```

覆盖：

- `test_evaluate_bpb_empty_loader_is_finite`
- `test_evaluate_bpb_zero_byte_token_does_not_divide_by_zero`
- `test_evaluate_bpb_restore_mode_both_directions`

⚠ **`test_evaluate_bpb_zero_byte_token_does_not_divide_by_zero`**
守的是一个真实的边界：某些 token 可能对应 0 字节
（比如一个不完整的 UTF-8 序列片段）。
**分母不能是 0**。

## 指标二：pass@k —— 那个极易写错的地方

```python
def compute_pass_at_k(outcomes: list[list[bool]], k: int) -> float:
    """
    无偏估计的 pass@k（来自 Codex 论文的推导）。

    给一道题生成 n 个样本，其中 c 个正确。pass@k = 至少有一个对的概率。
    直接算 c/n 是有偏的（n 小的时候方差极大），正确的无偏估计是：

        pass@k = 1 - C(n-c, k) / C(n, k)
    """
```

### 公式的含义

`1 - C(n-c, k) / C(n, k)`：

- `C(n, k)` = 从 n 个样本里挑 k 个的方式数（分母）
- `C(n-c, k)` = **全部都错**的挑法数（分子）
- 所以 `1 - 那个比值` = 「至少有一个对」的概率

**这是无偏估计** —— 数学上等于「如果真的从 `p = c/n` 的分布里
独立采 k 个，至少一个对的概率」。

### ★ 那个写错的地方

docstring 说：

> 公式里的 c 是「n 个样本里对了几个」的**总数**，
> 不是「前 k 个里对了几个」。两者的含义完全不同：
>
> ```
> c = sum(outcomes)          ✅ 总正确数
> c = sum(outcomes[:k])      ❌ 只数了前 k 个
> ```
>
> 写成后者的话，正确的样本若恰好不在前 k 位，c 就会被算成 0，
> pass@k 直接归零。实测 `[F,F,F,T]` 在 k=1 时会返回 0（正确值 0.25）。

实测（对照**暴力枚举**参考实现）：

```
   n   k               outcomes       正确     本实现      参考值
    4   1 [False, False, False, True]       1    0.2500    0.2500
    4   2 [False, False, False, True]       1    0.5000    0.5000
    4   4 [False, False, False, True]       1    1.0000    1.0000
    5   3 [True, True, False, False, False]       2    0.9000    0.9000
    8   2 [True, False, True, False, ...]   2    0.4643    0.4643
    1   1                 [True]       1    1.0000    1.0000
    2   2         [False, False]       0    0.0000    0.0000
    3   2       [False, True, False]       1    0.6667    0.6667
```

**8 组全部与暴力枚举完全一致**（参考实现是
「枚举所有 k 个的组合，看有几个至少含一个对的」）。

### 错误版本会怎样

```
  n=4 k=1 [False, False, False, True]
    正确 0.2500   错误版 0.0000   <- 归零!
  n=4 k=2 [False, False, False, True]
    正确 0.5000   错误版 0.0000   <- 归零!
  n=8 k=2 [False, False, False, True, False, False, False, False]
    正确 0.2500   错误版 0.0000   <- 归零!
```

**三个 case 全部归零。**

⚠ 而 `[F,F,F,T]` 是一个**完全正常**的结果 ——
4 个样本里对了 1 个。`pass@1` 应该是 0.25。

**这个 bug 不会崩溃、不会警告，只会静默返回一个 0。**
所以必须由判据守住（`test_pass_at_k_matches_reference`）。

### k=1 的化简

```python
# 实测
  n= 1 c= 1: pass@1=1.000000  c/n=1.000000
  n= 4 c= 2: pass@1=0.500000  c/n=0.500000
  n= 8 c= 3: pass@1=0.375000  c/n=0.375000
  n=16 c= 1: pass@1=0.062500  c/n=0.062500
```

**`k=1` 时 `pass@1 = c/n` 精确成立。**

数学上：`1 - C(n-c, 1)/C(n, 1) = 1 - (n-c)/n = c/n`。

### ★ 但这个化简的价值在方差

docstring 说：

> 这个公式的价值在于：**可以用 n > k 的采样来更稳地估 pass@k**。
> 特别地，`k=1` 时式子化简正好是 `c/n` —— 于是「用 n 个样本估 pass@1」
> 和「取单个样本」是同一个量，但前者方差小得多。

实测（真实正确率 `p = 0.25`，4000 次采样）：

```
  n= 1: 均值 0.2480  标准差 0.4319
  n= 4: 均值 0.2449  标准差 0.2114
  n= 8: 均值 0.2491  标准差 0.1522
  n=16: 均值 0.2485  标准差 0.1082
```

| n | 标准差 | 相对 n=1 |
|---|---|---|
| 1 | 0.4319 | 100% |
| 4 | 0.2114 | **49%** |
| 8 | 0.1522 | 35% |
| 16 | 0.1082 | 25% |

**n=4 就把标准差砍了一半。** 而 docstring 说
「n=4 时标准差约为 n=1 的一半」—— **实测 49%，完全吻合**。

> 理论上 `std ∝ 1/√n`：`1/√4 = 50%`。实测 49%。
> **这是教科书级的吻合。**

**实践含义**：如果你要报「pass@1 = 62%」，
用 1 个样本的话这个数字的标准差是 ±43% —— **几乎没信息量**。
用 16 个样本才降到 ±11%。

## 指标三：多选题

```python
def evaluate_multiple_choice(model, tokenizer, items, device="cuda",
                             max_examples: int = 500) -> dict:
    """
    在一批选择题上评测。items 每项形如
        {"question": str, "choices": [str,...], "gold": int}
    """
```

### ★ 一个顺序陷阱

```python
# ★ 顺序：先记住原状态，再切 eval()。反过来写的话 eval() 已经把
#   training 置成 False，was_training 恒为 False，下面的还原成了死代码。
was_training = model.training
model.eval()
...
if was_training:
    model.train()
```

**这是一个典型的「看起来对但没生效」的 bug**：

如果写成

```python
model.eval()
was_training = model.training      # ← 恒为 False！
...
if was_training:
    model.train()                   # ← 死代码
```

**评测结束后模型留在 eval 模式。**

⚠ 本项目目前没有 dropout/batchnorm（第 14 章），所以这个 bug
**在数值上完全无影响**。但它是一个「等将来加了 dropout 就炸」的雷。

判据：`test_evaluate_multiple_choice_counts_and_restores_mode`。

### score 是**平均** logprob，不是总和

```python
targets = ids[:, 1:]
logprobs = F.log_softmax(logits[:, :-1].float(), dim=-1)
picked = logprobs.gather(-1, targets.unsqueeze(-1)).squeeze(-1)[0]  # (T-1,)
scores.append(picked[start - 1:].mean().item())
```

**最后是 `.mean()`。**

⚠ **为什么不能用 sum**：不同选项的长度可能不同
（`test_render_mc_handles_more_choices_than_letters` 这类）。
用 sum 的话长选项天然吃亏。

**用 mean = 「每个 token 的平均置信度」** ——
这是一个长度归一化的似然（几何平均概率）。

> **代价**：`mean(log p) = log(geomean(p))`，
> 所以它比「概率」更偏向保守 ——
> 任何一处低概率都会被平均掉。
> 这是个已知的不完美之处。

### `logits[:, :-1]` 与 `ids[:, 1:]` 的错位

**这是最经典的自回归错位。**

```
ids      = [t0, t1, t2, t3]
logits   = [l0, l1, l2, l3]     # l_i 预测的是 t_{i+1}
所以     logit[i] 对应 target[i+1]
```

所以要 `logits[:, :-1]` 配 `ids[:, 1:]`。

⚠ **写反了不会报错**，只会让所有分数变成垃圾
（用「预测当前 token」的 logprob 去评分「下一个 token」）。

`picked` 的长度是 `T-1`，然后 `[start - 1:]` 取从答案开始的部分。

> 那个 `-1` 又是一个错位修正 —— 因为 `picked` 已经错位过一次，
> 索引含义变了。

## 延伸

**为什么 bpb 是唯一可跨模型比的**

三个模型的「词表」「语言」都不同，所以：

| 指标 | 能否跨模型比 |
|---|---|
| loss (nats/token) | ❌ 词表不同 |
| perplexity | ❌ 同上 |
| **bpb (bits/byte)** | ✅ **只依赖原始文本** |

**bpb 的分母是原始 UTF-8 字节数** ——
这是所有 tokenizer 的公共分母。

第 06 章算过：`full` 档 V=16384，均匀 over 词表的基线是
`log2(V)/bytes_per_token` = **3.1466**（实测 4.4492 B/token）
或 1.7500（8 B/token 理想化）。⚠ 不是 `ln(V)/8` —— 那是 nats/byte。

**pass@k 的应用场景**

`pass@k` 在 Codex 论文里是**代码生成**的指标：
「生成 n 个，k 个里至少一个能通过测试」。

数学上和这里一样 —— 关键在**采样多样性**：
一个温度为 0（贪心）的模型 `pass@k = pass@1`（所有样本一样）；
温度高才有 `pass@k > pass@1`。

⚠ **这意味着报 pass@k 必须同时报采样配置**，否则数字没意义。

**无偏 vs 有偏估计**

| 估计方式 | 公式 | 问题 |
|---|---|---|
| **有偏（简单）** | `1 - (1 - c/n)^k` | 假设独立，忽略「有限 n」 |
| **无偏（本项目）** | `1 - C(n-c,k)/C(n,k)` | 精确 |

有偏版本在 `n >> k` 时差别很小，在 `n` 接近 `k` 时差别很大
（那时必须用无偏版本，否则可能算出负数或者大于 1）。

**多选题的替代方案：log-likelihood 之外**

| 方法 | 做法 | 问题 |
|---|---|---|
| **本项目** | 选项文本的平均 logprob | 长度归一，但对「正确答案较短」有偏 |
| Letter-based | 问「答案是 A/B/C/D」 | 需要模型会字母，MMLU 做法 |
| Logit-based | 直接比选项字母的 logit | 同上 |

**本项目两种都用，但用在不同的模型上** ——
这是个实测之后才想清楚的设计：

| 模型 | 用哪种 | 理由 |
|---|---|---|
| **基座**（`eval_base.sh`） | 选项文本的平均 logprob | 没接受过多选格式训练，「选字母」对它没有意义 |
| **SFT 后**（`eval_sft.sh`） | **生成式**：让模型直接吐一个字母 | SFT 恰恰教了它这个格式 |

### ★ 生成式评分器（`eval_sft.py` 的 `eval_mc`）—— 与上面那套是两回事

`src/evaluation/metrics.py` 的 `score_choices` 比的是
「选项**文本**的平均 logprob」。而 `src/training/eval_sft.py` 的
`eval_mc` 完全换了一套做法：

```python
ids = render_chat_prompt(tokenizer, ex["messages"][0]["content"])
kv = KVCache(1, m_nkv, m_hd, m_nl, len(ids), device, dtype=COMPUTE_DTYPE)
kv.cache_seqlens.fill_(len(ids) - 1)          # 只喂最后一个位置
with torch.no_grad():
    logits = model(torch.tensor([ids[-1:]], device=device), kv_cache=kv)

row = logits[0, -1]
best, best_logit = 0, float("-inf")
for j, L in enumerate("ABCD"):
    tid = tokenizer.encode(L)
    assert len(tid) == 1, f"字母 {L!r} 不是一个 token: {tid}"
    if row[tid[0]] > best_logit:
        best, best_logit = j, row[tid[0]]
```

**四个值得注意的设计**：

**① 只前向最后一个位置。**

`kv_cache_seqlens.fill_(len(ids) - 1)` 把 RoPE 的起点挪到正确位置，
于是「第 L-1 个位置的 k/v 已经算好了」—— 一次 prefill 都不需要。
**只算 1 个位置**，比分整个 prompt 便宜得多。

（这正是[第 32 章](32-推理引擎与KV-cache.md)那个「KV cache 省不下时间」
的例外：**decode 阶段本来就只算 1 个位置**，所以 cache 的价值在这里
体现为「prompt 只投影一次」，而不是「每步少算很多」。）

**② 只在 `A`/`B`/`C`/`D` 四个 token 里取 argmax。**

⚠ **不限制的话，SFT 步数很少的模型会 argmax 到 `<|python_start|>`
之类的特殊 token 上**，得出 0% 这种没有信息量的数字。

**③ 字母必须单独成为一个 token —— 这条断言是真需求，不是防御性编程。**

实测（V=16384）：

```
encode('A')    -> [65]        1 个 token ✓
encode(' A')   -> [328]
encode('A.')   -> [65, 46]    2 个 token ✗
encode('(A)')  -> [40, 65, 41]
```

**如果 `A` 被切成多个 token，那 `row[tid[0]]` 取的就是「`A` 第一个片段」的
logit** —— 而不同字母的片段位置不同、不可比，四个分数就是垃圾。

**④ 用 `render_chat_prompt` 而不是 f-string 拼 `<|user_start|>`。**

就是本章前面那个 `encode_ordinary` 坑 —— 拼字符串会被切成 12 个普通 token，
与训练格式不一致。

### ⚠ 两套评分**不能相减**

| | 基座（`eval_base.sh`）| SFT 后（`eval_sft.sh`）|
|---|---|---|
| 实现 | `metrics.score_choices` | `eval_sft.eval_mc` |
| 比什么 | 选项**文本**的平均 logprob | `A`/`B`/`C`/`D` 四个 **logit** 的大小 |
| 前向成本 | 整个 prompt（每选项一次）| **1 个位置** |
| 前置要求 | 无（基座也能跑）| **必须先 SFT**（否则不知道要吐字母）|

⚠⚠ **ARC-Challenge 从 22.7% 涨到 29.3% 看着像「SFT 提升了推理能力」，
但两列用的是上表两套完全不同的评分方式。**

**这不是「小改动」，是换了一把尺子。** 而且两把尺子的量纲也不同
（一个 log 概率、一个 logit）。

> **为什么基座评测要用 loglikelihood 那套**：
> 基座模型没接受过「回答一个字母」的训练，`eval_mc` 会得到纯噪声。
> 反过来，SFT 之后用 loglikelihood 也不合适 ——
> 那套假设「答案是选项里的一段文本」，而 SFT 教的是「吐一个字母」。
>
> **两套各有用武之地，关键是别把它们的结果放在同一张表里比较。**

---

**2026-10 实测印证了这个分工**（`ablation` 档 d6）：

| | 基座（loglikelihood） | SFT（生成式） |
|---|---|---|
| MMLU test | 27.0% | 23.7% |
| ARC-Easy | 24.0% | 24.7% |
| ARC-Challenge | 22.7% | **29.3%** |

⚠⚠ **这两列不可直接相减。** ARC-Challenge 那个 **+6.6** 看着像「SFT 提升了
推理能力」，**但主要是评分方式变了**。

> **这是一个很容易自己骗自己的地方**：
> 换了评分方式之后两列数字都还在 25% 附近，
> 而 ARC-C 恰好涨了 6.6 个点 —— 不加说明就会被当成「SFT 有效」。
>
> **`eval_sft.sh` 自己的提示说得很准**：
> 「看格式对不对比看准确率更有意义」。
> 格式确实学到了（[第 34 章](34-对话模板与SFT训练.md) 实测四个特殊 token
> 一个不缺），准确率没有。

**评测的方差**

第 29 章的验证 3 实测 `smoke` 档跑 3 步得到 `best_val_bpb = 3.24`。
**3 步训练的模型不该有任何质量** ——
这个数字完全反映的是「随机初始化的 bpb」。

⚠ **所以「跑几步就评测」只能验证管线能跑通，
不能验证模型质量。**
