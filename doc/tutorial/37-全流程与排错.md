## 完整流程

### 阶段 0：确认环境

```bash
uv run pytest -q                    # 期望 210 passed, 2 skipped
uv run ruff check .                 # 期望 All checks passed!
bash script/progress.sh             # 28 章的手抄进度
```

**⚠ 第一步必须在 `main`（骨架态）分支上跑**，且期望**有 failed**
—— 那是「你还有东西没敲」的意思。

在 `solution` 分支上跑会全绿 —— **那说明你走错分支了**。

### 阶段 1：验证数据管线

**不要一上来就训练。** 先花 2 分钟确认数据是对的：

```bash
uv run python scratch/check_data.py       # 数据集是否就绪
uv run python scratch/packing_demo.py     # 第 05 章的打包可视化
uv run python scratch/bpb_demo.py         # 第 06 章的 bpb 验证
uv run python scratch/ortho_demo.py       # 第 23 章的正交化验证
```

**为什么这一步值得**：

- `check_data.py` 能发现「训练 shard 缺失」这类问题 ——
  否则你会跑 44 分钟才发现
- `packing_demo.py` 让你**肉眼**确认 BOS 对齐和 best-fit 打包
- `ortho_demo.py` 能在 5 步里看到正交化收敛

**第 00 批的教训**：`~/.cache/gpt_base/` 里有 1 个训练 shard

所以「环境就绪」和「跑过训练」是两件事。

```bash
uv run python -m training.train_base --mode debug --num-iterations 5 --no-resume
```

**`debug` 档**：32 维 / 2 层 / 128 token，跑 5 步几秒钟。

**这个测试能发现**：

| 参数分组 assert 失败 | 新增参数漏分组（第 27 章） |


**这一步是真正的第一道关卡**：

**⚠ 不要跳过这一步直接跑 `full`（41 小时）。**

```
  scaling 参数量  : 176,160,768                   <- ★ 不是 195,035,136
  训练 token 数   = 2,188,613,248
  全局 batch      = 1,048,576 tokens = 128 × 8×1024
```

**逐条检查**：

| 行 | 该看到 | 看到别的 = 什么问题 |
|---|---|---|
| `COMPUTE_DTYPE` | `torch.bfloat16` | 不是 → fp32，会 OOM |
| `注意力后端` | `✓ 已启用` | `✗` → 退回 mem-efficient，慢 |
| **`词表`** | **`8192`** | **`16384` → 你没跑 `train_base`（或在用别的入口）** |
| `scaling 参数量` | **176,160,768** | 不同 → 第 27 章的 muP 缩放变了 |
| `全局 batch` | `128 × 8×1024` | 不同 → 显存不够（第 00 批的教训） |
| `Muon flavor` | `advanced` | `simple` → `--muon-advanced` 没传 |
| `Weight decay` | `峰值 0.02134` | `λ_ref=0` → 谨慎 WD 整条空转（第 26 章） |

## ★ 为什么「按预设推的数」和「实测的数」不一样

这是本章最该记住的一条，来自[第 29 章](29-训练循环.md) 的实测。

`ModelConfig` 的定义：

```python
vocab_size: int = 16384       # 由 tokenizer 决定
```

**默认值写死 16384，注释却说「由 tokenizer 决定」。**

而 `train_base.main` 无条件覆盖：

```python
cfg = make_run_config(args.mode, depth=args.depth,
                      vocab_size=tokenizer.get_vocab_size())
```

本仓库的 tokenizer 是 **8192**。**所以预设里的 16384 没有真正生效。**

| 量 | 按预设 16384 推（**旧文档写的**） | 按实际 8192（**真正训的**） |
|---|---|---|
| `ln(V)` 随机基线 | 9.7041 | **9.0109** |
| `lm_head`（d24） | 12,582,912 | **6,291,456** |
| 12 张 ve 表（d24） | 150,994,944 | **75,497,472** |
| `scaling_params`（d24） | 195,035,136 | **176,160,768** |

### ★ 根因：tokenizer 缓存不按词表大小分桶

**注意 `16384` 才是本项目的本意**，链条是：

```
script/_common.sh:      debug|smoke → VOCAB=8192
                        ablation|full → VOCAB=16384
script/train_base.sh:   python -m training.train_tokenizer --vocab-size "$VOCAB"
```

问题在 `src/training/train_tokenizer.py`：

```python
ckpt = os.path.join(tokdir, "tokenizer.pkl")
if os.path.exists(ckpt):
    log0(f"tokenizer 已存在，跳过训练：{ckpt}")
else:
    tok = BPETokenizer.train(..., args.vocab_size)
```

**只判断文件存在，不检查词表大小是否等于 `args.vocab_size`。**

实测（当前仓库状态）：

```
$ uv run python -m training.train_tokenizer --vocab-size 16384 --shards 2
tokenizer 已存在，跳过训练：.../tokenizer/tokenizer.pkl
── 压缩率报告 ──────────────────────────────
chars / token  : 3.240
压缩率         : 3.240 bytes/token
词表大小       : 8,192          ← 要求的是 16384
```

**因果链**：

1. 第一次跑的是 `smoke`（或 `debug`）→ 缓存里建了一个 **8192** 的 tokenizer
2. 后来跑 `ablation` / `full`，传 `--vocab-size 16384`
3. 文件已存在 → **静默复用那个 8192 的**
4. `train_base` 读 `get_vocab_size()` = **8192** → 真的按 8192 训练

⚠ **`词表大小 : 8,192` 就在日志里，但它上面那行写的是「跳过训练」** ——
读起来像「一切正常」。**没有任何一行说「这和你要的 16384 不符」。**

### 为什么没判据发现

`test_presets.py` 有一条判据检查 **`script/*.sh` 里的 `VOCAB=`
与 tokenizer 是否一致** —— 但它在 `smoke` 下**是绿的**
（`smoke` 本来就要 8192）。

而所有 `make_run_config(..., vocab_size=8192)` 的用法都是
**显式传参**，恰好绕开了「不传时会用 16384」这条路径。

**判据检查的是「配置与 tokenizer 一致」，
没检查「tokenizer 是不是用户要的那个大小」。**

### 影响面

修好之后，`ablation` / `full` 档**真的会按 V=16384 训练**，
嵌入表显存翻倍（`lm_head` 6.29M → 12.58M，12 张 ve 表 75.5M → 151M）。
**这会改变这两个档位的全部训练结果**，且上表四行数字全部要重算。

⚠ **本会话只记录不修**（改行为属于用户决策）。
修法见[第 29 章](29-训练循环.md)的「修法」小节。

## 排错清单

### 症状：loss = NaN

**按这个顺序查**：

1. **是不是第 15 章的 softcap 关了**？
   `logits` 涨到 30+ 时 softmax 饱和 → 梯度消失
2. **是不是 SFT 的 truncate 错了**？
   第 34 章：mask 全 0 → `0/0 = NaN`
   （有兜底降级成 0，但**那一步等于白跑**）
3. **是不是 bf16 下算了 `1 - beta2`**？
   第 21 章：`beta2=0.999` 时 `1-beta2=0.001` 在 bf16 里是 0
   → `adamw_step` 第一行的 `.float()` 就是防这个
4. **`grad_clip` 打开了？** 默认是 0.0（关闭）

**快速定位**：

```bash
uv run python -m training.train_base --mode debug --num-iterations 5 \
    --no-resume 2>&1 | grep -E "loss|警告"
```

### 症状：启动日志里的参数量和文档对不上

**先看 `词表` 那一行。**

第 29 章的实测：预设写 `vocab_size=16384`，
但 `train_base.main` 无条件用 `tokenizer.get_vocab_size()` 覆盖，
本仓库的 tokenizer 是 **8192**。

所以这两条**才是正常的**：

| 你看到的 | 文档旧值 | 说明 |
|---|---|---|
| `词表 : 8192` | （文档假设 16384） | **正常** |
| `scaling 参数量 = 176,160,768` | 195,035,136 | **正常**（`lm_head` 尺寸差一倍） |

⚠ **凡是靠 `V` 推出来的数字都要重算**：
`ln(V)`、`lm_head` 尺寸、ve 表参数量、嵌入表显存。

**自查一行**：

```bash
uv run python -m training.train_base --mode smoke --num-iterations 1 \
    --no-resume 2>&1 | grep 词表
```

### 症状：`平均 MFU` 大于 100%（或大得离谱）

**别当成 bug 报告 —— 它本来就是 bug。**（[第 29 章](29-训练循环.md)）

分子数了 `num_iterations` 步，分母 `total_time` 只累加 `step > 10` 的步。

**误差 = `num_iterations / (num_iterations - 11)`**：

| 跑多少步 | 误差 |
|---|---|
| 13 | 高估 **696 倍** |
| 1,000 | 高估 1.1% |
| 2,088（`full` 全程） | 高估 **0.53%** |

**所以短跑测试恰好是最容易骗过你的场景。**

**正确的看 MFU 的方式**：看逐步日志里 `mfu` 那一列，
或自己按同口径重算（第 29 章验证 1c）。

### 症状：loss 完全不降

1. **看 step 0 的 loss 是否 ≈ `ln(8192) = 9.0109`。**
   不是 → 初始化或词表有问题（见上一条）
2. **`lr_mult` 是不是恒为 0？** 第 30 章：`(step+1)/warmup` 保证不为 0，
   但 `warmup_steps <= 0` 就会炸
3. **实际 lr 是不是 0？** 第 30 章坑 5：`lr_mult` 之外还有
   `dmodel_lr_scale` 和 `batch_lr_scale` 两层因子
4. **参数是不是根本没在更新？** 跑 `test_adamw_step_actually_moves_params`

### 症状：`CUDA driver error: device not ready`

**这是 `device_batch_size` 太大**。

第 00 批的实测记录：

> dbs=12 峰值 15.01 GiB 可用（错，第 2 步 `CUDA driver error: device not ready`）

**规律：单步测量不可信** —— 第 1 步能跑不代表第 2 步能跑
（优化器状态在第 1 步才分配完）。

**解决**：降 `device_batch_size`，等量升 `grad_accum_steps`：

```bash
bash script/train_base.sh full --device-batch-size 6 --num-iterations 2088
# 总 batch 不变，但峰值显存降下来了
```

⚠ **必须连跑 3-4 个完整 step 才能判断显存够不够**。

### 症状：loss 下降但 bpb 不动

1. **`best_val_bpb` 一直是 `null`？**
   → 第 36 章：`inf` 存成 `null`，忘了还原就会崩（所以没崩说明有值）
2. **验证真的在跑吗？** 看 `history.csv` 里有没有 `val_bpb` 那一列
3. **val loader 建了吗？** 第 29 章 6.4 的 `eval_every > 0`

### 症状：日志里 `torch.compile 不可用`

第 28 章：`fullgraph=True` 遇到不支持的算子会**静默回落**。

**检查**：

```bash
gcc --version          # 需要 gcc（本机 15.2）
```

**代价**：`full` 档从 45.4 小时变 55.3 小时（**+22%**）。

⚠ **这是「不报错只变慢」的 bug** —— 唯一的线索是日志那一行。

### 症状：两个消融的 bpb 一模一样

第 02 章记着的那个真实 bug（`use_rope`）的形状：
**开关只出现在打印字符串里，forward 无条件生效**。

**排查**：

```bash
# 1. 开关在 CLI 里能改 config 吗？
uv run python -m training.train_base --mode smoke --num-iterations 1 \
    --no-resume --all-tricks --no-smear 2>&1 | grep "残差流 trick"
# 期望：trick 列表里没有 smear

# 2. 在 solution 分支上建模型，直接比结构
uv run pytest tests/test_core.py -k ablation_switches -v
```

### 症状：`assert` 说参数分组不完整

第 27 章：`setup_optimizer` 里

```python
assert accounted == sum(1 for _ in model.parameters()), (
    f"参数分组不完整：分到 {accounted} 个，模型有 "
    f"{sum(1 for _ in model.parameters())} 个")
```

**这说明你新增了一个参数，但没在分组规则里处理。**

修法：加一个 `elif` 分支。**别删这条 assert** ——
它是「新增参数被漏掉」的唯一防线。

⚠ 但注意：**它只抓「完全没分组」，抓不到「分错组」**
（第 27 章的 `smear_gate` 就在 Muon 组里）。

### 症状：续训后 loss 突然变大

**正常。** 第 36 章：优化器状态不入 checkpoint。

> 后果是断点续训会丢失优化器动量，**头几十步会有一段小抖动**。

**处理**：忽略前 20-50 步的 loss 曲线。

### 症状：中文输出乱码

第 33 章那个 `decode(encode(text)) == text` 的性质意味着
**encode 侧的 bug 在 decode 侧看不出来**（第 34 章）。

如果 `decode` 出来是乱码，说明 encode 就已经错了 ——
去查 `encode_ordinary` vs `encode_special`（第 34 章）。

### 第 00 批的教训：计数会连锁

⚠ **`test_tutorial_claims_match_reality` 用的是精确相等** ——
**新增一个测试就必须同步 4 处**：

1. `scratch/audit_docs.py` 的 `CHAPTER_TESTS`
2. `tests/test_judging_soundness.py` 的 `minimum`
3. 文档里的「N 个测试」
4. 文档里的「M passed, K skipped」

第 00 批新增两条判据时漏了一处，测试立刻红了。

**第 25 章之后本会话加判据时已经形成习惯**：
先改测试 → 跑 audit → 按它的报错同步 → 再跑。

### `floor` vs `==` 的区别

```python
minimum = {
    "test_core.py": 30,            # 卷2-3
    ...
}
for name, floor in minimum.items():
    n = _collected(path)
    assert n >= floor, (...)
```

docstring 解释了这个设计：

> - 「删除测试」-> 数量跌破 floor -> **能抓到**（与 == 等价）
> - 「新增测试」-> 放行（这是 == 做不到的，也正是改用 >= 的唯一理由）
>
> 精确数字的核对不在这里，而在 `scratch/audit_docs.py`：
> 它比对 `CHAPTER_TESTS` 字典并在不符时退出非零。
> **两者分工：本测试 = 快速、防灾难性掏空；audit_docs = 精确。**

⚠ **所以「跑 pytest 全绿」不等于「文档里的数字对」** ——
要跑 `uv run python scratch/audit_docs.py` 才行。

## 延伸

**卷 1-4（手抄）和卷 5-8（只读）的区别**

| | 卷 1-4 | 卷 5-8 |
|---|---|---|
| 学法 | **敲**出 `raise NotImplementedError` 的地方 | **读** `src/` |
| 判据 | 同一套 pytest，两种状态 | 同一套 pytest，只一种状态 |
| 风险 | 敲错 | **改坏** |
| 主要 bug 类 | 形状/布局（第 02/07/11 章） | **静默失效**（第 24/25/28 章） |

**手抄章的错误会立刻暴露**（形状不对就 assert）。
**只读章的错误往往是静默的** —— 第 24 章的 `ns_steps>5`、
第 25 章的 `use_muon_plus`、第 28 章的 compile 回落，
**三个都不报错，只是没效果**。

**所以卷 5-8 的判据设计原则是：
「关掉一个东西之后，两个版本必须真的不同」**
（见第 25 章那条判据的迭代过程 ——
第一版只查「参数是否存在」，抓到 bug 才改成「扰动权重看输出变不变」）。

**整条流水线的成本**

| 阶段 | 耗时 | 产出 |
|---|---|---|
| 0 环境 | 1 分钟 | — |
| 1 数据验证 | 2 分钟 | 确认数据管线 |
| 2 冒烟 | 30 秒 | 确认能跑 |
| 3 `ablation` | **44 分钟** | 第一个能用的模型 |
| 4 `full` | **34.1 h（本次实测外推）**<br>**41.2 h（旧记录）** | 目标模型 |
| 5 评测 | 几分钟 | `val_bpb` |
| 6 SFT | 视数据量 | 对话能力 |
| 7 对话 | — | — |

⚠ 第 4 行的两个数并列，理由见本章开头「实测基线」一节。
**`full` 档从未真正跑完过** —— 34.1 h 是用 13 步的稳态 `dt`
外推的，不是全程测出来的。

**所以「先跑 ablation 再跑 full」省的不是时间，是「44 分钟后
才发现 full 档某个超参不对」的风险。**
