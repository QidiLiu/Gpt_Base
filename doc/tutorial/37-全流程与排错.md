## 完整流程

### 阶段 0：确认环境

```bash
uv run pytest -q                    # 期望 225 passed, 2 skipped
uv run ruff check .                 # 期望 All checks passed!
bash script/progress.sh             # 28 章的手抄进度
```

**⚠ 第一步必须在 `main`（骨架态）分支上跑**，且期望**有 failed**
—— 那是「你还有东西没敲」的意思。

在 `solution` 分支上跑会全绿 —— **那说明你走错分支了**。

### 阶段 1：验证数据管线

**不要一上来就训练。** 先花 2 分钟确认数据是对的：

```bash
uv run python scratch/check_data.py       # 数据集是否就绪
uv run python scratch/packing_demo.py     # 第 05 章的打包可视化
uv run python scratch/bpb_demo.py         # 第 06 章的 bpb 验证
uv run python scratch/ortho_demo.py       # 第 23 章的正交化验证
```

**为什么这一步值得**：

- `check_data.py` 能发现「训练 shard 缺失」这类问题 ——
  否则你会跑 44 分钟才发现
- `packing_demo.py` 让你**肉眼**确认 BOS 对齐和 best-fit 打包
- `ortho_demo.py` 能在 5 步里看到正交化收敛

**⚠ 这一步不能跳过。** 2026-10 实测踩到过一个真实的坑：
`~/.cache/gpt_base/tokenizer/` 里躺着一个**别的档位建的** tokenizer，
而 `train_tokenizer` 当时只判断文件存不存在、不检查词表大小 ——
于是 `ablation` 传进去的 `--vocab-size 16384` 被静默忽略，
整轮训练跑在一个**从未被设计过的配置**上（详见本章后面那节）。

**现在 `train_tokenizer` 会核对词表大小**，所以脚本会按需重建。
但「数据 shard 够不够」仍然是你的责任：
`ablation` 要 4 个训练 shard，缓存里可能只有 1 个。

所以「环境就绪」和「跑过训练」是两件事 —— 而 `check_data.py`
只查前者。

### 阶段 2：冒烟测试（几分钟）

```bash
uv run python -m training.train_base --mode debug --num-iterations 5 --no-resume
```

**`debug` 档**：32 维 / 2 层 / 128 token，跑 5 步几秒钟。

**这个测试能发现**：

| 现象 | 说明 |
|---|---|
| `assert` 失败 | 形状对不上（第 02/07 章的坑） |
| loss = NaN | 初始化或数值问题 |
| 参数分组 assert 失败 | 新增参数漏分组（第 27 章） |
| `[optim] torch.compile 不可用` | 缺 gcc（第 28 章） |

### 阶段 3：短训练（44 分钟）

```bash
bash script/train_base.sh ablation --no-resume --model-tag d6_probe
```

**`ablation` 档**：384 维 / 6 层 / 3096 步。

**这一步是真正的第一道关卡**：

- 能跑完说明所有子系统都正常
- `val_bpb` 会落在某个合理量级（随机初始化约 1.2）
- 可以试各种消融开关

**⚠ 不要跳过这一步直接跑 `full`（41 小时）。**

## ★ 为什么「按预设推的数」和「实测的数」不一样

这是本章最该记住的一条，来自[第 29 章](29-训练循环.md) 的实测。

`ModelConfig` 的定义：

```python
vocab_size: int = 16384       # 由 tokenizer 决定
```

**默认值写死 16384，注释却说「由 tokenizer 决定」。**

而 `train_base.main` 无条件覆盖：

```python
cfg = make_run_config(args.mode, depth=args.depth,
                      vocab_size=tokenizer.get_vocab_size())
```

修复前本仓库的 tokenizer 是 **8192**，所以预设里的 16384 没有真正生效。

| 量 | 文档旧值 | 修复前实测（V=8192） | **修复后实测（V=16384）** |
|---|---|---|---|
| `ln(V)` 随机基线 | 9.7041 | 9.0109 | **9.7041** ✓ |
| `lm_head`（d24） | 12,582,912 | 6,291,456 | **12,582,912** ✓ |
| 12 张 ve 表（d24） | 150,994,944 | 75,497,472 | **150,994,944** ✓ |
| `scaling_params`（d24） | ~~195,035,136~~ | 176,160,768 | **182,452,224** |

⚠ **最后一行是另一个独立的文档错误**，与词表 bug 无关：
`195,035,136 = matrices + lm_head + **wte**`，
而 `scaling_params()` 明确**不含 `wte`**（它是查找表，不是矩阵乘）。

```
真实值 182,452,224 = matrices(169,869,312) + lm_head(12,582,912)
文档值 195,035,136 = matrices(169,869,312) + lm_head(12,582,912) + wte(12,582,912)
```

（巧合：`195,035,136` 也正好等于 **V=32768** 时的 `scaling_params`。）

### ★ 根因：tokenizer 缓存不按词表大小分桶

**注意 `16384` 才是本项目的本意**，链条是：

```
script/_common.sh:      debug|smoke → VOCAB=8192
                        ablation|full → VOCAB=16384
script/train_base.sh:   python -m training.train_tokenizer --vocab-size "$VOCAB"
```

问题在 `src/training/train_tokenizer.py` —— 原来是：

```python
if os.path.exists(ckpt):
    log0(f"tokenizer 已存在，跳过训练：{ckpt}")
```

**只判断文件存在，不检查词表大小是否等于 `args.vocab_size`。**

实测（修复前的行为）：

```
$ uv run python -m training.train_tokenizer --vocab-size 16384 --shards 2
tokenizer 已存在，跳过训练：.../tokenizer/tokenizer.pkl
── 压缩率报告 ──────────────────────────────
压缩率         : 3.240 bytes/token
词表大小       : 8,192          ← 要求的是 16384
```

**因果链**：

1. 第一次跑的是 `smoke`（或 `debug`）→ 缓存里建了一个 **8192** 的 tokenizer
2. 后来跑 `ablation` / `full`，传 `--vocab-size 16384`
3. 文件已存在 → **静默复用那个 8192 的**
4. `train_base` 读 `get_vocab_size()` = **8192** → 真的按 8192 训练

⚠ **`词表大小 : 8,192` 就在日志里，但它上面那行写的是「跳过训练」** ——
读起来像「一切正常」。**没有任何一行说「这和你要的 16384 不符」。**

### ✅ 已修

三处改动。

**① `train_tokenizer` 复用前核对词表大小**

```python
need_train = True
if os.path.exists(ckpt):
    try:
        cached_vocab = BPETokenizer.load(tokdir).get_vocab_size()
    except Exception as e:
        log0(f"缓存的 tokenizer 读不出来（{type(e).__name__}...），重建")
        cached_vocab = None
    if cached_vocab == args.vocab_size:
        log0(f"tokenizer 已存在（V={cached_vocab}），跳过训练：{ckpt}")
        need_train = False
    elif cached_vocab is not None:
        log0(f"缓存的 tokenizer 是 V={cached_vocab}，"
             f"与要求的 V={args.vocab_size} 不符 -> 重建")
```

**读不出来也重建** —— 半个 pkl / 版本不兼容的情况同样该重建。

⚠ **同时保住「大小一致时复用」** —— 否则每次跑入口脚本都要重训
（`ablation` 档要几分钟），脚本会变得没法用。
有判据专门守这一条（`test_tokenizer_cache_is_reused_when_vocab_size_matches`）。

**② 顺带修一个相关的不一致**

```python
# 原来：report_compression(BPETokenizer.load())        # 没传目录
# 现在：report_compression(BPETokenizer.load(tokdir))
```

不传目录会回落到 `get_tokenizer_dir()`，也就是**报告的是「别处那个」
tokenizer 而不是刚处理过的这个**。生产路径上 `tokdir == get_tokenizer_dir()`
所以看不出问题，但它让「报告」和「实际处理的对象」脱钩了。

**③ `train_base` 加最后一道防线**

直接调 `python -m training.train_base` 会绕过 `train_base.sh`，
也就绕过了 ① 的重建检查。所以 `main()` 里再比一次：

```python
for _line in vocab_mismatch_messages(
        args.mode, PRESETS[args.mode]["vocab_size"], tokenizer.get_vocab_size()):
    log0(_line)
```

实测输出：

```
  [注意] tokenizer 的词表是 V=8192，但 full 档期望 V=16384。
         本次将按 V=8192 训练（预设里的 16384 只作占位，不影响计算）。
         若要按 16384 训练：先跑 `bash script/train_base.sh full`
         （它会按词表大小重建 tokenizer），或 `rm -rf ~/.cache/gpt_base/tokenizer` 后重跑。
```

**只告警不中断** —— V=8192 训得动，而 `debug`/`smoke` 本来就要 8192。
告警逻辑抽成 `vocab_mismatch_messages()` 纯函数，因为
**「告警逻辑本身」也是判据该覆盖的行为**，不测它会随重构悄悄消失。

### 判据：6 条，全过故障注入

`tests/test_presets.py` 新增 6 条（15 → 21）：

| 判据 | 守什么 |
|---|---|
| `test_tokenizer_cache_is_reused_when_vocab_size_matches` | **别把修复做成每次都重训** |
| `test_tokenizer_cache_rebuilds_when_vocab_size_differs` | ★ bug 本体 |
| `test_token_bytes_cache_is_regenerated_together_with_tokenizer` | ★ 第二阶后果 |
| `test_train_base_warns_when_tokenizer_vocab_differs_from_preset` | 最后一道防线 |
| `test_average_mfu_numerator_and_denominator_cover_the_same_steps` | ★ MFU 口径 |
| `test_average_mfu_can_never_exceed_100_percent` | MFU > 100% 不可能 |

**第三条值得单独说**：`token_bytes.pt` 必须和 `tokenizer.pkl` 一起换，
否则 **bpb 会静默算错** —— 而 bpb 是本项目唯一跨模型可比的指标。
所以这两者是同一个「重建单元」，不能分开缓存。

**故障注入验证**（写完判据必须做，否则不知道判据会不会红）：

```
注入 1  还原 train_tokenizer 的「只判存在」
  -> 2 条变红，复用那条正确保持绿（没误伤）
注入 2  还原 MFU 分子口径
  -> 物理自检直接拦下：MFU=19267% 超出 (0,100)
```

### ⚠ 验证判据时最容易犯的一个错：注入点选错

**我第一次注入 `test_special_tokens_are_sequential_tail` 时，
判据没有变红。** 差点就此判定「这条判据抓不住」。

真实原因是我把注入打在了 `BPETokenizer.train` 里：

```python
# 我的注入（无效）
special_tokens = {name: offset + i + 1 for i, name in enumerate(SPECIAL_TOKENS)}
```

而**判据不调 `train`** —— 它 `get_tokenizer()` 加载的是**缓存里的 pkl**，
那个 pkl 是在注入之前生成的。**注入根本没进入被测路径。**

改到 `encode_special`（判据真正执行的那一行）：

```
注入 A  encode_special 整体 +1
  -> assert 16376 == (16384 - 9) + 0    红 ✓
注入 B  把第一个特殊 token 换到末尾（破坏顺序）
  -> assert 16383 == (16384 - 9) + 0    红 ✓
还原    -> 绿
```

> **「判据没红」有两种可能，而第二种更常见：**
> ① 判据抓不住这个 bug
> ② **注入根本没进到被测路径**
>
> 区分它们的方法：**再换一个注入点试一次。**
>
> **如果你只试了一个注入点就宣布「判据无效」，
> 你会去改一条其实完全正确的判据。**
> 本项目已经因此栽过（第 00 批：同号初值下逐位相同，
> 必须用反号才区分得出）。

### 顺带修掉第 4 处「把环境值写死」的判据

`test_special_tokens_are_sequential_tail` 原来有一行：

```python
assert V - n == 8183, "普通 token 数应等于 vocab_size - n"
```

**8183 不是不变量**，它是「当时缓存里那个 tokenizer 的词表大小减 9」。

结果**修好 tokenizer 缓存 bug 之后**（V 从 8192 变成 16384），
这条判据**立刻红了** —— 而它 docstring 声称要守的东西
（「特殊 token 占最后 9 个 id 且顺序一致」，由下面的循环守着）**毫发无损**。

**它验证的是缓存状态，不是那个不变量。**

改成只守环境无关的部分：

```python
assert V > n
for i, name in enumerate(SPECIAL_TOKENS):
    assert tok.encode_special(name) == V - n + i          # 真正的不变量
assert V in {p["vocab_size"] for p in PRESETS.values()}   # 词表大小必须是某个预设的
```

> **这是本项目第四次出现同一类问题**：
> `weight_decay_final_frac`（死配置）、5 个无 CLI 入口的 `use_*` 开关、
> 预设里从不生效的 `vocab_size`、以及现在这条把环境值写死的判据。
>
> **共通点：都把「某个具体取值」当成了「一条规律」。**
> 写判据时要问的不是「这个值对不对」，而是
> **「换成另一个合法取值，这条判据还该成立吗？」**

### 修复后你的环境会怎样

**你当前缓存里那个 V=8192 的 tokenizer 现在会被判为「不符」**，
所以下次跑 `bash script/train_base.sh ablation` 会**自动重建一个 16384 的**。

⚠ **那意味着 `ablation` / `full` 档从此真的按 V=16384 训练** ——
本章开头那张「按预设 vs 实际」对照表描述的是**修复前**的状态。
按 16384 算的历史章节（第 02/07/15/18/22 章）会重新变成对的。

**自查**：

```bash
uv run python -m training.train_tokenizer --vocab-size 16384 --shards 2   # 重建
uv run python -m training.train_tokenizer --vocab-size 16384 --shards 2   # 再来
# 第二遍应该出现：tokenizer 已存在（V=16384），跳过训练
```

### 阶段 6：SFT

```bash
bash script/train_sft.sh full
bash script/eval_sft.sh full
```

**`ablation` 档实测：869 步 / 1m30s**（比预训练快 30 倍，因为
`dbs=8`、`seq_len=1024`、且只有对话数据）。

⚠ **两个该看的日志行**：

```
（已跳过 N 条无有效监督信号的对话）    ← 正常，N 应该很小
[警告] 本批没有有效的监督 token        ← ★ 如果出现这个，说明有 bug
```

**第一个是数据层的正常过滤**（`train_sft.py:107`），
`truncate="left"` 正确时 N 通常是个位数。

**第二个是事后兜底**（`gpt.py`）—— 有第一个在，
**SFT 路径上它永远不该触发**。出现了就说明 dataloader 的过滤被绕过了。

### 第 00 批的教训：计数会连锁

⚠ **`test_tutorial_claims_match_reality` 用的是精确相等** ——
**新增一个测试就必须同步 4 处**：

1. `scratch/audit_docs.py` 的 `CHAPTER_TESTS`
2. `tests/test_judging_soundness.py` 的 `minimum`
3. 文档里的「N 个测试」
4. 文档里的「M passed, K skipped」

第 00 批新增两条判据时漏了一处，测试立刻红了。

**第 25 章之后本会话加判据时已经形成习惯**：
先改测试 → 跑 audit → 按它的报错同步 → 再跑。

### `floor` vs `==` 的区别

```python
minimum = {
    "test_core.py": 30,            # 卷2-3
    ...
}
for name, floor in minimum.items():
    n = _collected(path)
    assert n >= floor, (...)
```

docstring 解释了这个设计：

> - 「删除测试」-> 数量跌破 floor -> **能抓到**（与 == 等价）
> - 「新增测试」-> 放行（这是 == 做不到的，也正是改用 >= 的唯一理由）
>
> 精确数字的核对不在这里，而在 `scratch/audit_docs.py`：
> 它比对 `CHAPTER_TESTS` 字典并在不符时退出非零。
> **两者分工：本测试 = 快速、防灾难性掏空；audit_docs = 精确。**

⚠ **所以「跑 pytest 全绿」不等于「文档里的数字对」** ——
要跑 `uv run python scratch/audit_docs.py` 才行。

| | 卷 1-4 | 卷 5-8 |
